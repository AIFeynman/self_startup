# 主题学习计划：方法论与 JSON 格式

目标：把一个陌生主题变成「专业级」、循序渐进的学习路径——三轮由浅入深：先拿到最新全貌和主干机制，再学会判断，最后跟上前沿、用项目和产品实践检验。每一步都可打分、反馈、调整。

## 三轮由浅入深（stage 字段填 1 / 2 / 3，按顺序；每轮结束用户都可以停下）

技术发展很快，所以**先给最新的全貌，再往深处走**；主线只讲主干，用户对某个点感兴趣或没懂时，平台会「按需加一节」现场补，计划里不要预先铺满。

1. **第 1 轮 · 看懂：最新全貌 + 主干机制**（2–3 步，约 5 小时）
   - 目的：拿到这个领域**最新的整体地图**（分类、每个方向的痛点 / 热点 / 开放问题 / 主流方案），并吃透撑起它的 2–3 个最核心机制；学完能把任意一篇新论文或新产品定位到地图上、讲清它靠什么机制工作。
   - 第一步必须基于**最新的综述或书籍**：先联网检索近 12 个月的综述 / 书 / 权威课程（arXiv、出版社、作者主页），选最新且质量高的作为主读物，写明发表或更新日期；最新的也超过 12 个月时，在步骤里说明之后的关键变化、补读什么。不要用三年前的经典综述当全貌。思路可参考 `~/.codex/skills/domain-landscape/SKILL.md`（根问题、约束、核心机制、失效边界、相邻领域）。
   - 机制步骤：每步一个机制，直觉 → 形式化 → 最小实现 → 失效条件，附可推导 / 可复现的材料。
2. **第 2 轮 · 会判断：经典讲透机制 + 一线人物的判断**（3–4 步，约 6–8 小时）
   - 目的：知道主干是怎么来的、为什么有效，并能像一线的人一样对新方案下判断。
   - 经典论文和机制合在一起讲：「一篇奠基论文讲透一个机制」——当时卡在哪 → 关键洞察 → 方法核心 → 证据 → 局限 → 后续谁接着做。不要把经典和机制拆成两步重复讲。
   - 人物观点放在这一轮（懂了机制才看得出判断的好坏）：3–6 位代表人物 / 团队，「核心判断 → 依据 → 过往预测与后来的实际情况 → 分歧」。
3. **第 3 轮 · 跟前沿、做出来：最新进展 + 项目与产品实践**（3–4 步，约 6–8 小时）
   - **前沿**（1–2 步）：同样要**最新**——近 6–12 个月的论文、技术报告、开源发布，优先最近 3 个月；每项写日期和证据级别（预印本 / 会议 / 已部署）、相对已有工作的增量、证据可不可信。
   - **项目实践**（1 步）：挑 1–2 个代表性的 GitHub 开源项目（写 star 数和最近提交日期，选活跃的），读架构和关键实现：它把本领域哪个机制落成了代码、做了哪些工程取舍；资源里放仓库链接（type: repo），平台可以一键速读。
   - **产品实践**（1 步）：挑 1–3 个对标的外部产品 / 工具 / 服务（真实存在、用户能上手的，写清是否免费、怎么开始用），让用户**亲手用**，按评估维度写一份使用评估：能做什么、效果和证据、和本领域方法的对应、短板与坑、适合谁、和同类比怎样。评估维度在步骤 description 里给出（4–6 条，可直接当 rubric）。

总共 8–11 步，主线总时长 15–20 小时（每周投入多的可以到 25 小时，少的压到 12 小时），每步不超过 2 小时（实践步骤不超过 3 小时）。按用户背景跳过已会内容、加强薄弱处。

每一步之后会被平台展开成一章教程 + 章末测试，所以步骤要「一章能讲完、能考」：主题聚焦，`goal` 写清这一步学完要具备的具体能力（可检验，例如「能把一篇新的 Agent 评测论文归到 4 个分支之一并说出它针对的痛点」「能按 5 条维度写出对 X 的使用评估并和 Y 对比」）。

## 资源要求
- 只给真实存在的链接；能访问的先用 WebFetch/curl 核对，`verified: true`；无法核对的 `verified: false`，不要编造 URL。
- `type`: paper / book / course / video / blog / repo / doc / talk / product。
- 综述、书、前沿论文写 `date`（发表 / 更新日期）；仓库写最近提交日期和 star 数；产品写清是否免费、怎么开始用。
- `why`: 一句话说明它在这一步解决什么。

## 检查题
- 每步 2–4 道，能检验理解而非记忆（「为什么」「如果没有…会怎样」「如何验证」）。

## 生成计划时输出的 JSON（最终回复里放一个 ```json 代码块）
```json
{
  "overview_md": "Markdown：主题边界、底层逻辑一段话、路线总览（每阶段一句话写清目的）、资料时效（主要综述的日期、是否最新、之后的关键变化）、资料核对日期",
  "steps": [
    {"stage": 1, "title": "...", "goal": "学完这一步能做到什么（具体、可检验）", "description": "做什么、产出什么（Markdown 可）",
     "resources": [{"title": "...", "url": "https://...", "type": "paper", "date": "2026-08", "why": "...", "verified": true}],
     "questions": ["..."], "est_hours": 3}
  ]
}
```

## 根据反馈调整时输出的 JSON
```json
{
  "summary": "一两句：发现了什么问题、怎么调",
  "edits": [
    {"op": "add", "stage": 2, "after_step_id": 12, "title": "...", "description": "...", "resources": [], "questions": [], "est_hours": 2},
    {"op": "modify", "step_id": 13, "title": "...", "goal": "...", "description": "...", "est_hours": 3, "questions": ["..."]},
    {"op": "skip", "step_id": 15, "reason": "已掌握"},
    {"op": "add_resources", "step_id": 12, "resources": [{"title": "...", "url": "...", "type": "blog", "why": "补救：..."}]}
  ]
}
```
调整原则：章末测试得分低（<60）或理解度 ≤2 或反馈说没懂 → 补前置/换更易懂的资源（add_resources 或 add 补救步）；理解度 5 且很快完成 → 后续同类步骤可 skip 或加深；不修改已 done 的步骤；只做有依据的少量修改。

## 老计划（六阶段）

2026-10-31 之前生成的计划用六个阶段：1 领域综述、2 核心人物与观点、3 关键书籍 / 经典论文、4 核心机制 / 概念精学、5 前沿进展、6 实践与输出。调整这类计划时 stage 仍按六阶段填（任务里会写明计划用哪种结构）；用户想换成三轮时，平台会另生成一份三轮计划，旧计划保留。
