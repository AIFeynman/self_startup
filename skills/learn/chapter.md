# 章节教程：把计划里的一步写成「跟着学」的一章 + 章末测试

计划里每一步 = 一章。章节不是资料清单，而是**替用户把核心内容消化好、按逻辑讲清楚**，读完这一章就能完成这一步的能力目标；原始资料只作为出处和延伸阅读。
**总目标**：读者有技术背景，但对这个领域是新手；只读这些章节就要能学到精通，不靠另找资料补课。所以材料自成体系：用到的前置概念（本章之前没讲过的）当场用一两段讲清，或明确指向计划里讲它的那一步；不默认读者知道领域黑话。
**深度阶梯**：每个核心知识点都从入门走到专家、从理论走到实践——入门（直觉和一个生活化 / 小数字的例子）→ 原理（按学法讲到能自己复现）→ 专家（论文里的关键细节、取舍、实测数字、仍未解决的问题）→ 实践（在真实项目和产品里长什么样、读者自己动手做一个最小练习）。
风格参考平台里评价最好的单篇 HTML 教程：先给地图再讲细节、用一条主线例子串起来、事实与判断分开标注、原文默认折叠、每节都能自测。
本章写什么、考什么、结构上哪里要变，以任务末尾的「学法」为准；学法和下面的通用结构冲突时听学法。任务里会写本章属于第几轮。


## 写作要求（chapter.md）

结构（按顺序；标题用 `##`，平台自动生成目录）：
1. 开头一个引用块：`> **本章目标**：…（对应这一轮的目的，具体到本步）` + `> **学完能回答**：`2–4 个问题 + `> **预计用时**：…`
2. `## 资料时效`（学法要求必有的章节必写，其他章节资料较新时可一行带过）：主要资料的发表/更新日期；联网查它之后 12–18 个月的重要变化；结论写清「仍可作为主读物 / 部分过时，需要补 X / 已过时，改读 Y」。今天的日期在任务里给出。
3. **计划的第一步**按学法的「首章」写（任务里会注明）。
   `## 全景图`：先给这一章的地图——用下面「图示组件」画分类树 / 流程 / 卡片，或用 markdown 表格，一屏内看清全貌和各部分关系。
4. 3–6 个正文小节（按学法要求组织）。每节：
   - **每个核心知识点按四步讲**：① 价值与动机——它解决什么问题、不解决会怎样（给数字或具体场景）、为什么现在重要；② 具体原理——机制怎么工作，技术类讲到机制时按学法里的「公式与手推」写到能手推；③ 后续改进——之后谁在哪一点上改了它、改了什么、为什么；④ 相关工作对比——和解决同一问题的其他方案放进一张对比表（维度如：核心做法、代价、适用场景、代表模型与日期），并给出「什么情况下选哪个」的判断。不能只讲原理，也不能只列名字。
   - 先一句话结论，再展开因果和依据；具体到数字、例子，不要空泛的「很重要」。
   - 区分来源：事实用 `<span class="fact">源文事实</span>`，自己的分析和推断用 `<span class="judge">解读者判断</span>` 标在段首。
   - 原文摘录放进折叠块，并注明出处（节号 / 页码 / 链接）：
     `<details><summary>原文摘录 · 出处</summary>`（空行）`> 摘录`（空行）`</details>`
   - 节末一张「停一下」卡：正面一个需要用户**自己下判断**的问题（「如果…你会怎么做 / 这个结论成立吗 / 它属于哪一类、为什么」，而不是背定义）；背面是答案要点，写 3–4 条 `<ul><li>`，每条以粗体标签开头：`<b>结论</b>` 一句话判断；`<b>为什么</b>` 背后的因果（不是复述结论）；`<b>例子</b>` 一个具体例子或数字；可选 `<b>用到项目</b>` 一句落到实践的做法（用户在做 AI Agent / 学习平台类项目）。平台让用户在一个框里写下自己的判断（只提示可以从「结论 / 为什么 / 例子 / 用到我的项目」去想，不要求逐项写），再和要点并排对照，可请 Agent 点评差异：
     `<div class="dg-flash"><div class="dg-q">问题</div><div class="dg-a"><ul><li><b>结论</b>：…</li><li><b>为什么</b>：…</li><li><b>例子</b>：…</li></ul></div></div>`
5. `## 一条主线走一遍`：用一个贯穿的具体例子（一个任务、一个案例、一个决策）把本章内容串起来。
6. `## 我的判断框架`：把本章提炼成可复用的判断清单 / 决策规则（遇到新情况时按什么顺序问哪几个问题）。
7. `## 与已学内容的联系`：对照任务给出的本机资料库和前几章，具体指出关系，已深读的条目用 `[标题](#learn/item/<id>)` 链过去；没有就写「暂无」。
8. `## 延伸阅读`：精选 3–6 个资源（真实链接），每个一句话说明读它解决什么、读哪部分。

## 本地资料（任务里的「本机资料库」）

本机已经抓下来的论文、深读、开源项目、创业公司和调研，是比临时联网更全、更可靠的素材。写之前先按本章主题检索一遍，相关的用在需要的位置，不堆成清单：
- **已深读的条目**：讲到它时链过去 `[深读笔记](#learn/item/<id>)`，可以直接引用它的结论和数字；它产物目录里的 figs/ 有现成原图，拷进本章 figs/ 再引用。
- **论文库与脉络图**：用来挑本章的关键论文（被引、年份、谁接着谁），是时间线和对比表的依据；表里的论文给真实链接，已深读的标出来。
- **开源项目库**：讲到实现时找对应的仓库（优先已深读的），写到具体文件或模块，见学法里的「在代码里看」。
- **创业公司与产品库**：写「产业落地」——谁在用这个方法、做成了什么产品、用到哪一步、公开数字是什么；查不到可信的就不写。
- **调研文档**（知识库检索）：已有结论直接引用并注明是哪份调研。
引用本地资料同样标来源；本地资料和网上最新信息矛盾时以较新的为准，并点明差异。

## 图示与交互组件（HTML，平台负责样式和交互）

**不要画 ASCII / 字符画 / 用代码块画框图**（中文换行后会错位）。需要图时直接写下面几种 HTML，正文其余部分仍是 markdown。规则：
- HTML 从行首开始写，**内部不要有空行**，不要缩进 4 格以上；HTML 里不写 markdown（加粗用 `<b>`，代码用 `<code>`）。
- 每张图后面空一行再接 markdown。每个节点文字短（标题 ≤ 12 字，说明 ≤ 40 字），细节放正文。
- **按内容选呈现方式，读者看图就能抓住结构**：每个核心知识点至少配 1 个视觉元素，选最贴内容的一种——
  | 内容 | 用什么 |
  |---|---|
  | 领域地图、概念分解 | `dg-tree` |
  | 机制的执行过程、数据流 | `dg-flow steps`，或自己画的 SVG 机制图 |
  | 论文的结构图、结果曲线、消融表 | 论文原图（见下面「图片」），配读图说明 |
  | 两种做法 / 之前与之后 | `dg-vs` |
  | 多方案多维度对比 | markdown 表格 + 一句选型判断 |
  | 演进、后续改进、谁先谁后 | `dg-timeline` |
  | 参数一变结果就变的机制（门控、温度、学习率、采样、量化误差…） | 交互小组件 |
  全章不要只有表格；不要为了凑数画和正文重复的图。

1. **树 / 分类图**（领域地图、概念分解）：根 + 3–6 个分支，每个分支下 2–5 条。
```html
<div class="dg-tree">
<div class="dg-root"><b>根问题</b><span>Agent 多轮行动、改变环境、结果随机：怎样可信地知道它好不好？</span></div>
<div class="dg-branches">
<div class="dg-branch"><b>评测对象</b><ul><li>模型 + harness</li><li>workflow vs 自主 Agent</li></ul></div>
<div class="dg-branch hot"><b>核心机制</b><ul><li>多次 trial × 多种 grader</li><li>pass@k / pass^k</li></ul></div>
</div>
</div>
```
2. **流程 / 闭环**（步骤、数据流）：3–7 个节点自动加箭头；闭环加 `loop` 类（末尾显示「回到第一步」）。
```html
<div class="dg-flow loop">
<div class="dg-node"><b>真实失败</b><span>线上 / 人工发现</span></div>
<div class="dg-node"><b>写成任务</b><span>输入 + 成功标准</span></div>
<div class="dg-node"><b>多次试验</b><span>每题跑 k 次</span></div>
</div>
```
3. **卡片组**（并列的方向、人物、论文、方案）：每张卡标题 + 2–4 行要点，可加 `<i>` 写一行标签（日期 / 证据级别 / 立场）。
```html
<div class="dg-cards">
<div class="dg-card"><b>Hamel Husain</b><i>产品实践派</i><p>先读 trace 做错误分析，再写评测</p><p>二元 pass/fail 优于 1–5 分</p></div>
</div>
```
4. **对比**（两种做法 / 两派观点 / 之前 vs 之后）：
```html
<div class="dg-vs">
<div class="dg-side"><b>能力评测</b><p>通过率应该低，用来爬坡</p></div>
<div class="dg-side"><b>回归评测</b><p>通过率应接近 100%，防退化</p></div>
</div>
```
5. **时间线**（方法演进、后续改进、事件顺序）：每个事件写日期、名字、一句「它改了什么」；加 `hot` 标本章主角。
```html
<div class="dg-timeline">
<div class="dg-event"><i>2020-06</i><b>线性注意力</b><span>去掉 softmax，状态 S 累加 kvᵀ</span></div>
<div class="dg-event"><i>2021-02</i><b>DeltaNet</b><span>先读再写，按误差改写记忆</span></div>
<div class="dg-event hot"><i>2025-10</i><b>KDA</b><span>逐通道衰减 + delta 写入</span></div>
</div>
```
任何节点 / 分支 / 卡片 / 模块加 `hot` 类表示本章重点，加 `warn` 类表示坑 / 失效边界。

**交互**（平台自动接上，不要写 `<script>`）：
- **点开看细节**：树的分支、流程节点、卡片里加一个 `<div class="dg-more">…</div>`，默认收起，点击节点展开。用它放「为什么 / 例子 / 出处」，让图保持简洁、细节按需看。
- **逐步播放**：流程加 `steps` 类（`<div class="dg-flow steps">`），平台加「上一步 / 下一步」按钮，逐个高亮节点并在下方显示该节点的 `dg-more`。适合讲执行过程、一条主线例子。
- **标签页**：并列的几种视角 / 几个人物 / 几篇论文，内容较长时用标签页，避免一长串：
```html
<div class="dg-tabs">
<div class="dg-tab" data-title="Hamel"><p>…</p></div>
<div class="dg-tab" data-title="Shreya"><p>…</p></div>
</div>
```
- **翻转卡**：`dg-flash`（见上，「停一下」用它）。
- **交互小组件**（机制章每个核心机制配 1 个，一章最多 4 个；用在「动手调参数比读文字更能建立直觉」的地方，例如拖动 β 看状态改写、改温度看分布、改比特数看量化误差）：写一个自包含 HTML 到 `widgets/<名字>.html`（原生 JS + 内联 CSS，不加载外部资源，宽度自适应、高度 ≤ 420px，配色跟平台一致：背景 #fffdf9、文字 #2a2520、次要 #8b8178、线 #ebe3d8、强调 #c4552f，并写 `@media (prefers-color-scheme: dark)` 换成背景 #262420、文字 #ece6dd、强调 #e0774f；body 背景透明、无外边距，字体用 system-ui），正文里用
  `<div class="dg-widget" data-src="widgets/<名字>.html" data-height="360" data-title="一句话说明"></div>` 嵌入。小组件里写清楚「拖动 / 输入什么、观察什么」。

**图片**：
- **论文原图**：讲到某篇论文的结构、算法流程、关键实验结果时，把原图下载到 `figs/`（来源、做法见任务里的「关键图」规则：优先 arXiv HTML 版，没有就从 PDF 抽），先用 Read 打开看清楚，再在正文里用 `![图：标题（论文简称 Fig.3）](figs/xxx.png)` 嵌入，紧接一行 `> 怎么读这张图：…` 写清坐标 / 图例、关键数字和它支撑的结论。
- **自己画的示意图**：原文没有合适的图、或要把几篇论文的思路画在一起时，自己写 SVG 到 `figs/<名字>.svg`，用 `![图：标题（自绘）](figs/<名字>.svg)` 嵌入。要求：`viewBox` 定尺寸、宽度自适应；箭头上写动作（读出、写入、衰减）；文字 12–14px、标签几个字，解释写在图下；配色同上面小组件，并写 `@media (prefers-color-scheme: dark)`；里面不放公式源码（用 Unicode：Sₜ、β、kᵀ）；写完用 `rsvg-convert` 或浏览器渲染一遍确认没有重叠、出界。
- 图注里注明「原图」或「自绘」以及出处。

## 公式写法

平台用 KaTeX 渲染，规则来自 marked-katex 的标准模式，不遵守就会原样显示 `$`）：
- 行内 `$...$`，独立公式 `$$...$$` 单独成段（前后空行）。
- 开头的 `$` 前面必须是空格或行首；结尾的 `$` 后面必须是空格或 `?!.,:？！。，：` 之一。所以紧挨「、；）」「的」等字时先加空格：写 `为什么 $k$ 必须归一化， $\beta$ 必须……`，不要写 `、$\beta$`。
- `$` 里面开头和结尾不能是空格。
- HTML 组件（`dg-*` 卡片、`<details>` 摘要等）里也可以写 `$...$` / `$$...$$`，平台直接渲染，不受上面空格规则限制。
- 表格里不要出现 `|`，范数写 `\lVert k \rVert`，绝对值写 `\lvert x \rvert`。
- 金额写「5 美元」，不要写 `$5`。

篇幅 3000–6000 字中文；机制章（需要手推）可到 10000 字，按「预计用时」写实。深度体现在因果、证据和判断，不在堆砌。保留英文术语。不要编造链接、数字和引语；拿不准的标注「待核实」。

## 交付前自检（写完 chapter.md 和 quiz.json 后逐条做，没过就改）

- **本机资料真的查过**：任务里的本机接口至少按本章主题各查一次；curl 失败时先重试、换关键词，仍失败就在最后回复里写明哪个接口、什么错误，正文不写「本机资料库连不上」这类过程信息。
- **链接真实**：GitHub 仓库先用开源项目库的 `intel/oss/repo` 核对存在，具体文件链接写到读过的文件；论文链接用论文库返回的 `url`；深读条目只链任务列出的 id。
- **数字可复算**：手算例子、数量级都用 python 跑过；正文写「已核对」的必须真的跑过。
- **呈现不坏**：每张 `figs/` 图片文件存在、每个 `widgets/` 组件能独立打开；公式按上节规则写，`$` 只用于公式，价格写「美元」。
- **深度阶梯走完**：每个核心知识点都有动机 → 原理 → 后续改进 → 对比表，技术章还有「在代码里看」「产业落地」，章末有「动手」。
- 拿不准的标「待核实」并在最后回复里列出来，不在正文里猜。

## 章末测试与本章要点（quiz.json）

测试的目的不是考记忆，而是评估用户对这个方向的 **理解、判断力、应用能力** 三件事。题少而精：

- **4–5 题，其中需要手写的 `short` 最多 2 题**，其余用情景化的 `choice`（选择题也要考判断：给一个具体情景让用户选「最该做的事 / 最可信的结论 / 最大的问题」，干扰项是常见误解，不考定义背诵）。
- 每题标 `dim`，三个维度都要覆盖：
  - `理解`：能否把本章内容放到领域全局里。
  - `判断`：面对一个新情况，能否像一线的人一样给出有依据的判断。
  - `应用`：能否把本章用到用户自己的事情上。
- **学以致用（必做）**：任务里给出了「用户最近在读 / 在做」的内容（论文深读、调研、项目、事项）。至少 1 题（通常是 `应用` 那道 short）要直接拿其中**和本章相关**的一篇论文或一个项目来出题，例如「你最近读的 X 用的评测方法属于哪一类、缺了哪一环」「在你的 Y 项目里，按本章方法该怎么设计 Z」；`about` 字段写明关联的是哪篇 / 哪个项目。确实都不相关时才用通用情景，并在 `about` 写「无直接相关」。
- `short` 题要具体到能在 3–6 句里答完，给 `reference`（参考答案要点）和 `rubric`（2–4 条评分要点）。
- `choice`：4 个选项，`answer` 为正确下标（从 0 开始），`explain` 说明为什么对、其他为什么错。
- 每题写 `section`（对应正文小节标题，答错时引导回看）。

另给 6–10 条**本章要点**（`cards`）：直接总结，用户只读不答。`front` 是要点标题（一个概念 / 一句核心思想 / 一条判断规则，≤ 20 字），`back` 1–2 句说清楚（可用 `<b>` 强调）；`tag` 写类别（概念 / 思想 / 判断 / 人物 / 数据）。

```json
{"cards": [{"front": "评分以 outcome 为准", "back": "看环境最终状态，不信 Agent 自述；transcript 用来诊断和约束。", "tag": "判断"}],
 "questions": [
  {"id": "q1", "type": "choice", "dim": "判断", "q": "情景：……你最该先做哪件事？", "options": ["...", "...", "...", "..."], "answer": 2, "explain": "...", "section": "全景图"},
  {"id": "q4", "type": "short", "dim": "应用", "about": "你最近读的论文《…》", "q": "...", "reference": "...", "rubric": ["要点1：...", "要点2：..."], "section": "..."}
]}
```

## 按需加的一节（用户说「对 X 感兴趣」或「X 没懂」时）

任务里会写「这是用户按需加的一节（深入 / 补课）」、用户的原话（可能带划线原文）和来自哪一章。它不是计划里的一整章，而是**围绕用户这一个点**的一节短讲解，读完 15–30 分钟、马上能测。先读来源那一章的正文，不重复它已讲清的部分。

- **深入**（感兴趣的子方向）：把这个子方向当成一张小地图讲——它在原章节地图里的位置、要解决的核心问题、2–4 个代表性方案 / 作品 / 人物（真实、写日期）、目前的分歧与开放问题、最新进展（联网核对时效）、想继续往下学该读什么。
- **补课**（没懂的地方）：先一句话诊断「卡在哪」（结合任务里给的答错题、「停一下」作答和反馈：缺前置概念？混淆了两个东西？只记住结论不懂因果？），然后**换一个讲法**：从缺的前置概念讲起 → 一个日常类比 → 一个具体的小例子一步步走完（能用「逐步播放」流程图就用）→ 回到原章那句没懂的话，用新理解重新解释一遍 → 常见误解对照。不堆新概念。

写法沿用上面的规范，但：
- 篇幅 1500–3000 字；用户要「手推 / 公式」或这个点是机制、算法时按学法里的「公式与手推」写，篇幅可到 10000 字、预计 60–120 分钟，正文小节可到 8 个。结构：开头引用块（本节目标 / 学完能回答 / 预计用时）→ 2–4 个正文小节（每节末尾一张「停一下」）→ `## 回到原章` 一小节，说清和原章哪部分接上、现在再读原章该注意什么 → `## 延伸阅读`（深入必有，补课可省）。全景图、主线例子、判断框架等按需取舍，至少 1 张图。
- 资料时效：深入要核对；补课讲的是基础概念时可省。
- quiz.json：**2–3 题**（按学法「公式与手推」写的机制类可到 4 题，加 1 道对比判断题；最多 1 道 short），只考这一节要解决的那个点：补课题要换一个情景检验是否真懂（不能和原章的题同题换皮），深入题偏「判断 / 应用」。`cards` 3–6 条。
- quiz.json 顶层另加 `"title"`（这一节的标题，≤ 20 字，不要带「深入 / 补课」前缀，平台会加）和 `"goal"`（学完能做到什么，一句话、可检验）。
