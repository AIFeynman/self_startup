# 章节教程：把计划里的一步写成「跟着学」的一章 + 章末测试

计划里每一步 = 一章。章节不是资料清单，而是**替用户把核心内容消化好、按逻辑讲清楚**，读完这一章就能完成这一步的能力目标；原始资料只作为出处和延伸阅读。
风格参考平台里评价最好的单篇 HTML 教程：先给地图再讲细节、用一条主线例子串起来、事实与判断分开标注、原文默认折叠、每节都能自测。

## 每个阶段的目的（决定这一章写什么、考什么）

| 阶段 | 目的（学完要能做到） | 章节必须覆盖 | 测试重点 |
|---|---|---|---|
| 1 领域综述 | 对领域有**整体地图**：分类体系、每个方向的痛点 / 热点 / 开放问题 / 主流方案，能把任意一篇新论文或新产品定位到地图上 | 资料时效评估；分类树；方向 × {核心问题、痛点、主流方案、热点、开放问题} 矩阵；方向之间的关系与演进；底层约束 | 定位题（给一篇新论文/新产品，归到哪个方向、解决哪个痛点）、对比题、「为什么这个问题还没解决」 |
| 2 核心人物与观点 | **提升判断力**：知道一线人物怎么看问题、依据是什么、哪些判断后来被验证或被推翻，能对新事件做出同等深度的判断 | 每人：核心判断 → 依据与推理链 → 过往预测与后来的实际情况 → 与他人的分歧点；一张「分歧地图」；一个新近事件让各人「隔空点评」 | 判断题（给一个新事件/新论文，X 会怎么看？你怎么看？依据是什么）、识别论证漏洞、预测题 |
| 3 经典书籍/论文 | **快速吸收核心思想和背后逻辑**：10 分钟内能讲清一篇经典的问题、关键洞察和为什么有效 | 每篇：当时卡在哪 → 一句话关键洞察 → 方法核心（最少的公式/图）→ 证据 → 局限 → 它改变了什么、后续谁接着做；「读哪几节」的导读 | 一句话核心思想、「如果去掉 X 会怎样」、把思想迁移到新问题 |
| 4 核心机制/概念 | **吃透机制**：能推导、能自己实现最小版本、知道失效条件 | 直觉 → 形式化（推导一步步来）→ 最小实现（伪代码/短代码）→ 常见误解 → 失效边界 | 推导/计算题、找错题、改条件后的结果预测 |
| 5 前沿进展 | **快速消化新论文并判断价值**：知道相对经典增量在哪、证据是否可信、代表什么趋势 | 每篇（写日期、证据级别：预印本/会议/已部署）：相对已有工作的增量、关键证据、可疑之处、对趋势的意义；最后综合「现在的前沿在哪、下一步可能是什么」 | 增量识别、证据可信度判断、趋势判断 |
| 6 实践与输出 | **用产出检验理解** | 项目说明：目标、验收标准（rubric）、分步路线、常见坑、自检清单 | 用 rubric 自评题 + 设计取舍题 |

## 写作要求（chapter.md）

结构（按顺序；标题用 `##`，平台自动生成目录）：
1. 开头一个引用块：`> **本章目标**：…（对应上表这一阶段的目的，具体到本步）` + `> **学完能回答**：`2–4 个问题 + `> **预计用时**：…`
2. `## 资料时效`（阶段 1、3、5 必有，其他阶段资料较新时可一行带过）：主要资料的发表/更新日期；联网查它之后 12–18 个月的重要变化；结论写清「仍可作为主读物 / 部分过时，需要补 X / 已过时，改读 Y」。今天的日期在任务里给出。
3. `## 全景图`：先给这一章的地图——用下面「图示组件」画分类树 / 流程 / 卡片，或用 markdown 表格，一屏内看清全貌和各部分关系。
4. 3–6 个正文小节（按阶段要求组织）。每节：
   - 先一句话结论，再展开因果和依据；具体到机制、数字、例子，不要空泛的「很重要」。
   - 区分来源：事实用 `<span class="fact">源文事实</span>`，自己的分析和推断用 `<span class="judge">解读者判断</span>` 标在段首。
   - 原文摘录放进折叠块，并注明出处（论文节号/页码/链接）：
     `<details><summary>原文摘录 · 出处</summary>`（空行）`> 摘录`（空行）`</details>`
   - 节末一张「停一下」卡：正面一个需要用户**自己下判断**的问题（「如果…你会怎么做 / 这个结论成立吗 / 它属于哪一类、为什么」，而不是背定义）；背面是答案要点，用 `<ul><li>` 列 2–4 条，每条一个可对照的点（判断题写结论 + 依据）。平台让用户先写下自己的判断，再和要点并排对照，可请 Agent 点评差异：
     `<div class="dg-flash"><div class="dg-q">问题</div><div class="dg-a"><ul><li>要点 1</li><li>要点 2</li></ul></div></div>`
5. `## 一条主线走一遍`：用一个贯穿的具体例子（一个任务、一篇论文、一个产品决策）把本章内容串起来。
6. `## 我的判断框架`：把本章提炼成可复用的判断清单 / 决策规则（遇到新论文/新方案时按什么顺序问哪几个问题）。
7. `## 与已学内容的联系`：对照任务给出的「已学内容」和前几章，具体指出关系；没有就写「暂无」。
8. `## 延伸阅读`：精选 3–6 个资源（真实链接），每个一句话说明读它解决什么、读哪部分。

## 图示与交互组件（HTML，平台负责样式和交互）

**不要画 ASCII / 字符画 / 用代码块画框图**（中文换行后会错位）。需要图时直接写下面几种 HTML，正文其余部分仍是 markdown。规则：
- HTML 从行首开始写，**内部不要有空行**，不要缩进 4 格以上；HTML 里不写 markdown（加粗用 `<b>`，代码用 `<code>`）。
- 每张图后面空一行再接 markdown。每个节点文字短（标题 ≤ 12 字，说明 ≤ 40 字），细节放正文。
- 一章 2–4 张图就够：全景图必有，机制/流程/对比各用最合适的一种。矩阵、多维对比仍用 markdown 表格。

1. **树 / 分类图**（领域地图、概念分解）：根 + 3–6 个分支，每个分支下 2–5 条。
```html
<div class="dg-tree">
<div class="dg-root"><b>根问题</b><span>Agent 多轮行动、改变环境、结果随机：怎样可信地知道它好不好？</span></div>
<div class="dg-branches">
<div class="dg-branch"><b>评测对象</b><ul><li>模型 + harness</li><li>workflow vs 自主 Agent</li></ul></div>
<div class="dg-branch hot"><b>核心机制</b><ul><li>多次 trial × 多种 grader</li><li>pass@k / pass^k</li></ul></div>
</div>
</div>
```
2. **流程 / 闭环**（机制步骤、数据流）：3–7 个节点自动加箭头；闭环加 `loop` 类（末尾显示「回到第一步」）。
```html
<div class="dg-flow loop">
<div class="dg-node"><b>真实失败</b><span>线上 / 人工发现</span></div>
<div class="dg-node"><b>写成任务</b><span>输入 + 成功标准</span></div>
<div class="dg-node"><b>多次试验</b><span>每题跑 k 次</span></div>
</div>
```
3. **卡片组**（并列的方向、人物、论文、方案）：每张卡标题 + 2–4 行要点，可加 `<i>` 写一行标签（日期 / 证据级别 / 立场）。
```html
<div class="dg-cards">
<div class="dg-card"><b>Hamel Husain</b><i>产品实践派</i><p>先读 trace 做错误分析，再写评测</p><p>二元 pass/fail 优于 1–5 分</p></div>
</div>
```
4. **对比**（两种做法 / 两派观点 / 之前 vs 之后）：
```html
<div class="dg-vs">
<div class="dg-side"><b>能力评测</b><p>通过率应该低，用来爬坡</p></div>
<div class="dg-side"><b>回归评测</b><p>通过率应接近 100%，防退化</p></div>
</div>
```
任何节点 / 分支 / 卡片加 `hot` 类表示本章重点，加 `warn` 类表示坑 / 失效边界。

**交互**（平台自动接上，不要写 `<script>`）：
- **点开看细节**：树的分支、流程节点、卡片里加一个 `<div class="dg-more">…</div>`，默认收起，点击节点展开。用它放「为什么 / 例子 / 出处」，让图保持简洁、细节按需看。
- **逐步播放**：流程加 `steps` 类（`<div class="dg-flow steps">`），平台加「上一步 / 下一步」按钮，逐个高亮节点并在下方显示该节点的 `dg-more`。适合讲机制的执行过程、一条主线例子。
- **标签页**：并列的几种视角 / 几个人物 / 几篇论文，内容较长时用标签页，避免一长串：
```html
<div class="dg-tabs">
<div class="dg-tab" data-title="Hamel"><p>…</p></div>
<div class="dg-tab" data-title="Shreya"><p>…</p></div>
</div>
```
- **翻转卡**：`dg-flash`（见上，「停一下」用它）。
- **交互小组件**（可选，一章最多 2 个，只在「动手调参数比读文字更能建立直觉」时用，例如 pass@k / pass^k 随 k 变化、采样温度对分布的影响、评分器一致性模拟）：写一个自包含 HTML 到 `widgets/<名字>.html`（原生 JS + 内联 CSS，不加载外部资源，宽度自适应、高度 ≤ 420px，配色跟平台一致：背景 #fffdf9、文字 #2a2520、次要 #8b8178、线 #ebe3d8、强调 #c4552f，并写 `@media (prefers-color-scheme: dark)` 换成背景 #262420、文字 #ece6dd、强调 #e0774f；body 背景透明、无外边距，字体用 system-ui），正文里用
  `<div class="dg-widget" data-src="widgets/<名字>.html" data-height="360" data-title="一句话说明"></div>` 嵌入。小组件里写清楚「拖动 / 输入什么、观察什么」。

篇幅 3000–6000 字中文；深度体现在因果、证据和判断，不在堆砌。保留英文术语。不要编造链接、数字和引语；拿不准的标注「待核实」。

## 章末测试与本章要点（quiz.json）

测试的目的不是考记忆，而是评估用户对这个方向的 **理解、判断力、应用能力** 三件事。题少而精：

- **4–5 题，其中需要手写的 `short` 最多 2 题**，其余用情景化的 `choice`（选择题也要考判断：给一个具体情景让用户选「最该做的事 / 最可信的结论 / 最大的问题」，干扰项是常见误解，不考定义背诵）。
- 每题标 `dim`，三个维度都要覆盖：
  - `理解`：能否把本章内容放到领域全局里（属于哪个方向、解决什么痛点、为什么之前不行）。
  - `判断`：面对一个新事件 / 新论文 / 新方案，能否像一线的人一样给出有依据的判断（可信吗、值得跟吗、哪里有问题）。阶段 2 至少 1 题给真实的新事件，参考答案写出代表人物会怎么看。
  - `应用`：能否把本章用到用户自己的事情上。
- **学以致用（必做）**：任务里给出了「用户最近在读 / 在做」的内容（论文深读、调研、项目、事项）。至少 1 题（通常是 `应用` 那道 short）要直接拿其中**和本章相关**的一篇论文或一个项目来出题，例如「你最近读的 X 用的评测方法属于哪一类、缺了哪一环」「在你的 Y 项目里，按本章方法该怎么设计 Z」；`about` 字段写明关联的是哪篇 / 哪个项目。确实都不相关时才用通用情景，并在 `about` 写「无直接相关」。
- `short` 题要具体到能在 3–6 句里答完，给 `reference`（参考答案要点）和 `rubric`（2–4 条评分要点）。
- `choice`：4 个选项，`answer` 为正确下标（从 0 开始），`explain` 说明为什么对、其他为什么错。
- 每题写 `section`（对应正文小节标题，答错时引导回看）。

另给 6–10 条**本章要点**（`cards`）：直接总结，用户只读不答。`front` 是要点标题（一个概念 / 一句核心思想 / 一条判断规则，≤ 20 字），`back` 1–2 句说清楚（可用 `<b>` 强调）；`tag` 写类别（概念 / 思想 / 判断 / 人物 / 数据）。

```json
{"cards": [{"front": "评分以 outcome 为准", "back": "看环境最终状态，不信 Agent 自述；transcript 用来诊断和约束。", "tag": "判断"}],
 "questions": [
  {"id": "q1", "type": "choice", "dim": "判断", "q": "情景：……你最该先做哪件事？", "options": ["...", "...", "...", "..."], "answer": 2, "explain": "...", "section": "全景图"},
  {"id": "q4", "type": "short", "dim": "应用", "about": "你最近读的论文《…》", "q": "...", "reference": "...", "rubric": ["要点1：...", "要点2：..."], "section": "..."}
]}
```

## 按需加的一节（用户说「对 X 感兴趣」或「X 没懂」时）

任务里会写「这是用户按需加的一节（深入 / 补课）」、用户的原话（可能带划线原文）和来自哪一章。它不是计划里的一整章，而是**围绕用户这一个点**的一节短讲解，读完 15–30 分钟、马上能测。先读来源那一章的正文，不重复它已讲清的部分。

- **深入**（感兴趣的子方向）：把这个子方向当成一张小地图讲——它在原章节地图里的位置、要解决的核心问题、2–4 个代表性方案 / 论文 / 人物（真实、写日期）、目前的分歧与开放问题、最新进展（联网核对时效）、想继续往下学该读什么。
- **补课**（没懂的地方）：先一句话诊断「卡在哪」（结合任务里给的答错题、「停一下」作答和反馈：缺前置概念？混淆了两个东西？只记住结论不懂因果？），然后**换一个讲法**：从缺的前置概念讲起 → 一个日常类比 → 一个具体的小例子一步步走完（能用「逐步播放」流程图就用）→ 回到原章那句没懂的话，用新理解重新解释一遍 → 常见误解对照。不堆新概念。

写法沿用上面的规范，但：
- 篇幅 1500–3000 字；结构：开头引用块（本节目标 / 学完能回答 / 预计用时）→ 2–4 个正文小节（每节末尾一张「停一下」）→ `## 回到原章` 一小节，说清和原章哪部分接上、现在再读原章该注意什么 → `## 延伸阅读`（深入必有，补课可省）。全景图、主线例子、判断框架等按需取舍，至少 1 张图。
- 资料时效：深入要核对；补课讲的是基础概念时可省。
- quiz.json：**2–3 题**（最多 1 道 short），只考这一节要解决的那个点：补课题要换一个情景检验是否真懂（不能和原章的题同题换皮），深入题偏「判断 / 应用」。`cards` 3–6 条。
- quiz.json 顶层另加 `"title"`（这一节的标题，≤ 20 字，不要带「深入 / 补课」前缀，平台会加）和 `"goal"`（学完能做到什么，一句话、可检验）。
