semk 自迭代：评测和运行机制怎么改

2026-11-19 · 接 两天复盘 · 依据 scripts/explainer_eval/semk_run.py（ARCHITECT / CRITIC / MINE 提示词、TARGETS、ledger_settle）、docs/design/semk/lessons.json、human-picks.json · 只给方案，没改代码
结论：过拟合不是哪一步做错，而是闭环里没有一个会说“不”的环节是靠程序强制的。目标函数（像 Opus）、训练/验收样本（同一批片）、确认条件（训练片上涨分）、合入路径（Agent 直接改内核）都允许“记住这几部片”通过。改法分两层：评测——换目标、分样本、校准尺子、按噪声判；运行——把闸门从提示词搬进脚本，一轮只变一类东西，预先登记停止规则。复盘里的方向基本对，但有 4 处要补，第一步可以直接照复盘的“新旧内核 DeepSeek 盲比”做，只是题量要放大。

一、复盘之外，代码里直接造成过拟合的 6 处

复盘讲了现象和根源，下面是落到代码上的“开关”，改法要从这里下手：

#位置现在写的为什么必然过拟合
1ARCHITECT 规则 4predict “只写训练片”提案的预期收益只在训练片上登记，验收也只看这些拍——确认条件本身就是“训练集上涨分”。
2ledger_settleuses 在转写稿里找，转写没用上记 doubt（“不能算试过”）转写者看得到 Opus 原片，必然会用新能力；DeepSeek 用不上的情况从来不会进入判定。产品路径上“没被用上”应当直接是否决信号。
3lessons.json 状态30 条：trial 22、rejected 3、doubt 2、deferred 2、vetoed 1、confirmed 0trial 就已经合进内核，确认这一步实际不存在。内核里 22 项能力没有一项走完验证。
4ARCHITECT 规则 0 vs CRITIC 第 1 条“两种以上题材就收”“每轮至少一项组件级” vs “≥3 部、≥2 题材才算通用”架构师和反方门槛不一致，且缺口库 58 部是同一套 codex-对比-Opus 挖出来的，≥3 部很容易凑够；配额保证每轮必加东西。
5TARGETS 生成组gen.first_pass_rate ≥ .85 写成底线每轮 cround.sh 不跑 write，这条底线永远不被检查；词表说明从 6.1k 涨到 25.5k 字没有任何指标拦。
6人评闸门 vs blind_sides台账对比页已有随机 A/B；轮次评审页却默认“这一轮更好”、不盲机制里已经有盲测的写法，最关键的那道人评没用上，偏向新版是结构性的。

复盘建议里要修正的 4 点

  • 留出题太少。复盘第一步写“5 老题 + 5 新题”。同片重打噪声 0.17–0.3/拍，加上 DeepSeek 写稿方差，10 题单次很难分出差别。建议每题写 2 次、至少 12 题（24 对），按“胜率 + 置信区间”判，不按均值。
  • 范例检索（方案 D）有泄漏。拿转写稿当 DeepSeek 范例时，评测题必须排除同题、同参考片的转写稿，否则 D 只是在抄答案，和现在的过拟合是同一回事。
  • “该用没用”需要标注，不然没法判。复盘说没机制区分“该用而没用”和“本来不该用”。最便宜的做法：每个验证题由人或强模型一次性标“这题适合的 2–4 个组件”（冻结，不随轮次改），新组件的使用率只在标了它的题上算。
  • 评审校准集现在不够。human-picks.json 只有 3 轮的记录，算一致率样本太少。第一批人评盲比要同时作为评审的校准集，至少 20 对。

二、评测机制改法

E1 主目标换成产品路径的盲比胜率
现在每拍高严重度差距数（codex 对比 Opus）。
改成主指标 = 验证题上“DeepSeek 只看题目 → 剧本 → 成片”，候选版对当前冠军版的盲比胜率（左右随机，可选“都不行”）；附带三条硬门：一次通过率 ≥85%、底线违规不增加、词表说明字符不超预算。codex 对比 Opus 降为诊断，只用来找“哪里可能缺”，不进合入判定。
验收线胜率 ≥60% 且 95% 区间下界 >50%（24 对时约需 17 胜）。
E2 三分题库，按角色锁死
集来源谁能看用途
挖缺集~15 部有 Opus 参考的片Agent 可看 scene.js / notes找缺口、提手法卡、转写上限诊断
验证集~12 题（可有 Opus 参考，但闭环不可读参考代码）只看题目和成片每个改动收不收
留出集~10 个新题，无 Opus 参考阶段末才跑一次判断这一阶段是否真的变好
清单写进一个文件（如 evalbench/semk_splits.json），脚本读取时按集校验路径：验证集和留出集的 opus_reference/<片>/a/ 不给 transcribe / mine / propose 读。复盘列出的 pop120、substr30、fraud56、geom17、sushi51、zhenghe、kahneman、pdca 都已被“挖过”，只能放挖缺集。
E3 先测噪声，再谈改进
每阶段开头跑一次 A/A：同一内核、DeepSeek 对验证题各写两次并出片，让评审互比。A/A 的“胜率”偏离 50% 的幅度就是这把尺子的噪声。之后任何改动的胜率要超出 A/A 区间才算数；报告里每个数字带区间。底线类指标同样先测 A/A 波动（同剧本重渲、同题重写）。
E4 评审先校准，校准过才拿来决策
第一批人评盲比（≥20 对）同时作为校准集；codex 用同一份绝对量表（讲清楚 / 跟得上口播 / 无硬错 / 观感，1–5）+ 两两偏好打分，和人选比一致率。≥75% 才允许评审替人做轮内决策，否则轮内只用底线 + 人评。动效、音效只用短视频片段（或人），不用 4 张静帧判。参考片只作为“可以这样做”的提示，不作答案——提示词里明确“和参考不同但讲得清不算缺陷”。
E5 冻结尺子：评审、底线、量表一阶段不改
建 rulers.lock：评审模型（现在 CODEX_MODEL = gpt-6.2-sol）、评审提示词、TARGETS、各条 floor 口径、量表的哈希。每次评测产物写入当时的 lock 哈希；比较两轮时哈希不同直接报错。要改尺子只能单开一轮“只换尺子”，把冠军版和基线版用新尺子重打，再写变更记录。refloor 重算历史这种做法保留，但必须和内核改动分开。
E6 新能力的准入看“DeepSeek 用得上 + 用上就变好”
每题一次性标“适合的组件”（冻结）。新组件 / 新字段合入条件：在标了它的验证题上，DeepSeek 自发使用率 ≥50%，且这些题的盲比胜率过 E1 的线。用不上就三选一：改 describe（写清适用信号 + 短例子）、并进已有组件做选项、或交给内核自动做；都不行就不收。把 ledger_settle 的 uses 改成在 DeepSeek 剧本里找，“没被用上”记 rejected 而不是 doubt。
E7 复杂度预算是硬门
describe 组件段设上限（建议先回到 ≤15k 字，当前 25.5k）、组件数上限（如 32，即自迭代起点水平）。超了必须先合并或删除才能加。gen.first_pass_rate、gen.in_tokens 每轮真的跑 write 去算，而不是只写在 TARGETS 里。

三、运行机制改法

R1 闸门从提示词搬进脚本：内核只能经 promote 合入
复盘第 4 条：B2 以后架构师 / 反方被跳过，改动由执行 Agent 看图后直接写进内核。提示词约束对执行者无效。改法：迭代 worktree 装 pre-commit hook，凡改 skills/video-styles/engine/lib/semk/ 的提交，必须附 .promote/<id>.json，里面有 E1 验证集胜率、A/A 区间、底线前后、DeepSeek 使用率、rulers.lock 哈希，脚本校验通过才放行。Agent 可以在实验分支随便改，但进冠军线只有这一条路。
R2 一轮只变一类东西，manifest 声明
每轮开跑先写 round.json：change_type ∈ kernel / describe / writer-prompt / ruler 之一，加冻结的内核 commit、剧本库版本、rulers 哈希。脚本检查：kernel 轮用冻结剧本库重渲（复盘的“内圈”，c4k 式）；describe / prompt 轮用冻结内核让 DeepSeek 重写；混了就拒绝出报告。这也顺带解决“跑一半内核被改、整轮作废”——渲染只认 manifest 里的 commit。
R3 先登记假设，再动手
每个改动在动代码前写进台账：要解决的讲解问题、预计哪些验证题变好（不是训练片的拍）、DeepSeek 会怎么用到、否决条件。结果出来后对照登记判，不允许事后换解释（复盘里 B3 变差被解释成“逐部均值持平”就是这种情况）。把 ARCHITECT 规则 4 的“predict 只写训练片”改成“只写验证题”。
R4 删掉配额，原则设上限
删 ARCHITECT 的“每轮至少一项骨架或组件级能力”“新组件两种题材就收”、两份提示词里的“压榨 Opus 直到提炼完”。允许一轮只删、只合并。ARCHITECT / CRITIC / MINE 的总原则抽成一个共享文件，≤5 条，三处引用同一份（现在是复制粘贴的两份 8 条）。人评意见进 human-notes.json 时标 scope: 个例，在 ≥2 部、≥2 题材的验证片上复现后才升级为原则；加一条原则要删或合并一条。
R5 人评闸门：盲、无默认、带固定基线、只点不写
左右随机、不标轮次、没有默认选项；四档：左更好 / 右更好 / 差不多 / 都不够好；每批至少 1 部对比固定基线（自迭代起点 04f0385e9），不只比相邻两版；每批 ≥6 部，从验证集抽。理由用勾选标签（讲不清、跟不上口播、太乱、太静、动效多余…），不要求打字。直接复用 blind_sides 的随机写法。
R6 预先登记停止规则和预算
阶段开头写死：主指标、A/A 噪声、验证集和留出集清单、最多 4 轮、预算上限。连续 2 轮没有改动通过 E1，或预算到，就停下跑留出集 + 人评，交给人决定下一阶段方向。过程中不改判据、不加预算。
R7 执行 Agent 的汇报格式固定
每轮汇报第一段固定四个数：验证集胜率（带区间）、一次通过率、词表说明字符数、底线违规数；然后才是诊断指标（对比 Opus 的差距）。不再用“每拍高差距下降”当头条。并发只在不同冻结 worktree 之间，同一 worktree 不并发写；禁止 git stash 等全局操作（复盘里出现过一次意外 stash）。

四、改完后的闭环

挖缺集：Opus 参考 → 手法卡（≥3 部 ≥2 题材）→ 登记假设（预计哪些验证题变好）→ 实验分支改（一轮一类）→ 内圈：冻结剧本库重渲 + 底线→ 外圈：DeepSeek 写验证题 → 成片→ 盲比（校准评审 / 人）vs 冠军，过 A/A 区间→ promote 校验 → 合入冠军线→ 阶段末：留出集 + 人评 → 人定下一阶段

和现在的差别：Opus 只出现在第一格；合入判定全在产品路径上；“像不像 Opus”只回到第一格当诊断。

五、落地顺序

  1. 测现状（不改代码，约半天）：定题库三分 → 验证集 12 题、每题 2 次，用起点内核 04f0385e9 和当前 HEAD 让 DeepSeek 出片，同时跑 A/A。得出“两天对产品有没有帮助”和噪声区间。写稿约 $0.15，主要是渲染时间。
  2. 人评盲比 + 校准：上面 ≥20 对给人盲选（只点），同时让 codex 打，算一致率，决定评审能不能替人。
  3. 改脚本：splits 文件和读路径校验、rulers.lock、round.json、ledger_settle 改用 DeepSeek 剧本、write 进每轮、promote hook、人评页去默认。提示词删配额、合并原则。
  4. 清台账：22 条 trial 逐条按 E6 在验证集上过一遍（内圈消融：关掉该能力重渲冻结剧本），用不上的合并或回退，词表回到预算内。
  5. 之后才按复盘的 A/B/C/D 归因决定下一阶段先改框架、改说明还是加规划步。

六、要你定的

  • 验证 / 留出的新题：留出集需要约 10 个没有 Opus 参考的新题。可以由我从 evalbench 现有题目外按题材分布挑，你只确认清单；或你指定。
  • 人评量：第 2 步需要你盲选约 20–24 对（每对一部片的左右两版，只点不写），这是评审校准的基础，省不掉。
  • 清台账的力度：第 4 步可能回退一批已在内核里的能力（预计 meter、spans 留，scatter、array、matrix 等若验证集用不上会合并或回退）。
