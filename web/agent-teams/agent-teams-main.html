为什么要先画层？判断 多 Agent 的讨论常常把「角色怎么命名」和「状态放哪、谁能写」混在一起。后面 7 种架构的差别，几乎都落在第 3 层（状态和写权限）上，而不是第 2 层（叫 manager 还是叫 lead）。

1　为什么要做 Teams：先看账，再看失败

起点：一个 Agent 够不够用

不做 Teams 的默认路线是：一个 Agent，一个上下文，一条循环。它有三个天花板：上下文装不下（任务太长）、墙钟时间太长（串行）、没人挑它的毛病（自己写自己审）。Teams 是对这三条的回应，但它不是免费的。

成本倍数：三个数，三个分母

课程里最容易被混用的就是「多 X 倍」。下表把分母写死：

倍数比什么出处标记

约 7×Agent Teams（teammate 处于 plan 模式）对比一个标准会话Claude Code 成本文档二手（Claude Code 闭源，只引文档）

判断 这四篇合起来的结论不是「别用 Teams」，而是三句话：（1）任务能不能拆开决定了成败；（2）要和「同样 token 预算的单 Agent」比，不能和「一次便宜的调用」比；（3）常见失败来自接口（沟通、承诺、验证），不是模型智商。这正是后面几节只谈接口的原因。

辩论：Cognition 前后两篇

一手 Cognition（Devin）2025-06-12 写了《Don't Build Multi-Agents》，2026-04-22 又写了《Multi-Agents: What's Actually Working》（Walden Yan，我读了后者的大部分）。后者的立场是：原来的观察对「多个 Agent 并行写」依然成立；但有一类能用——多个 Agent 提供智力，写操作仍保持单线程。它给的例子：代码审查循环，Devin Review 平均每个 PR 抓到约 2 个 bug，其中约 58% 是严重的，coder 和 reviewer 不共享上下文时效果最好；Devin 在最大企业客户群里的用量 6 个月涨约 8 倍。它还指出浏览器、C 编译器、训练脚本这些大 demo 有一个共同点：成功标准简单、可验证。（Smart Friend 和 manager-child 模式部分，我读到一半被截断，不引。）

判断 把它和 Anthropic、Cursor 放一起，可以调和成一条：并行的「读」和「想」没问题，并行的「写」要有单写者或隔离；任务可验证时 Teams 更值。

1.x　一个反面的对照：不靠多 Agent，靠单个 Agent 跑过一夜

来源：Claude 官方博客，Working at the frontier: How Cognition trusts Claude Fable 5 to work through the night（2026-07-10），读了全文。一手；都是 Cognition 自述，没有外部复现，也没有给任务本身的细节。

本节前面的账都在说：多 Agent 要花几倍到二十几倍的钱，换来的是时间和覆盖。Cognition 的案例提醒另一端：当单个模型能自己稳定跑很久，要不要拆成多个 Agent，答案会变。

事实原文怎么说
评测Cognition 自建的 Frontier Code，专门奖励「能活过真实代码库」的代码。在最难的子集上，上一代 Opus 约 10%，Claude Fable 5 约 30%

为什么撑得住在杂乱上下文里保持清醒：第一个会正确使用 Cognition 内部调试工具的模型；做迁移时先说出自己要守的不变量再执行；定位根因时会说出自己不知道什么

坑：把一个厂商客户故事当成「多 Agent 没必要」的证据。这是一篇 Anthropic 发布的客户案例：10% 到 30% 是 Cognition 自己的内部评测，8 小时只是一次轶事，没有给出任务类型、是否有人中途介入、成本。判断 它能支持的只有一句话：单 Agent 的有效时长在变长，所以第 1 节开头那个「为什么要做 Teams」的账，每过一代模型都要重算。它不能支持「Teams 没用」。同一篇里还有一条反过来有用的做法：验收靠人用一整天，而不是靠分数，这对评估任何多 Agent 方案都适用。

3　模块间接口：别看角色名，看接口怎么写

起点：不写接口，系统会长成一团

多 Agent 常见的毛病是：Agent A 的输出就是 Agent B 的输入，中间没有一层「合同」。出了错，谁都说不清是谁的责任。看 DeepSeek 原型怎么避免它。

DeepSeek 原型：四个端口

一手 仓库 deepseek-ai/dsh-superagent-prototype，src/core/ports.ts，main 分支，2026-11-16 读取。下面只摘文档注释和接口签名，省略了部分字段：

/** Versioned rules; `gate` decides who may originate work.
    Source scope is not part of Policy. */
export interface Policy { version: string; paused: boolean;
  gate(trigger, thread, tickets): GateResult;
  revalidate(mandate): boolean; admitsInferred(rules): boolean;
  evalTimeoutMs: number }

/** What the assessor receives: bounded facts, never authority. */
export interface Candidate { evalId; thread; triggers; strength; policyVersion; tickets }

export type AssessmentOutcome =
  | {kind:'ignore'} | {kind:'unavailable'}
  | {kind:'accept'; title; scope; reason; ...}
  | {kind:'stop'; ticketId; reason}

/** Semantic judgement. `request` queues the assessment, idempotently per `evalId`;
    the outcome returns through `Engine.decide`. */
export interface Assessor { request(candidate: Candidate): void; release?(evalId: string): void }

/** Executes assignments; concurrency and workspace management are its own concern.
    The Engine calls it inside its commands, so each method only queues work,
    which reports back through the Engine's callbacks. */
export interface Executor { start(ticket, assignment): void;
  deliver(ticket, assignment): void; stop(ticket, assignment, reason): void }

export interface Outbox { send(message: OutboundMessage): void;
  status(id): ReplyStatus|undefined; withdraw(id): void }

逐条读，会发现几个设计选择，都是为了解决具体事故：

设计点是什么防什么
「bounded facts, never authority」把「事实」交给语义判断的 Agent，权力不给它模型被一条恶意 Issue 说服，自己给自己加权限
request 幂等（按 evalId）同一次评估重复请求只排队一次重启或重试后重复派活
结果走 Engine.decide 回来Assessor 不能直接改状态，只能提交「决定」多个写者互相覆盖
Executor 的方法「只排队」每个方法只入队，完成后通过回调汇报在事务里做慢事、做副作用
Outbox 有 status / withdraw对外消息有状态，可撤回消息已决定发但没发出，或发了又想撤

一手（docs/007-architecture.md）配套规则：Engine（src/core/engine.ts）是 Triggers / Threads / Decisions / Tickets / Assignments 的唯一写者；所有 Engine 方法同步；一个命令一个事务；对外的工作在事务里只入队，提交之后才由适配器去做。持久化是单个 SQLite 文件 orchestrator.sqlite（表有 trigger / disposition / trigger_thread / thread / ticket / decision / effect / outbox / kv）。

为什么「提交之后再做」是关键？判断 如果先发邮件、再写库，库写失败时人已经收到了邮件；如果先写库、再发邮件，崩了也能靠 outbox 重发。这和后端常见的 outbox 模式是同一件事，DeepSeek 把它用在了 Agent 上。

坑（原型自己写明的）：这是研究原型，不是 DeepSeek 官方产品；文章《Exploring Super-agent Design》里有些设计没有实现；还没有任何东西删除旧记录，会一直长；Trigger 字段的可信度、部署隔离是列出来的开放问题。一手（README）

4　并发写同一份东西：数据与教训

起点：让 N 个 Agent 直接改同一个目录

会在两个层面出事：文本冲突（合并不了），语义冲突（合并了但是互相矛盾）。

Cursor 的三代做法（一手，Wilson Lin，2026-01-14，读了全文）

精读 P1　MAST：多 Agent 到底怎么失败（2503.13657 v3，经典例外）

一句话：多 Agent 系统失败时，失败长什么样？能不能分类？一手（全文，NeurIPS 2025 Datasets and Benchmarks）

方法：先人工标 150 条轨迹，归纳出分类 MAST；再用 LLM 当标注员（o1 加 few-shot）标 1,642 条轨迹。

怎么测的：7 个框架（ChatDev、MetaGPT、HyperAgent、AppWorld、AG2、Magentic-One、OpenManus）。人工标注部分每个框架 30 条（Table 1）；其余靠 LLM 标注，模型有 GPT-4o、Claude 3.7 Sonnet、Qwen2.5-Coder-32B、CodeLlama-7B。LLM 标注员对人：准确率 0.94，Cohen κ 0.77，F1 0.80（Table 2，few-shot）；不带示例时 κ 只有 0.58。

我核对出的问题：

  • 摘要和引言里的「+9.4%」是 ChatDev 从 25.0 到 34.4，是 9.4 个百分点，基数是 32 道题，约多对 3 题。别当成稳定提升。

  • 失败的标注来自 o1，不是人。人标只有 7×30=210 条，其余 1,400+ 条的分布是模型估的，κ=0.77 说明有可观的误标。

讨论：它支持第 1 节「失败比成功多」，但给出的是失败原因，不是失败率的现状。三个追问：

  1. 占比最大的是「系统设计问题」，其中「重复步骤」「忘了终止条件」，换成有硬停（预算、轮数上限）的 harness 后还剩多少？
  2. 「验证」只占 23.5%，但上文第 5 节说验证是 manager 的价值所在。验证失败占比低，是因为根本没有验证步骤所以没法失败吗？
  3. 作者自己的结论是「改 prompt 和拓扑只能小幅改善」。这和 CAID 一类靠隔离与合并拿到的提升放一起，能说明失败多发生在协调机制，而不是角色措辞上吗？

坑：引 MAST 的占比时要说「1,642 条、o1 标注」。我在二手文章里见过把 44.2% 说成「多 Agent 有 44% 的任务失败」，那是失败里的占比，不是任务失败率。

一句话：同一个项目、同一个模型，换协作拓扑，质量、时间、成本差多少？一手（全文，约 104KB 文本；附录细表只扫了结构）

精读 R1　Paperclip：原子 checkout 到底锁了什么

入口：server/src/services/issues.ts（master，2026-11-16 读，共 14,967 行）的 checkout（第 12765 行起）。一手上文原来只读了本地深读笔记，这里补读源码。

调用链：Agent 的 heartbeat run 启动，调用 checkout(issueId, agentId, expectedStatuses, checkoutRunId) → 先 assertAssignableAgent → 查子树暂停（pause hold）→ clearExecutionRunIfTerminal / clearCheckoutRunIfTerminal 清掉已死 run 留下的锁 → 查依赖阻塞 → 一条带条件的 UPDATE ... WHERE 抢占；抢不到再走「收养」分支。

片段取自 server/src/services/issues.ts，master，2026-11-16；中间省略了 6 个 notify* 调用。

怎么读：「原子」靠的是一条 UPDATE 的 WHERE 条件，不是显式的行锁：状态要在期望集合里，指派人要空或就是自己，executionRunId 要空或就是本 run。数据库保证两个 run 同时执行，只有一个返回行。

抢不到之后（updated 为空）不是直接报冲突，而是分三种「收养」：

  • 自己已被指派、in_progress、但 checkoutRunId 为空：补上 run id。
  • checkoutRunId 指向另一个 run：调用 adoptStaleCheckoutRun，它先对 heartbeatRuns 行 for update，只有旧 run 已进入终止状态才接管（第 8185 行起）。
  • executionRunId 指向终止或不存在的 run：同样视为过期锁，接管。

设计取舍：锁挂在「run」上，不是挂在「Agent」上，所以同一个 Agent 的新 run 可以接管自己旧 run 留下的锁；代价是 checkout 一个函数就写了两百多行状态机，每种半死状态各有分支。与 Anthropic 编译器的「往目录写文本文件当锁」相比，一个靠数据库事务保证一致，一个靠 git 同步，成本差别很大。

坑：过期判断依赖 heartbeatRuns.status 是否终止。如果 run 进程崩了但状态没来得及改成终止，锁会一直被视为有效，必须等别处的清理任务把 run 标成终止后才能收养。我读到的是这个依赖关系；清理任务本身（heartbeat 超时检测）我没读，所以「多久能恢复」没有数字。

设计取舍：handoff 做成工具调用，好处是模型决策和普通工具走同一条路径；代价是一轮里只允许一次转交，同轮多个并行转交被丢掉，只在 tracing 里记一个 Multiple handoffs requested 错误。失败时不触发 hook，也不做历史过滤，当前 Agent 继续下一轮（NextStepRunAgain）。

设计取舍：三点。其一，同一个节点同一时刻只跑一份，新触发先排队，这是用串行换不出竞态。其二，并发上限 max_concurrency 在调度处检查，replay 中的节点不占名额，因为它们是历史快进。其三，完成的任务按「恢复序列」排序处理，注释里写明是为了让重放结果与历史一致（asyncio.wait 返回的集合没有顺序）。代价：整个循环围绕「可重放」设计，复杂度很大，一个调度函数里混了 held transfer、interrupt、replay 三套逻辑。

坑：WAITING 且有未决 interrupt 的节点会让新触发一直排队（见 continue），如果人一直不回应，上游持续产出会在缓冲区里堆起来。我没找到缓冲区上限的代码，不能下结论它会不会无限增长。

判断 三个仓库放在一起，各自回答「状态在哪、谁写」：Paperclip 把「谁在做」写进 Postgres 一行并靠 WHERE 条件抢占；OpenAI SDK 干脆限定每轮只有一个活动 Agent；ADK 用事件触发缓冲加节点串行化。共同点是都在调度点上硬编码了互斥，没有一个靠 Agent 自己协商。

  2. 并行写要隔离，并行想可以放开。CAID（worktree + merge）、Gas Town（flock）、Cognition（写保持单线程）三者一致。判断
  3. Manager 要有核实手段。没有，就别加这一层。判断
  4. 成本比要用同一个分母。15×、7×、22× 不是一回事。
  5. 要验证的三件事（没做）：在自己的任务上量单 Agent 与 Teams 的 token 比；DeepSeek 原型的 Engine 单写者在高并发时的吞吐；Codex、Pi 的多 Agent 结构是否趋同。
