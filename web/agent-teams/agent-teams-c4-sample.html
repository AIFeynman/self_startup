1　指令文件：让 Agent 不用每次从零开始

起点：不写指令会怎样

每个会话开始，模型的上下文里没有「这个项目怎么干活」。它不知道测试怎么跑、哪些文件不能动、团队要什么风格。你在聊天里纠正一次，会话一结束就没了。第二天它犯同样的错。

所以大家把规则写进文件，让 harness 每次启动自动读进上下文。

设计原理：为什么是一个纯文本文件？ 判断

  • 不用训练模型。改一行文字，下一个会话就生效。
  • 跟着代码走。放进 git，评审、回滚、分支都能用，团队共享。
  • 没有格式门槛。AGENTS.md 官网明说没有固定格式，就是 Markdown。写得好不好，只看内容。
  • 代价：它只是「放进上下文的文字」，模型怎么用它，harness 管不了。这是后面所有问题的根源。

每个目录按这个顺序试：AGENTS.override.md → AGENTS.md → 你配置的备选名（project_doc_fallback_filenames，默认空）。找到第一个就停，每个目录最多读一个。

判断 为什么要有 override？个人想临时覆盖团队约定，又不想改被 git 跟踪的 AGENTS.md。把 override 文件加进 .gitignore，就是「个人本地版」。这是我从源码和命名推出来的用法，没有在官方文档里核对。

判断 备选名里写 CLAUDE.md，同一个仓库就能给 Codex 和 Claude Code 共用一份，不用写两份。同样没有核对过官方说法。

第 3 步：读多少，超了怎么办

默认总预算 32 KiB（codex-rs/config/defaults.toml 里 project_doc_max_bytes = 32768）。一手 读文件的核心代码：

  • 文件比剩余预算大，就硬截断，截掉的是文件尾部。
  • 截断时往 warnings 里放一条警告，写明只读了多少字节。
  • 预算是所有文件共用的。外层先读先占；内层文件最容易被挤掉。

另有两处检查在 load_project_instructions 开头：项目是 untrusted，或者预算为 0，一个都不读。

坑 1：关键规则写在文件末尾。超预算时被截的正是尾部。把最重要的规则放文件开头。

坑 2：最内层的规则最容易丢。你以为「子目录的规则优先」，但预算被外层先吃掉了。外层文件要瘦，给内层留空间。

坑 3：以为超限没有提示。我读到一份调研说「超限时没有警告」，源码里是有警告的。警告在界面里怎么显示、用户能不能看到，我没实测。判断 遇到「规则没生效」，先查文件总大小是不是超了 32 KiB。

2　Skill：把「流程」从常驻上下文里拿出来

起点：指令文件越写越长

指令文件一直在上下文里。每加一个流程（发布步骤、评审清单、写周报的格式），所有任务都要多背一份。大多数任务根本用不上。

Skill 的想法是：平时只让模型知道「有这个流程」，真要用时再读全文。

目录结构和三层加载

pdf-processing/
├── SKILL.md          必需：frontmatter + 正文
├── scripts/          可运行的脚本
├── references/       详细资料，按需读
└── assets/           模板、图片、数据文件

规范（agentskills.io）的硬约束：一手

字段要求
name必填，最多 64 字符，必须和目录名一致
description必填，1–1024 字符，要写「做什么」和「什么时候用」，带具体关键词
可选license、compatibility、metadata、allowed-tools（实验性，各 harness 支持不一）

设计原理：渐进披露，用的是「上下文预算」的思路。 判断

  • 上下文是稀缺资源（越满越贵，也越容易漏看）。所以把「知道有它」和「读它的内容」分开。
  • 第 1 层极小，所以可以装很多 Skill。第 2、3 层大，但只在用到时付费。
  • 代价：触发全靠第 1 层那一句 description。模型没判断出该用，后面两层就永远不会读。

精读：Skill 触发率到底怎么测——skill-creator 的三个脚本

来源：anthropics/skills 的 skills/skill-creator/scripts/run_eval.py、improve_description.py、run_loop.py，2026-11-16 读取，main 分支（run_eval.py 最近一次提交 2026-02-25）。一手 没读 skill-creator 的 SKILL.md 和其余脚本。

入口：run_loop.py。它反复调用 run_eval.py 测「这条 description 能不能让 claude 去调用 Skill」，再调用 improve_description.py 让模型改写 description。

1　切分split_eval_set(eval_set, holdout, seed=42)，按 should_trigger 分层，留出测试集
2　测run_eval.py：每条 query 跑 N 次（默认 3），统计触发率
3　判正例触发率 ≥ 阈值（默认 0.5）算过；反例要 < 阈值
4　改improve_description.py 用评测结果和历史写新 description

关键调用链（run_eval.py）：

  1. 在项目的 .claude/commands/ 下写一个临时文件 <skill>-skill-<uuid8>.md，把候选 description 放进去。这是代理：它没有走真正的 Skill 注册，而是借斜杠命令让 claude 看到一条带描述的条目。判断（依据：脚本注释和写文件的位置）
  2. 执行 claude -p <query> --output-format stream-json --verbose --include-partial-messages，进程里删掉 CLAUDECODE 环境变量以便在 Claude Code 里嵌套运行。
  3. 逐行读流式事件，只要 Skill 或 Read 的工具调用参数里出现这个唯一名字就算触发；超时（默认 30 秒）按未触发；finally 里一定删临时文件。

            .get(query_term)
            .copied()
            .unwrap_or_default() as f64;

            return score;
        }

            document
                .fields
                .iter()
                .enumerate()
                .fold(0.0, |weighted, (field_index, terms)| {
                    let term_frequency =
                        terms.iter().filter(|term| *term == query_term).count() as f64;
                    if term_frequency == 0.0 {
                        return weighted;
                    }
                    let average_length = average_field_lengths[field_index];
                    let length_ratio = if average_length == 0.0 {
                        1.0
                    } else {
                        terms.len() as f64 / average_length
                    };
                    weighted
                        + FIELD_WEIGHTS[field_index] * term_frequency / (1.0 - B + B * length_ratio)
                });
        if weighted_term_frequency == 0.0 {
            return score;
        }
        let inverse_document_frequency =
            (1.0 + (document_count - frequency + 0.5) / (frequency + 0.5)).ln();
        score
            + inverse_document_frequency * weighted_term_frequency * (K1 + 1.0)
                / (weighted_term_frequency + K1)
    })

3　MCP：给模型一个标准的外部接口

起点：每个应用接每个系统，都要单独写

这就是官网「USB-C 接口」比喻的意思。一手 M×N 的说法和「借鉴了 Language Server Protocol」来自维基百科。二手

三个角色，怎么连

每个 server 配一个专用 client；server 对外提供 tools、resources 等能力，可以在本机，也可以远程。二手（维基百科）官网给出的三类能力：数据源、工具、工作流。一手

判断 Skill 教模型「怎么做」，MCP 给模型「能碰什么」。一位演讲者的比喻是：MCP 提供厨房，Skill 提供菜谱。二手

设计原理：标准化的好处和代价是同一件事。 判断

  • 好处：接入成本从 M×N 降到 M+N；用户装一个 server，各个应用都能用。
  • 代价 1：为了让模型会用，server 要把每个工具的名字、描述、参数都交给模型，这些常驻上下文。装得越多越占地方。
  • 代价 2：工具描述是别人写的文字，模型会把它当可信信息读，这就成了攻击面。

一个最小 MCP server 长什么样

官方 Python SDK 的示例，把两个普通函数暴露成工具。一手

这几行里藏着前面讲的坑的来源：

  • 示例里没有任何权限控制。工具里的函数想做什么就能做什么，安全要靠你自己在工具里加，或者在 harness 层用 Hook 拦（第 4 节）。判断

三层筛选：事件（PreToolUse）→ matcher（只对 Edit、Write 生效）→ 脚本里的判断。脚本检查要写的路径，包含 robots.txt 就退出码 2。NicholasDulait 说他测过：Claude 想覆盖 robots.txt，被拦住，文件没变。二手（自述；配置原文来自他的文章）

设计原理：为什么 Hook 是「保证」？ 判断

  • 它在 harness 里运行，不经过模型。模型没有机会「忘记」或「判断不用遵守」。
  • 它在动作之前运行（PreToolUse）。事后补救（PostToolUse）只能告诉模型出错了。
  • 默认「出错就放行」（fail open），避免一个坏脚本把整个会话卡死。这是官方的取舍，但对安全规则是反方向的，见下面的坑。

坑 16：脚本报错 = 没拦住。只有退出码 2 才阻止。脚本崩溃、jq 没装、路径写错，harness 都当「非阻塞错误」继续执行。所以安全 Hook 要写一个小测试，确认它真的会拦。yureki_lab 也建议这样做。二手 文档里还提到可以给 Hook 设 onFailure: "block"，让失败也算阻止。一手

坑 17：以为「放行」能压过「拒绝」。hooks 官方文档原文：PreToolUse 的 hook 返回什么，deny 和 ask 规则都照样判；PermissionRequest 里的 allow 也推翻不了匹配的 deny 规则。所以 Hook 只能把门收紧，不能把管理员的禁令放宽。一手（hooks 文档，我读了；steve kinney 课程页的说法与它一致，不再作为依据）

坑 18：把所有规则都改成 Hook。只转换「机器能判断」的规则（路径、命令、关键词）。「代码要简洁」写不成 Hook。风格类规则交给 linter，用 Stop 事件把错误回传。二手（HumanLayer 的做法）

坑 19：以为 Hook 只能跑 shell 脚本。官方文档列了五种 handler：command（本地命令，事件 JSON 走 stdin）、http（POST 到一个地址）、mcp_tool、prompt、agent。事件按频率分三档：每会话一次（SessionStart、SessionEnd）、每轮一次（UserPromptSubmit、Stop、StopFailure）、每次工具调用（PreToolUse、PostToolUse）。官方事件表远不止这几个，Agent Teams 的 TeammateIdle、TaskCreated、TaskCompleted 也在里面（见 C5）。一手 实用结论：PreToolUse 加 matcher 再加 if 字段（例如只在命令匹配 Bash(rm *) 时才起进程），可以让大部分工具调用不付起进程的成本。一手（文档示例，我没测过耗时）

坑 20：不知道到底有没有加载。Claude Code 有 InstructionsLoaded 事件，可以记录哪些 CLAUDE.md 和 rules 在什么时候加载。排查「规则没生效」时用它。一手

Plugin：把 Skill、Hook、MCP 打成一包

起点：团队里每个人各配一套 Skill 和 Hook，换个人就不一致。Anthropic 的发布博客（2025-10-09）写的做法是：把斜杠命令、subagent、MCP server、Hook 打成一个 plugin，用 /plugin 安装，可以随时开关，不用时关掉以减少系统提示的上下文。博客还把用途分成五类：统一规范、支持用户、共享流程、接工具、打包多项自定义。一手

官方 plugins 文档给的目录是：.claude-plugin/plugin.json（清单）、skills/review/SKILL.md、agents/reviewer.md、hooks/hooks.json、.mcp.json。装好后 Skill 以「plugin 名:skill 名」的形式运行，例如 /my-plugin:review。一手

坑 21：把 plugin 当成「装了就安全」。plugin 里的 Skill 能带脚本，Hook 会在你的机器上执行命令，MCP 会把外部内容送进上下文。Anthropic 自己的容器化文章（how-we-contain-claude，2026-05-25）提醒：已审计的连接器不等于已审计的数据；远程工具装完之后行为可以变，安装时的信任不再成立；目录之外的一律当不可信，先拿假数据跑。一手 它还提到 Claude Code 曾有三个漏洞出在「用户点信任之前」就执行的代码：仓库里的 .claude/settings.json 带 hook，会在信任弹窗之前运行，修法是把项目配置的解析推迟到用户确认之后。一手 判断 这对 plugin 的启示是：装第三方 plugin 前先读它的 hooks/hooks.json，不要只看 Skill 的说明。

论文 3　Do Context Files Help Coding Agents?（arXiv 2607.27250，2026-07-28）

作者：Khatri，独立研究者。一手 规模小，但设计最接近日常问题：同一份内容，怎么送进去有区别吗？

  • 规模：Claude Code（sonnet-4-6）与 Codex；3 个仓库（opshin、pdm、firebase）的 17 个任务；288 次有效运行（每任务重复 3 次）。
  • 三种「注入方式」：
    • none：不给；
    • always_on：完整 AGENTS.md 每轮都放进系统提示；
    • selective：把内容拆成按主题分的 wiki 文件放在工作区，提示里只说「需要时去读 wiki/*.md」，Agent 用 Read 工具按需取。

测到什么：

  • 正确率：三种方式没有可测差异；用等价检验（TOST）把效应限制在 10–15 个百分点以内。作者强调这不是「功效充足的等价结论」：要把界限压到 10pp，大约需要 120 个任务，他只有 15–17 个。
  • 为什么没差别：他对失败做了分类，发现 Agent 失败是因为「实现能力」（怎么设计功能、选哪种模式、接线是否准确），不是缺少仓库知识。他还做了一个探针：真实的 AGENTS.md 从来没有把一个「差一点」的任务变成通过。
  • 效率有两个窄小的效应：selective 在 Claude 上降低了缓存占用（Holm 校正 p = 0.012）；在 opshin 仓库（文件里写了「全量测试很慢」），Agent 不再盲目跑全量测试，且随文件分量增加而更明显。
  • 他对前两篇矛盾的解释（假设，他没有对方的任务集）：论文 2 的「效率变好」可能只是注入方式带来的机械差别，论文 1 的「成本变高」则是反方向的同类机械差别；两者都不是 Agent 能力的变化。

对写文件的人，他的实务结论：通用的上下文文档花的力气，可能不如花在任务拆分、工具和「带例子的提示」上；但即使不改通过率，上下文能改变 Agent 的做法（少跑无谓的全量测试），所以可以因为成本和延迟留下。判断 这条结论的样本很小，只能当线索。

6　怎么写才有效

起点：解剖一份流传很广的例子

multica-ai/andrej-karpathy-skills 的 CLAUDE.md，约 23 万 star。一手 它是社区整理，不是 Karpathy 官方发布；作者说灵感来自 Karpathy 的一条推文，我没读到原推文。它有没有用没有 A/B 数据，star 数不代表效果。我们只拿它当解剖样本。

规则（仓库原话）针对的失败能不能机器检查
Think Before Coding：Don't assume. Surface tradeoffs.悄悄选一种理解，硬写下去弱，只能人看有没有列假设
Simplicity First：Minimum code that solves the problem.写没人要的抽象中，能数行数、新增文件
Surgical Changes：Touch only what you must.顺手改旁边的代码强，diff 范围可以用 Hook 检查
Goal-Driven Execution：Define success criteria. Loop until verified.「让它能用」这类弱目标强，先写测试，跑不过就不算完

写规则的四个原则

判断 这是我从上面的证据和一线文章里总结的，不是论文结论。

原则差的写法好的写法
一条规则对应一个失败模式「注意代码质量」「改完必须跑 pnpm test，不过不算完成」
给替代动作，不只是禁止「别用 npm」「包管理用 pnpm」
写成能检查的样子「代码要简洁」「新增文件不超过 3 个」
带上理由「不要改 pages/ 下的 URL」「不要改 pages/ 下的 URL：改了会丢搜索排名」

对照我们自己全局规则里的一条：**先减后加**：直接替换旧实现，同一次改完所有调用方；不做兼容、迁移、旧字段别名、fallback。

它有动作（直接替换）、范围（同一次改完所有调用方）、禁止清单。但没写理由，也不能自动检查。这一条可以改进。

他的 CLAUDE.md 地图，精简后是这样（只有五块，没有一条是「注意代码质量」这类空话）：

# my-site.com: SEO map
<!-- For humans: last cleaned 2026-11-02. Keep under 200 lines. -->

## The site
- Sells: project management software for agencies
- Reader: agency owners, 5 to 50 people
- Money pages: /pricing, /features, /vs/* (never change their URLs)

## Where things live
- keywords/: one cluster per file, with the target page
- pages/: one file per money page, current position and last refresh
- decisions.md: every SEO choice, with the reason

## How to answer
- Real data before opinions: ask for Search Console numbers, never guess volumes
- Quote the file you used. If no file covers it, say so.

## Always in focus
- This quarter: @strategy/now.md

逐块看它好在哪：

  • The site：只写模型猜不到的事实（卖什么、给谁），不写「这是一个网站」。
  • Where things live：给目录地图，让 Agent 知道去哪读，而不是把内容塞进来。
  • How to answer：规定了做事顺序（先要数据，再给意见）和可检查的动作（引用用了哪个文件；没有就说没有）。
  • HTML 注释：写给人的备注，注入前被剥掉，不花 token。
  • Always in focus：只 import 必须每次都在眼前的一份文件。

第 2 层的 rules，每条都是「可检查的动作 + 理由或边界」：

---
paths:
  - "pages/**"
---
# Money pages
- Never change a URL that has clicks in the last 90 days
- One target query per page. Check keywords/ before adding a new one
- Every edit gets a line in decisions.md with the date

第 3 层的 Skill，用编号步骤写流程。注意第 3 步「先读规则再动手」和第 4 步里的禁止项：

name: page-refresh
description: Use when I ask to refresh a page, or which pages are losing clicks.
---

2. List the queries that lost clicks, and the ones with impressions but no clicks.
3. Read pages/<page>.md and the matching rules before changing anything.
4. Propose the edits: new sections for the missing queries, title and meta only

5. Log the change and the date in decisions.md.

判断 这份 description 只有一句「什么时候用」，还不够强。按前面 Vercel 的数据，触发是 Skill 的弱点，更稳的写法是加上用户会说的词（「refresh」「losing clicks」「掉点击」）。

8.1　Parcha：一个 Skill 怎么长成「公司大脑」

作者 Miguel Rios，Parcha 团队；开源在 Parcha-ai/parcha-skills。是一线团队的自述，有测量数字，但是自家系统、没有外部复现。二手

演进过程，每一步都是「撞到问题才加东西」：

阶段形态撞到的问题
4 月一份 SKILL.md：告诉 Agent 会话记录放在 ~/.claude/projects（每个会话一个 JSONL），怎么 grep、读匹配、写总结只能读一台机器、一种工具
加脚本find_sessions.py（按提示词排序）、extract_user_prompts.py、dump_turn_context.py每次搜索要读完所有记录；7 月有 5,000+ 份、约 5 GB。Agent 每用一次脚本，就回去手动 grep 约 9 次

多人多机对象存储 + 摄入服务（入库前脱敏）+ Turbopuffer 搜索 + Parquet/DuckDB + 沙箱 + 小 Postgres 目录；通过 4 个 MCP 工具暴露：search、scope、scan、exec一个月 800 美元的 embedding 费用，促使他们把搜索换成 Turbopuffer

三个值得学的设计决定：

  • Skill 先是文字，脚本和服务是后来长出来的。「很多 Skill 都走同一条路：先是 markdown，加几个脚本，有的长成要托管运行的系统。」这和第 2 节的三层加载一致：先写流程，撞到瓶颈再下沉到代码。
  • 名字就是设计：Recall（召回）。工具只负责「别漏掉」，每条结果带一个 receipt（凭据，能打开原始记录）；「判断真假」交给调用它的 Agent。原话：召回要尽量全，精度由 grep 和执行层负责。
  • 他们删掉了自己加的「召回 Agent」。理由：调用方本身就是 Claude Code 或 Codex，已经很会取证、搜索、总结；中间再放一个 Agent 是重复劳动，还会藏起证据。所以后面把精力放在工具和快速检索上。这是 MCP 工具设计的一条实战原则：给调用方的 Agent 好工具，不要在中间再放一个 Agent。判断

怎么保证不退化：每天一份评分卡（准确率、延迟）。第一周 p95 从 20 秒降到 1.4 秒，「前 20 个里有正确会话」从 54% 升到 88%；他们的验收线是「前 5 个命中 ≥90%，搜索 <2 秒」。

他们的一个数据，提醒你「Skill 不一定是终点」：到 10 月底，53% 的 Agent 会话读了记忆，26% 调用了 Skill。他们的解读是记忆在超过显式 Skill。这是单个团队的数据，不要外推。

8.2　Sentry 创始人：MCP 还是 CLI？都要

作者 zeeg（David Cramer，Sentry 创始人）。他在自家产品上做了取舍，文章讲的是理由。二手

做法：sentry mcp 本质是以 stdio 模式启动 MCP 服务器，再加一层，让它复用 CLI 已登录的凭据。三个理由：

理由具体内容我的判断
共享认证用一个独立的 token 头（Sentry-Bearer 而不是 Bearer）绕开 MCP 服务那套 OAuth（CIMD/DCR）；以前的 MCP 认证 bug 因此不再出现。他自己承认这是「一次性方案」，丢掉了 MCP 的统一认证优势（组织级认证、客户端原生存 token）用在你每天都用的工具上可以，不是长期答案
能力不同CLI 有文件系统：会话回放是大量有序事件，服务端很难预先做好搜索接口；让 Agent 拿到原始事件日志，再分页、grep，更省 token。MCP 的优势是原生：Agent 不用被告知有它，工具说明自带引导「沙箱多于受限 API」是他的判断，不是定论
MCP 实现不一致各 harness 对 tool search（延迟加载工具）的做法不同；instructions 字段「极其重要」但没被统一支持；MCP Events 大多还不可用这解释了第 3 节的坑：同一个 MCP 服务器在不同客户端的体验并不相同

他还提了一个还没实现的设想：MCP 服务器知道自己是被 CLI 启动的，所以可以在工具返回里「引导」Agent 用 CLI 去拿细节（transport-specific steering）。注意这是设想，不是已有功能。

8.3　Addy Osmani：什么该写在文件里，什么该硬拦

文章以 Claude Code 官方 best-practices 指南为蓝本，用「管理者」的视角整理。指南原文我没读，这是转述。二手

  • CLAUDE.md 该放什么：四类。怎么验证（准确的命令）；容易误导的代码区域；仓库里看不到的决定；被你纠正过两次的事。
  • 单条最有用的一行：跑验证的那条命令。理由：Agent 做完「看起来像完成」就停，没有验证机制，「看起来完成」就是唯一的验证。
  • 两类机制的分界：prompt、CLAUDE.md、Skill 是请求（模型可以考虑，也可以不做）；hook、deny 规则、managed settings 是要求（一定执行）。默认让 Agent 自己判断，只对「必须做 / 绝不能做」的少数事用硬拦截，例如「不要改生成的 client」「总是跑加 license 头的脚本」。
  • 两条判据，各管一边：如果一条规则你已经反复强调、Agent 还是不照做，它应该变成 hook；如果一个 hook 表达的只是偏好，不是要求，应该删掉。
  • 反模式：全大写的指令、「think harder」「don't be lazy」（effort 现在是设置项）；用 hook 管可选偏好；新模型出来后还留着老习惯。「过度流程是新的微观管理。」
  • 验证有四种入口：直接要求（「跑完 auth 测试直到通过」）、/goal（另一个模型每轮检查条件）、Stop hook（类型检查没过就不让结束）、/code-review（交给没看过对话的新子 Agent，像作者不批自己的 PR）。
  • 两次纠错就重来：纠正同一个问题两次还不行，清掉会话，把学到的写进更好的提示。

判断 第 4 节的 hook 退出码、第 9 节的「规则放哪里」决策树，实质是同一件事：先问这条规则是要求还是请求。

10　一条主线走一遍

用一条规则串起全章：「不要改已经有流量的页面 URL」。（场景来自 NicholasDulait 的 SEO 站点，机制通用。）

① 只在聊天里说会话结束就没了
② 写进 CLAUDE.md每次都读，但只是建议
③ 拆到 paths: 规则只在碰 pages/ 时加载，省上下文
④ 写成 Hook代码检查，改 URL 就被拦
  • ①→②：从「每天重讲一遍」变成「写下来自动读」。
  • ②→③：根文件越写越长，会被截断、遵循度下降，所以把局部规则拆出去。
  • ③→④：URL 改错，排名就丢了，不能靠建议。最后一步升级成 Hook，并且写测试确认它真的拦得住（坑 16）。

每一步都在回答同一个问题：这条规则要「建议」，还是要「保证」？

11　判断与方向

一句话总图：指令文件解决「每次从零开始」，但只是建议，实测也说明写多了不一定变好；要保证的规则写成 Hook；流程用 Skill 按需加载；外部系统用 MCP 接入，但要为上下文和安全付代价。

共识

  • 仓库概览没用，具体的、不寻常的约定有用。（2602.11988 摘要；两项实测方向一致）
  • 文字规则不保证执行；保证靠 Hook。（官方文档与多篇一线文章一致）
  • Skill 要先被触发才有用。（Vercel 评测）
  • MCP 的主要代价是上下文和安全。（Anthropic 博客、MCPTox、CSA，都是二手读到）

分歧

  • 指令文件到底提升还是降低表现：两项论文结论不同，还没有独立复现。
  • Skill 是否值得写：SkillsBench 报告精选 Skill 平均 +16.6pp，Signal or Noise 报告注入公开 Skill 平均降低 1.3–4.2pp。两篇我都读了全文，差别主要在 Skill 来源和与任务的匹配度，对照见第 5 节末的「三篇 Skill 论文并排看」。一手

开放问题：没找到专门研究 Hook 效果的论文，也没找到「指令文件长度与效果」的剂量曲线。这两块目前只有一线文章的经验。

    4. 接一个 MCP server

    4. 把整个流程写进 description
