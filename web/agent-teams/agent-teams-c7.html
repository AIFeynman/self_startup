片段 A：能做什么、不能做什么（karpathy/autoresearch，master，program.md 第 23-31 行）一手

Each experiment runs on a single GPU. The training script runs for a **fixed time budget of 5 minutes** (wall clock training time, excluding startup/compilation). You launch it simply as: `uv run train.py`.

**What you CAN do:**
- Modify `train.py` — this is the only file you edit. Everything is fair game: model architecture, optimizer, hyperparameters, training loop, batch size, model size, etc.

**What you CANNOT do:**
- Modify `prepare.py`. It is read-only. It contains the fixed evaluation, data loading, tokenizer, and training constants (time budget, sequence length, etc).
- Install new packages or add dependencies. You can only use what's already in `pyproject.toml`.
- Modify the evaluation harness. The `evaluate_bpb` function in `prepare.py` is the ground truth metric.

## The experiment loop

The experiment runs on a dedicated branch (e.g. `autoresearch/mar5` or `autoresearch/mar5-gpu0`).

LOOP FOREVER:

1. Look at the git state: the current branch/commit we're on
2. Tune `train.py` with an experimental idea by directly hacking the code.
3. git commit
4. Run the experiment: `uv run train.py > run.log 2>&1` (redirect everything — do NOT use tee or let output flood your context)
5. Read out the results: `grep "^val_bpb:\|^peak_vram_mb:" run.log`
6. If the grep output is empty, the run crashed. Run `tail -n 50 run.log` to read the Python stack trace and attempt a fix. If you can't get things to work after more than a few attempts, give up.
7. Record the results in the tsv (NOTE: do not commit the results.tsv file, leave it untracked by git)
8. If val_bpb improved (lower), you "advance" the branch, keeping the git commit
9. If val_bpb is equal or worse, you git reset back to where you started

The idea is that you are a completely autonomous researcher trying things out. If they work, keep. If they don't, discard. And you're advancing the branch so that you can iterate. If you feel like you're getting stuck in some way, you can rewind but you should probably do this very very sparingly (if ever).

文件 meta_harness.py，分支 main，读取日期 2026-11-16，第 218-254 行：一手

def update_evolution_summary(
    iteration,
    candidates,
    val_scores,
    propose_time=None,
    bench_time=None,
    wall_time=None,
):
    """Append one JSONL row per candidate to evolution_summary.jsonl."""
    frontier = json.loads(FRONTIER_VAL.read_text()) if FRONTIER_VAL.exists() else {}
    pareto = frontier.get("_pareto", [])
    best_val = pareto[0].get("val_accuracy", 0) if pareto else 0

    with open(EVOLUTION_SUMMARY, "a") as f:
        for i, c in enumerate(candidates):
            name = c["name"]
            avg_val = val_scores.get(name, 0)
            row = {
                "iteration": iteration,
                "system": name,
                "avg_val": round(avg_val, 1),
                "axis": c.get("axis", "?"),
                "hypothesis": c.get("hypothesis", ""),
                "delta": round(avg_val - best_val, 1) if best_val else None,
                "outcome": f"{avg_val:.1f}% ({avg_val - best_val:+.1f})"
                if avg_val > 0
                else "failed",
            }
            if "components" in c:
                row["components"] = c["components"]
            if i == 0 and wall_time is not None:
                row["timing_s"] = {
                    "propose": round(propose_time, 1),
                    "bench": round(bench_time, 1),
                    "wall": round(wall_time, 1),
                }
            f.write(json.dumps(row) + "\n")

读法：每个候选一行。hypothesis 是提议者自己写的假设，delta 是和当前最佳的差，所以每行同时是「预测」和「结果」，下一轮的提议者可以对照两者。计时只写在第一个候选行里（i == 0），所以按行求和会漏掉其他候选的耗时，做成本统计时要注意。一手

6.1　16 个并行 Claude 写 C 编译器（Carlini，2026-02-05）

项目原文怎么说
规模16 个 agent，近 2000 个 Claude Code 会话，两周，20 亿输入 token、1.4 亿输出 token，成本略低于 2 万美元；产物是 10 万行 Rust 编译器，能编译可启动的 Linux 6.9（x86、ARM、RISC-V），在多数编译器测试集（含 GCC torture test）上通过率约 99%
循环最简单的无限循环：一个任务做完马上起下一个会话，每个 agent 在自己的 Docker 容器里。作者说它和 Ralph-loop 类似
防撞车agent 往 current_tasks/ 写一个文本文件当锁（例如 parse_if_statement.txt）；两个 agent 抢同一个任务，靠 git 的同步让后到的换一个。做完先 pull 合并、再 push、最后删锁。合并冲突很多，Claude 自己能解
没有的东西没有编排 agent，没有别的通信渠道，也不管高层目标；每个 agent 自己挑「下一个最明显的问题」
测试怎么设计作者的话：任务验证器要近乎完美，否则 Claude 会解错题。后期 Claude 每加新功能就弄坏旧功能，作者补了 CI，并做了更严格的强制检查，让新提交不能破坏旧代码
给模型看的输出测试脚本只打几行，细节写日志；出错写一行 ERROR 加原因，方便 grep；预先算好汇总数字。作者还说 Claude 不会看时间，所以脚本默认带 --fast，跑 1% 或 10% 的随机抽样；抽样对同一个 agent 固定、不同 VM 之间不同，所以整体覆盖全部文件，单个 agent 也能准确看出回归
卡住怎么办测试通过率到 99% 后，各 agent 各去编译一个小开源项目（SQLite、Redis、Lua 等）。编 Linux 内核时所有 agent 撞上同一个 bug、互相覆盖。解法：用 GCC 当「已知正确的编译器」做对照，随机让大部分文件由 GCC 编、少数由 Claude 的编译器编；内核坏了说明问题在 Claude 那一份，再缩小范围，这样每个 agent 可以去修不同文件。之后还要用 delta debugging 找「单独都行、一起就坏」的文件对
分工一个 agent 专门合并重复代码，一个管编译器自身性能，一个管生成代码的效率，一个从 Rust 开发者角度挑设计毛病，一个写文档
天花板（作者自己写的）没有 16 位 x86 编译器，引导阶段调用 GCC；汇编器和链接器还有 bug，演示视频用的是 GCC 的汇编器和链接器；开全部优化的输出还不如 GCC 关优化的；新功能经常弄坏旧功能；作者说已接近 Opus 能力极限

能信多少：数字（2000 会话、2 万美元、99%）都是作者自报，没有第三方复现；99% 是「多数」测试集，不是全部；作者自己列出了不完整之处，这一点可信度较高。它是单次实验，不能推出「16 个 agent 一定比 4 个好」。判断

坑 22：验证器比提示词重要，它错了 agent 会很努力地解错题。作者原话的意思：Claude 会自主解你给的题，所以验证器要近乎完美。对应本章三道闸：确定性闸就是这件事，且要随失败样例持续补测试。一手
做法：每发现一种新失败，就补一条能复现它的测试；不要只调 prompt。

坑 23：测试输出会污染上下文，也会让 agent 浪费几小时。脚本打上千行无用字节会挤掉有用信息；agent 没有时间感，会一直跑测试。做法：只打几行、细节入日志、统计预先算好；默认走确定性的小抽样（--fast），整批留给收尾。这和本章「先便宜后贵」一致。一手（原文做法）判断（与本章规则的对应）

坑 24：只有一个大任务时，并行不会加速，要先把任务拆成可独立失败的块。编 Linux 内核时 16 个 agent 撞同一个 bug。作者用 GCC 当对照物，把「一个大失败」变成「每个文件一个小失败」。做法：能不能找到一个已知正确的实现当 oracle，是并行能否生效的前提。一手

6.2　Scion：agent 规模下，全局合并队列行不通（Anthropic，2026-10-13）

项目原文怎么说
压力每天合并的代码变更：2026-05 平均约 2500 个，到 9 月超过 3 万个。主分支历史近 100 GB，压缩后的工作副本超过 25 GB；CI 每天约 2500 万次 checkout，若直接用 git 取会是每天超过 600 PB 流量
做法自研版本控制系统 Scion，用 5 个月把 monorepo 从 git 全部迁过去。客户端总是在线，服务器负责 diff、blame、commit、merge；commit 在服务器上做，没有 push；CI 要的信息多数通过 API 问服务器，不必先 checkout
数据结构工作单位是 changeset（写前日志里的一项），存「相对第一个父节点改了哪些文件」加内容寻址的指针。blame、路径历史、提交图的跳表等放在「派生数据」里，按需或延迟计算
效果（自报）各层缓存命中率超过 99%；基础设施规模比之前的 git 镜像小 200 倍（CPU 与内存）；CI 与研究任务的 checkout 快两个数量级（秒级而非分钟级）；CI 一项就省了 25% 的 CPU 容量
团队7 人，同时做了 Scion 和代码评审工具 Antique 等，5 个月完成迁移，期间每日合并量涨了 10 倍
对合并队列的结论原文：他们没能复制业界标准的「全局仓库锁」合并队列，转而投资合并后与上线前的自动测试；这意味着并发改动可能冲突，但 Claude 通常比人更快修好冲突

能信多少：这是单家公司对自己系统的自述，规模（日合并量、PB 流量）是它自己的数字；作者也说明 Scion 不适合替代一般的 git，只适合超大 monorepo 或大量 agent 写代码的场景。「小 200 倍」「快两个数量级」没有给测量条件。我只能把它当作量级参考。判断

6.3　/goal：把「模型闸」做成产品功能（Claude Code 文档）

def get_report_score(test_report):
    """
    Get the score from the test report.
    """
    # Percentage of passed tests
    passed_count = sum([1 for v in test_report.values() if v == 'PASSED'])
    total_count = len(test_report)
    return passed_count / total_count if total_count > 0 else 0
