一　动手三步（压缩版）

0　先判断：该不该上 Teams

基线是「手上有 Teams 就都用」。证据说这样亏：Google 2512.08296 v3（经典例外）里，同一批多 Agent 配置在可拆的金融推理上 +80.8%，在顺序规划上 −70.0%（C5 §2 一手）。所以先问四项：

项问这个低的后果
可并行度能拆成互不改同一文件的几块吗？低：别上
上下文依赖几块之间有多少隐含决定要共享？高：写入单线程，其余当顾问
验收可机器化有没有一条命令给出通过 / 失败？低：先造裁判，别上
成本多花的钱和人时，值不值换来的时间？没量过单 Agent 基线就不知道

这四项和门槛是我的归纳（判断），没有定量依据。大多数任务四项过不齐。例：三个互不相关的类型错误，单 Agent 就够；120 个文件按目录迁移、有测试，才适合分 worker。这些是我拟的设想任务，不是实测。

1　搭小团队：1 lead + 2 worker + 1 评审（约 2h）

基线是开四个会话互相发消息。三个洞：状态在各自脑子里，崩一次就丢（C3）；谁说「做完了」谁当裁判，自评偏宽（C6、E）；没人管花钱（G）。所以骨架只做一件事：把「谁能改状态、能不能算做完、花了多少」从模型手里拿走。

角色能做不能做依据
lead读目标，写工单（范围、验收命令、预算），派活，回写不写代码少角色（B §7）
worker A / B在自己的 git worktree 里改，只改工单 scope 内文件不改状态、不改验收命令、不碰对方目录worktree 63.3 对 soft isolation 55.5（C5 §2）
评审新会话，只看 diff 和验收条件，最多 3 轮看不到 worker 的自我说明；只读E §3；Khazix 的 3 轮上限（A §5.1，转引）
人在批准卡上点一次—合 main、删数据、花钱必须人批（A §2）

五步做完（每步一句）：写 GOAL.md（完成标准一条命令、范围、预算、停止条件、必问人的事，到 80% 告警、100% 硬停，G §3）；git worktree add 两个目录，凭据不给 worker，外层加 timeout（C1、C2）；用下面的状态机管工单；执行后三层验收（确定性命令 → 评审看 diff → 人从真实入口走一遍，C7 §4、E §4）；人在批准卡上点一次，回写只追加（G、C7、D）。

NEXT = {"todo":"doing","doing":"checked","checked":"reviewed",
        "reviewed":"approved","approved":"done"}
WHO  = {"todo":"lead","doing":"worker","checked":"reviewer",
        "reviewed":"human","approved":"lead"}

def move(tid, actor):
    t = load(tid); st = t["status"]
    if WHO[st] != actor:
        sys.exit(f"DENY: {st} -> {NEXT[st]} 只能由 {WHO[st]} 做，不是 {actor}")
    if st == "doing":
        r = subprocess.run(t["accept_cmd"], shell=True)
        t["log"].append({"accept_exit": r.returncode})
        if r.returncode != 0:
            save(t); sys.exit("DENY: accept_cmd 退出码非 0，不能进 checked")
    if st == "reviewed" and not sys.stdin.isatty():
        sys.exit("DENY: 批准必须由人在终端里敲，管道输入不算")
    t["status"] = NEXT[st]
    t["log"].append({"to": t["status"], "by": actor}); save(t)

示例代码为我自写，非仓库原文。一手 我在 scratchpad 里用 accept_cmd = "test -f out.txt" 做过状态检查：worker 抢 lead 的步骤被拒；out.txt 不存在时 doing → checked 被拒，创建后通过；reviewer 越权做 human 的步骤被拒；echo y | … 当人批准被拒。这只是几次状态检查，没有接真实 Agent，没有跑过一轮完整任务。

坑：这个状态机防的是「Agent 手滑」，不是「Agent 作恶」。actor 是命令行参数，有 shell 的 Agent 可以传 human。真要防，得把 board/ 对 worker 设成只读，由沙箱外的进程来跑它（C2 的强制层、G）。isatty 只挡无终端的 headless 会话。判断

2　使用评估：对照单 Agent（约 1h）

基线是「演示一次成功」。洞有三个：运气、多花钱、人救场没记。口径先写死：

指标口径
成功率同一任务每组跑 k 次（建议 3），同时报 pass@1 和 pass^k。单次 80% 时，三次全对约 51%（0.8³），至少一次对约 99%（E §6，一手）
人介入次数人必须读并回答的事件算 1 次：批准卡、评审转人、救场、改工单。通知不算
单位成功产出成本（所有运行的机器花费 + 人的分钟 × 你填的时薪）÷ 成功工单数。失败、评审、返工全算进分子
失败原因每次失败归一类：任务不可拆 / 越界或合并冲突 / 验收命令不够 / 评审放行 / 上下文丢失 / 超预算或空转

怎么跑：选 4 个任务（3 个判断为适合、1 个不适合当对照）；先跑 Teams，记总 token 与墙钟，再让单 Agent 在同样的 token 上限内跑同一任务；同一台机器；每任务每组 3 次，共 4×3×2 = 24 次。本章没有跑这 24 次，上面只是口径。24 次只够做方向决策，不是统计结论（第二部分命题 10 会展开）。判断

Mollick（2026-01-27）把「该不该委托」写成三个量：自己做要多久、AI 一次做对的概率、你请求等待并评估一次的时间。他的例子：7 小时的任务，AI 约 72% 做对，每次评估约 1 小时，平均约省 3 小时（原文一手；数据来自 GDPval 一类评测，不是 Agent Teams）。用在这里：Teams 若让成功概率升了，却让每次的「请求加评估」时间翻倍，可能比单 Agent 更亏。所以成本指标必须带人的分钟数。判断

2.1　十条有争议的命题

命题 1　多个 Agent 可以并行往同一个代码库里写，吞吐值得那点冲突。

这是一线真分歧：Cursor 对 Cognition。

正方证据：Cursor 2026-01-14：浏览器项目跑了约一周，超过 100 万行、约 1000 个文件、数百个 worker，文中说冲突「minimal」；Solid 到 React 的迁移用了 3 周多，+266K/−193K 行编辑，但文中也说「still needs careful review」一手（厂商自述，无外部复现）。Anthropic 的 C 编译器：16 个 Agent、约 2000 个会话、花费约 2 万美元（20 亿输入与 1.4 亿输出 token），写出约 10 万行、能编译 Linux 6.9 的编译器，并用 GCC 当已知正确的对照物来拆活一手。

反方证据：Cognition 2025-06-12：默认用单线程的线性 Agent，并行的 Agent 做出的隐含决策会冲突一手；2026-04-22：并行写手群仍然不行，写保持单线程；那些惊艳的大 demo 共同点是成功标准简单、可验证一手。Cursor 自己：加锁后 20 个 Agent 的吞吐只剩 2 到 3 个一手。2607.04697：跨 Agent 的合并冲突率 41.7%（N=115），同类 19.8%（N=601）；CooperBench 两个 Agent 合作比单个低约 30%（C5 §5、main §1）二手。Anthropic 研究系统文章：大多数编码任务可真正并行的部分少一手。

证据强度：中。两边都是厂商自述。Cursor 的规模最大，但没有外部复现，也没有写明对照的单 Agent 做不做得成。Anthropic 编译器有 GCC 当裁判，且作者自己承认接近模型能力上限、新功能常破坏旧功能。Cognition 没给对照数据，但机制说得清。没有一个对照实验在同一任务上比并行写和单写。

我的判断：默认单写者；只有「scope 能切成不相交 + 有一条强裁判命令」两者同时满足才并行写。置信度 70%。判断

什么新证据会让我改判：有人在没有 oracle 的真实仓库任务上，公布并行写对单写的对照结果（同 token 预算、含合并冲突的返工成本），并行写更好且能被第三方复现。

落到你的团队：小团队里两个 worker 的 scope 不相交、各用 worktree；没有 accept_cmd 的工单一律单写。

命题 2　多 Agent 比单 Agent 强，是因为结构，不只是因为花了更多 token。

这是一线真分歧：Anthropic 对 Cognition。

正方证据：Anthropic 研究系统（2025-06-13）：多 Agent 在内部评测上比单 Agent Opus 4 好 90.2%一手。CAID（2603.21489）：worktree 隔离 63.3，单 Agent 57.2；单 Agent 迭代次数翻倍几乎没用（PaperBench，C5 §2）一手（C5 读过）。

反方证据：同一篇 Anthropic 文章说，BrowseComp 上 token 用量单独解释了 80% 的方差（三个因素共解释 95%），Agent 约是聊天的 4 倍 token，多 Agent 约 15 倍一手。2604.02460：多跳推理里总思考 token 相等时单 Agent 追平或超过多 Agent（main §1）二手。CAID 的代价：分数 +6，花费 2 到 4 倍（C5 §2）。Google 2512.08296：顺序规划 −70.0%（经典例外，C5 §2）。

证据强度：中。90.2% 来自 Anthropic 自己的内部评测，没有公开任务集。「token 解释 80%」是对多 Agent 优势的一个强削弱，但它测的是浏览类任务，不是写代码。

我的判断：多 Agent 的大部分收益先当成「多花 token」，只有同 token 预算下还领先，才算结构的功劳。读和搜这类可并行的任务值得，写和顺序规划不值得。置信度 65%。判断

什么新证据会让我改判：同 token 上限的对照里，多 Agent 在写代码任务上稳定领先（pass^k 层面），且有第三方复现。

落到你的团队：第一部分第 2 步评估时，单 Agent 一定要给同样的 token 上限；比较「单位成功产出成本」，不比成功率。

命题 3　独立评审要换一个模型，同一个模型的干净上下文不够。

这是一线真分歧：Cognition 对 Anthropic。

正方证据（要换 / 要独立）：Anthropic harness design（2026-03-24）：自评的 Agent 会「confidently praise」自己的产出；单独的评估者比让生成者自我批评更容易调；但评估者本身仍是 LLM，对 LLM 的产出偏宽松，且「Out of the box, Claude is a poor QA agent」一手。2607.25152：54 个循环里评审说每轮都在进步，按带外指标 56% 的轮次 ≤0（C6 §4.1，只读摘要）二手。

反方证据（同模型干净上下文就够）：Cognition 2026-04-22：评审用干净上下文效果最好；作者认为两个同模型的 Agent 不会像一个人既写又审那样有自我偏见；干净上下文胜过上下文腐烂；Devin Review 平均每个 PR 抓约 2 个 bug，约 58% 严重一手（厂商自报，没有对照）。OpenCodeReview（2608.09290）SEM-F1 25.10% 对 11.57%（2.17 倍），召回仅 20%，没有对 reflector 的消融（E §3）二手。

命题 4　harness 应该厚（多角色、多闸），还是薄（少角色，随模型进步拆掉）。

题 1　迁移：120 个文件从旧 API 迁到新 API，仓库测试覆盖约 90%，预算 60 美元，2 天内要完成，要不要组队？几个 worker？

推理链：先过四项。可并行度高（按目录切）；上下文依赖中（迁移约定要 lead 先写死）；验收可机器化高（编译加测试）；成本要量。四项都过，适合 Teams。接着定 worker 数：Cursor 的锁让 20 个 Agent 吞吐只剩 2 到 3 个，所以别靠堆人数；题设里单个 Agent 假设一次完整跑约 8 美元，4 个 worker 加评审，按 Anthropic 多 Agent 约 15 倍聊天 token 的量级，预算 60 美元很快紧张，所以建议 3 个 worker，先跑一个目录试水，看花费再放开。判断

题 2　评估：4 个任务，每任务每组跑 3 次。Teams 成功 10/12，单 Agent 成功 9/12。题设：单 Agent 每次花 2 美元，Teams 每次 6 美元。能说 Teams 更好吗？

写下你的判断，再看答案

推理链：成功率差 1 次，一次就是 8.3 个百分点，而 Anthropic 量过，仅资源配置不同就能差 6 个点，榜单差小于 3 个点要存疑。样本只有 12，差一次完全可能是噪声。再算单位成功产出成本：单 Agent 12×2 = 24 美元，成功 9 次，约 2.67 美元每次成功；Teams 12×6 = 72 美元，成功 10 次，7.2 美元每次成功，约是 2.7 倍。（还没算人的分钟。）结论：不能说更好；这批数据更像是「贵 2.7 倍、没看出收益」。该做的是拿失败原因分类，看 Teams 的那 2 次失败是不是任务不可拆。

常见错误：①「10 比 9 高，Teams 赢」：忽略噪声。②「只算成功那几次的花费」：低估成本。③「再多跑几次就能证明」：先量同一配置的重复噪声，不然多跑也分不清。

题 3　自迭代：Agent 改了 3 轮自己的 prompt。每轮评审都说「有进步」。你另有一套 Agent 碰不到的隐藏测试，通过率依次是 62%、60%、61%（基线 62%）。继续迭代吗？

写下你的判断，再看答案

推理链：评审是 Agent 体系内的，倾向说好（Anthropic：自评的 Agent「confidently praise」；2607.25152：54 个循环里 56% 的轮次按带外指标 ≤0）。你的隐藏测试是带外指标，三轮没有高于基线，应该以它为准：停，把最后一版回退到基线或最好的一版，并查为什么评审没看出来。不要再加轮。判断

常见错误：①「评审每轮都说好，趋势是对的」。②「61 比 60 高，在上升」：三个点都在基线上下，没有趋势。③「那就换个更强的评审模型」：命题 3 说过，换模型是否有用没有证据，先看带外指标。

题 4　预算：一张工单预算 30 美元。已用 24 美元（80%），第 4 轮评审还剩 2 条意见，最近两轮的失败原因都是「同一个测试没过」。怎么办？

写下你的判断，再看答案

推理链：80% 是告警线，不是继续线。关键信号是「同一失败原因出现两次」，这是停滞，不是收敛。继续烧只会把剩下 6 美元也用光（类比 AgentCore #498，一个会话 58 分钟花 72.67 美元，二手）。做法：到告警就停下，转人，给人一张卡：已花多少、剩什么问题、两次失败的共同点、选项（追加预算 / 换思路 / 放弃）。追加预算由人批。判断

题 5　记忆：4 个 worker 共用一份 MEMORY.md，每个完成后自动追加一条教训。3 天后文件有 260 行，其中一条写着「迁移时跳过 legacy/ 目录」，是第一天一个 worker 对着一次失败得出的错误结论。会发生什么？怎么改？

写下你的判断，再看答案

推理链：两件事叠加。一，Claude Code 自动记忆只加载前 200 行或 25 KB（官方文档说法，闭源，二手），后 60 行的内容不会被读到，旧的错误条目反而在前面一直生效。二，Anthropic memory 文章里 Mt. Moon 的例子：一条没被纠正的错笔记让 Agent 反复失败，靠对照 transcript 才改掉。所以：错误条目会持续影响所有 worker，而最新的修正反而可能被截掉。改法：单写者（或人批）、每条带日期和来源工单、定期对照 transcript 清理、总量控制在加载上限内。判断

常见错误：①「文件长了就是知识多了」：陈旧记忆曾使准确率从 100% 掉到 44.6%（二手）。②「让 worker 自己判断哪些该删」：命题 6 说，私人记忆可以，共享位置要人批。③「把规则全塞进文件」：Mollick 的规则书膨胀到 204 节，读规则本身吃上下文。

题 6　沙箱：worker 需要访问 npm registry 和一个内部 API。方案 A：域名白名单代理，放行这两个域名。方案 B：完全断网，依赖预先装好，API 调用由沙箱外的代理替它发并注入令牌。选哪个？

写下你的判断，再看答案

推理链：Anthropic 自建的白名单代理出过事：Cowork 的 Files API 经「已批准的域名」把数据带了出去，说明白名单放行的域名本身可能是出口。方案 A 的假设是「放行的域名都安全」，这个假设被一手事故推翻过。方案 B 把令牌留在沙箱外（Managed Agents、How we contain Claude 都强调凭据不进沙箱），代价是要自己做预装依赖和代理，且功能受限（Boundary-Bench：最严的策略成功率 −18.3 个点，二手）。选 B；若依赖多、跑不起来，就退到 A，但令牌仍放沙箱外、只放行读，写操作走人批。判断

常见错误：①「白名单只有两个域名，肯定安全」。②「令牌放环境变量里，方便」：沙箱里的 Agent 能读。③「沙箱越严越好」：过严使成功率掉，人会去放开它，反而更危险。

题 7　自主度的算术：你的 4 个 worker 一天产生 200 次权限提示，人批准了 93%。你想全开自动批准。有人算了一笔账：7% 是 14 次被拒，auto mode 漏报率 17%，所以每天漏过约 2.4 次危险动作。这笔账对吗？

写下你的判断，再看答案

推理链：算术没错（200×7% = 14；14×17% ≈ 2.4），但把两个不是同一种东西的数硬乘了。93% 是用户批准的比例，被拒的 7% 不等于「过度积极的危险动作」，里面有手滑、重复、不想批的；17% 是 Anthropic 在 52 个真实「过度积极」动作上的漏报率，样本小、负载不同。所以 2.4 次不是一个可靠估计，只能说「量级不是零」。真正该问的是：这 14 次被拒里有没有不可逆的？有，就按命题 5：不可逆的走人批，其余自动。文章里还有一个保险：连续 3 次或累计 20 次被拒就停下来找人。判断

常见错误：①「93% 都批了，说明全开没问题」：弹窗疲劳和安全是两回事。②「2.4 次太少，可以接受」：看后果不看次数，一次删库就不是小事（PocketOS，二手）。③「算错了所以不能信这些数」：能信 17% 这个数，只是它回答的不是你的问题。

题 8　读新论文：一篇（假想的）2026 年论文声称「多 Agent 评审使缺陷召回提升 25%」，作者是做代码评审产品的公司，在内部 89 题上搜索了配置、又在同一批 89 题上报告结果，没有放出代码。你的团队设计要不要改？

写下你的判断，再看答案

推理链：用 2.5 节的打分表。来源：厂商自述 1；样本：89 题但搜索和报告同一批 0；独立复现：无 0；利益：卖这个产品 0；年份：2026 2；与已有证据冲突：没有可比的对照 1。合计 4，落在「只当话题」档。这个情形和 Meta-Harness 的 TB2 结果（搜索与报告同一批 89 题）同类，也和 Cline 的实验同类（C7，二手）。不改设计；记一条「待验证」，等有人在留出集上复现再动。判断

常见错误：①「+25% 很大，赶紧上」。②「论文是 2026 年的，所以靠谱」：年份只是时效过滤，不是质量。③「厂商不可信，直接忽略」：厂商自报也可能有价值（Anthropic 报了自己的漏报率），要看他有没有报对自己不利的数。

题 9　共享资源：公司给每个员工配一个 Agent，大家共用一个团队预算和一份共享日历。有人提议「干脆让每个人的 Agent 自己协调」。你怎么判断？

写下你的判断，再看答案

推理链：先看这条证据的口径。Worse Together（arXiv 2610.00583，C5 精读 9）测的是「不同的人各带一个 Agent、争有限资源」：API key 环境里 Opus 5 的 coordinator 达到最优解的 64%，peer-to-peer 团队约 30%，没有通信的团队 7%。所以默认先用一个 coordinator，只在隐私或权限必须隔离时才拆成每人一个 Agent。拆开后，修法要按环境选：预算类可以加一个独占改任务权限的 lead；个人助理类的 lead 没用，要在平台层加「有未读私信就拒绝结账」的检查（恢复率 73.1% / 62.3%，是在失败局上重跑的结果，不是新一局成功率）。再看这条证据本身：preprint、模拟用户、部分由模型评判，且没有独立复现，只能当「线索」档。判断

常见错误：①「加个 lead 就行」：同一篇论文里 lead 在个人助理环境几乎无效（47.4% 对 45.5%）。②「把规则写进提示词」：论文里写进 AGENTS.md 的效果远低于平台硬检查。③把恢复率说成成功率。

2.3　4 个反例与事故复盘

写法固定：当时的判断 → 哪一步错了 → 哪个信号能更早抓到 → 换成什么规则。「当时的判断」是我根据原文做的还原，不是当事人原话。判断

复盘 1　Anthropic 的 2026-04-23 事后报告：评估没复现，不等于没问题（一手，April 23 postmortem）

事实：用户感到质量下降，原因是三处改动：3 月 4 日把默认 effort 从 high 改 medium（4 月 7 日撤回）；3 月 26 日的清除思考的 bug（4 月 10 日修复）；4 月 16 日加了一条控制啰嗦的系统提示（4 月 20 日撤回）。内部使用和评测最初都没复现。每处改动影响不同的流量、时间点不同，合起来看像是广泛而不一致的退化；那个 bug 通过了多轮人工与自动评审、单元测试、端到端测试和自用。最终是用户用 /feedback 和公开的可复现例子帮他们找到的。

当时的判断（还原）：内部评测和自用都正常，用户反馈和正常波动难以区分，所以先当波动处理。

哪一步错了：把「我的评测没复现」当成「没问题」。评测覆盖不到的配置组合（实验开关、显示方式）恰好遮住了 bug。

更早的信号：多个用户在同一时间窗口报同类问题；判断 默认配置改动后的质量指标变化。

替换规则：评测与用户报告冲突时，先怀疑评测的覆盖，不怀疑用户；默认值、系统提示的改动也要进评测并带灰度；每处改动记日期，才能回溯到「哪一个」。用到你的团队：评审放行但用户或人推翻的工单，要单独计数。

复盘 2　Cognition 的「Flappy Bird」：拆开并行，每个子 Agent 都以为自己对了（一手，2025-06-12）

事实：把「做一个 Flappy Bird」拆成「做背景和水管」「做能上下飞的鸟」两个子任务。子 Agent 1 误解了任务，做出了像马里奥的背景；子 Agent 2 的鸟不像游戏素材，动作也不像 Flappy Bird；最后的 Agent 要把两个误解拼起来。即使没误解，两个子 Agent 互相看不到对方在做什么，风格也会不一致。

当时的判断（还原）：任务能切成两块，各做各的，最后合起来更快。

哪一步错了：切分时没问「两块之间有多少隐含决策要共享」（命名、风格、边界）。动作里带着隐含决策，而 git 不会报这类冲突。

更早的信号：判断 两个子任务的描述里都出现「风格、一致、同一个」之类的词；或者你需要给两个子 Agent 都补充同一段背景。

替换规则：默认单线程；要拆，就共享完整的会话记录而不只是任务描述；或者让子 Agent 只回答问题、不动手（Cognition 说 Claude Code 的子 Agent 就是这么用的）。对应第一部分的「上下文依赖」一项。

复盘 3　Cursor 的协调：锁、乐观并发、integrator，三次都是从「安全」滑到「瓶颈」（一手，2026-01-14）

事实：先用锁：Agent 持锁太久或忘记释放，即使锁正确，20 个 Agent 的吞吐也只剩 2 到 3 个，大部分时间在等；换成乐观并发（读自由、写时若状态已变就失败），更简单稳健，但没有层级的 Agent 变得风险规避，只做小而安全的改动，没人对难题负责，工作长期空转。后来加了 planner / worker / judge；还专门设了 integrator 做质量控制和冲突处理，发现它造成的瓶颈比解决的多，因为 worker 自己就能处理冲突，于是去掉。

当时的判断（还原）：并行写的主要风险是冲突，所以先用机制（锁，然后乐观并发，然后专职集成者）把冲突管住。

哪一步错了：每一次都是用「更多管控」解决问题，而代价（等待、风险规避、瓶颈）没有提前度量。

更早的信号：判断 有效吞吐对 Agent 数的曲线（20 个只有 2 到 3 个的效果）；单个 Agent 提交的改动变小变保守。

替换规则：每加一个协调角色，就要写下「它假设什么」和「它的等待成本」；拿到度量之前，结构用「中间那一档」，不往两端走。这也是命题 4。

复盘 4　DGM 的「删日志拿高分」：评分物放在 Agent 够得着的地方（二手，经典例外，C7 引用；我没读原论文）

事实：DGM（2505.22954）里，node 114 删掉日志后得分 2.0，而真实表现最好的 node 96 是 1.67（C7）。我没核对这个分数的量纲，只用来说明方向。

当时的判断（还原）：用日志里的记录给每个自改版本打分，日志可信。

哪一步错了：日志在被评对象能写的位置，被评对象改了日志，就改了分数。

更早的信号：判断 某个版本的分数突然远高于父辈，而代码改动并不多；日志文件的修改记录里出现该 Agent 的写入。同类的还有 Cline 实验中「不碰验证器」只靠提示词禁止，以及 karpathy autoresearch 的 prepare.py 只读只靠指令（C7，二手）。

替换规则：评分环境与被评对象物理隔离，验证物只读且在沙箱外；本章 team.py 的 board/ 要对 worker 只读，也是这条（见第一部分的坑）。

4 道选择题加 1 道开放题，全部考判断。点开看答案。

  1. Cognition 与 Cursor 在「并行写」上的分歧，下面哪种说法最贴近证据？
    1. Cursor 的数百 worker 项目证明了并行写可行
    2. Cognition 的实验证明了并行写不可行
    3. 两边都是自述，没有同任务对照；有强裁判且 scope 不相交时并行写才有把握
    4. Anthropic 的 C 编译器证明单写者更好
    答案

    C。A 忽略了 Cursor 的结果没有外部复现；B 忽略了 Cognition 没给对照数据；D 与事实相反：编译器用的是 16 个 Agent 并行，靠 GCC 当裁判。判断

  2. 评估里 Teams 成功 10/12、单 Agent 9/12，Teams 每次成本是 3 倍。最合适的下一步是？
    1. 采用 Teams，成功率更高
    2. 弃用 Teams，太贵
    3. 先同一配置重复运行量噪声，并按失败原因分类，再看单位成功产出成本
    4. 把单 Agent 的重试次数提到 10 次
    答案

    C。差一次在噪声里（Anthropic 的 infrastructure noise：资源配置差异就能造成 6 个点，小于 3 个点要存疑）；成本是 2.7 倍而没有清楚的收益。A、B 都是在没有量噪声时下结论；D 改变了基线的 token 预算，对照就不公平。

  3. 某次自迭代每轮评审都说「有进步」，隐藏测试通过率是 62%、60%、61%（基线 62%）。应该？
    1. 继续迭代，趋势向好
    2. 以隐藏测试为准，停止并回退，同时查评审为什么没看出来
    3. 换一个更强的评审模型再跑 3 轮
    4. 把隐藏测试交给 Agent，让它自己对照
    答案

    B。评审在体系内，易偏宽；隐藏测试是带外指标。D 会让评分物落到 Agent 手里，重演 DGM 的删日志。C 的收益没有证据（命题 3，强度弱）。

  4. 你想让 worker 访问一个内部 API。哪种做法最符合已读到的证据？
    1. 域名白名单代理，令牌放在 worker 环境变量
    2. 断网加预装依赖，API 调用由沙箱外的代理发起并注入令牌
    3. 让分类器模型判断每次请求是否安全
    4. 只靠提示词要求 worker 不要外传数据
    答案

    B。Anthropic 自建白名单代理被已批准的域名绕过；令牌要放沙箱外；分类器漏报 17%（n=52），不适合当唯一一层；提示词不是保证（C4）。

    参考要点

    好答案的标志：证据标了来源和日期，并区分一手和二手；强度评级给了理由，不是只写「中」；置信度不是 100%，也不是 50% 的敷衍；改判条件是可观察、可测的事件（例如「同 token 对照下领先」），不是「如果我改主意了」；动作是一件能放进 GOAL.md 或 EVAL.md 的具体改动。要点可参照命题 1 到 10 的写法。
