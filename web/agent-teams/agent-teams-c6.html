1　交接物：让一个失忆的新会话知道现场在哪

起点：什么都不留会怎样

长任务一个会话做不完，上下文会满。新会话开始时，它的脑子里什么都没有，只有仓库里留下的文件。Anthropic 的比喻是轮班制：新来的工程师对上一班做了什么一无所知 一手（读原文）。如果上一班什么都没留，新会话只有两条路：重新摸索，或者看到一堆半成品就宣布「差不多做完了」。

官方把这两种坏结果都写成了问题：一种是想一口气做完全部（one-shot），做到一半上下文用光，留下半成品；另一种是后来的会话看到已有进展，直接宣布完成 一手（读原文：一次做太多、过早判定项目完成，是它点名的两个毛病）。

设计原理：为什么要分两种会话？ 判断

  • 第一个会话要做的事和后面不同：它要把「完成的定义」写下来（功能清单），搭好环境。后面的会话只管一次推进一小块。
  • 分开以后，「做完什么才算完」在最开始就被钉死，后面的会话不能边做边改目标。
  • 代价：清单质量全靠第一个会话；清单错了，后面几十个会话都在错的目标上使劲。

一个反直觉的事实：两个角色只差第一条用户提示

按官方说法，初始化器和干活 Agent 用同一个系统提示、同一套工具，只是第一条用户消息不同 二手（原文只说第一个会话用专用提示词，其余会话各自增量推进；「同一系统提示、同一套工具」那句，抓到的原文里只剩脚注编号，没核到）。我们去读开源样例确认。文件：anthropics/claude-quickstarts 分支 main，autonomous-coding/agent.py，读取日期 2026-11-16。一手

tests_file = project_dir / "feature_list.json"
is_first_run = not tests_file.exists()
...
while True:
    iteration += 1
    if max_iterations and iteration > max_iterations: break

    if is_first_run:
        prompt = get_initializer_prompt()

逐行看：

  1. 「是不是第一次」不是记在内存里，而是看磁盘上有没有 feature_list.json。所以进程崩了重启，也能正确接上（这一点和 C3 的恢复思路一致，细节见 C3）。
  2. 每一轮都 create_client：全新上下文。会话之间没有任何对话历史，只有磁盘。
  3. 初始化提示只用一次，之后一律用干活提示。

坑 1：循环从不检查「是不是全做完了」 一手

读完整个循环，我没有找到「所有 passes 都为 true 就退出」的判断。它只在 max_iterations 到了才停，结尾只是统计数量。意思是：如果不设上限，功能全做完以后它还会继续开新会话，让模型空转或乱改。

另外 progress.py 里统计通过数的函数，遇到 JSON 解析失败或文件不存在，一律返回 (0, 0)。清单文件被写坏了，界面上看起来是「还没创建」。一手

判断 这是样例代码，不是生产代码，作者没打算当产品用。但你抄它的时候要补上这两处：全通过时退出；清单解析失败时报错而不是显示 0。

坑 2：「只用一次」的标志在初始化完成之前就被改成了 False 判断

上面代码里 is_first_run = False 紧跟在取初始化提示之后。但下一轮是否再用初始化提示，其实是由磁盘上有没有 feature_list.json 决定的吗？不是：变量已经是 False，下一轮直接走干活提示。如果初始化会话中途失败、清单没写出来，下一轮会拿着干活提示去读一个不存在的清单。研究文件里的 Codex 版调研也提出了同样的推断 二手。我没有实际跑出这个故障，只是读代码得到的推断。

初始化器的提示词里写了什么

文件：autonomous-coding/prompts/initializer_prompt.md，main，2026-11-16。一手关键几句：

create a file called `feature_list.json` with 200 detailed end-to-end test cases
At least 25 tests MUST have 10+ steps each
IT IS CATASTROPHIC TO REMOVE OR EDIT FEATURES IN FUTURE SESSIONS.

它还要求：写 init.sh（启动环境）；git init 并做第一次提交，提交信息固定为 Initial setup: feature_list.json, init.sh, and project structure；搭项目结构；最后写 claude-progress.txt。

四件交接物各防一种失败：

交接物防什么怎么写才不出事
feature_list.json过早宣布完成；做偏每项带 category、description、steps、passes；passes 初始全 false；后续只许改 passes
claude-progress.txt新会话不知道上次做了什么、卡在哪每个会话结束前写：做了什么、没做完什么、下一步
git 提交半成品把环境搞坏；无法回退每个功能一次提交；开局先看 git log
init.sh每个会话重新摸索怎么启动一条命令起开发环境；新会话开局就跑它

为什么功能清单用 JSON 而不是 Markdown？官方的解释是，模型比较不容易随手改写 JSON，却容易把 Markdown 重写一遍 一手（读原文：原话是模型较不容易不当地改动 JSON）。社区文章也引用了这一点 二手（见 3.2 的 X 长文）。判断：这是个经验性说法，我没找到对照实验。

用户提醒过这块调研薄。我做了补充检索（arXiv 接口两轮、网页搜索两轮），没有找到专门研究「初始化器」设计的论文。能找到的是三类间接证据：

  • Loop Engineering（arXiv 2608.21884）：挖了 36,710 个仓库，找到 217 个带 Agent 循环的。几乎都提交了启动配置，但几乎没人提交状态文件。一手（全文，第 3.2 节细讲）
  • LongHorizon-Harness（arXiv 2608.01964）：把「状态由谁改」做成了规则，见第 4 节。一手
  • 2609.05510：读了全文，它讲的是记忆系统的可靠性运维（N=1），不是引导文件怎么产出，见本章精读补强。一手 2606.20512：只读了摘要。二手

所以本节关于初始化器的结论，主要来自读官方样例的提示词和代码，不是来自对照实验。下面这些是我读源码得到的观察 判断：

  1. 清单由同一个模型一次写出，没有任何校验。200 条里有没有重复、无法验证、范围蔓延的，没人查。
  2. 干活提示第一步用 cat feature_list.json | head -50 看清单，只看前 50 行 一手。清单排在后面的项，新会话开局是看不到的。
  3. 「只许改 passes」靠提示词约束，没有代码拦截。要拦截应该用 Hook（见 C4）或让 harness 校验差异。

坑 3：清单项写得不可判定 判断

「界面好看」「体验流畅」这种项，passes 改成 true 的依据只能是模型的感觉。写清单时每一项要能被机器或截图判对错：「点击新建后，列表第一行出现该标题」可以；「新建很顺畅」不行。

2　启动自检：先确认现场是好的，再动手

起点：不自检会怎样

上一个会话可能留下了一个坏掉的环境：服务起不来、上一个功能其实是坏的但标成了通过。新会话如果不先查，直接在坏地基上加新功能，错误会叠加，越晚发现越难修。

官方样例的开局六步

文件：autonomous-coding/prompts/coding_prompt.md，main，2026-11-16。一手

STEP 1 定位pwd、ls；读 app_spec；head -50 看清单；读 progress；git log --oneline -20；grep 数还有多少 false
STEP 2 起环境运行 init.sh
STEP 3 回归抽查只测 1–2 个「已通过的核心功能」；发现问题就把它改回 false
STEP 4–6 做一个功能选一个未通过的，实现，用浏览器自动化测
STEP 7 改 passes只改这个字段，截图验证后才改
STEP 8–10 收尾提交、更新进度、干净结束

几个细节值得抄：

  • STEP 3 标题就叫 VERIFICATION TEST (CRITICAL!)。意思是：先查旧的，再做新的。发现旧功能坏了，先修它。
  • STEP 6 明确禁止只用 curl 测、禁止用「执行 JS」绕过界面。目的是逼模型走用户真正会走的路径。
  • STEP 7 写的是「只在用截图验证之后才改 passes」。这一条靠模型自觉。

坑 4：只抽查 1–2 个，覆盖不了回归 判断

清单有 200 项，每次开局只复测 1–2 项。第 50 个会话时，前面 49 个会话做的功能，每个被复测到的概率很低。一个旧功能被新改动悄悄弄坏，可能很久才被抽到。

外部证据：LoopsBench（arXiv 2608.00267）在每一种循环配置里都观察到了回归 一手（第 4 节拆解）。

补救：把「全部旧功能的冒烟」做成一条脚本，每个会话开局和结束都自动跑，不靠模型挑哪几个测。成本是会话变慢；好处是回归第一时间现形。

坑 5：自检靠提示词，模型可以跳过 判断

开局六步是写在提示词里的建议。想要「保证」，把它做成代码：启动脚本先跑 init.sh 和冒烟，失败就不进入干活。这和 C4 讲的「建议用文件、保证用 Hook」是同一个道理。

坑 6：原文自己承认的盲区，浏览器自动化看不见原生弹窗 一手

《Effective harnesses》（2025-11-26，读原文）讲到：用 Puppeteer MCP 做端到端测试，Claude 看不到浏览器原生的 alert 弹窗，依赖这类弹窗的功能因此更容易有 bug。它还给了开局套路：先 pwd，再读 git 日志和进度文件，再读功能清单挑最高优先级的未完成项，然后用 init.sh 起开发服务器、走一遍最基本的端到端流程，确认现场没坏才动手。清单里 claude.ai 克隆的例子有 200 多条功能，初始全是「未通过」，提示词里写明「删改测试是不可接受的」。

判断 所以「所有 passes 为真」的前提，是测试手段看得见每一类功能；看不见的那类，要有人工或别的手段补。

第一次干活前，该有一条「基线」

Carlini 的 C 编译器项目（Anthropic 工程博客，2026-02-05，读原文）：16 个 agent 并行，近 2000 个 Claude Code 会话，约 2 周，花费略低于 2 万美元，产出 10 万行 Rust 编译器。一手 他的经验之一是：验证器必须近乎完美，否则 Agent 会很认真地解决错的问题。另一个细节是「时间盲」：模型分不清时间，会花几个小时跑测试，所以测试工具默认带 --fast，只随机抽 1% 或 10%，并且对每个 agent 是确定的。一手 对本章的启示：判断 自检本身也要有预算，全量冒烟太慢就抽样，但抽样的方式要由代码决定，不要让模型挑。

3　循环与停止条件：谁说「停」

起点：没有停止条件会怎样

最简单的长任务循环只有一行：

while true; do claude -p "$(cat PROMPT.md)"; done

这是 Huntley 的 Ralph 技巧的最简形态 二手。每一轮都是新上下文，记忆全靠磁盘文件。它出乎意料地好用，也没有任何停止办法：没有检查，没有反馈，只有账单会让它停下。

3.1　对比：四种停止条件

做法谁判断「做完」上下文主要风险
Huntley 原版 Ralph（bash 循环）没有；人看着或设轮数每轮全新空转烧钱
官方 ralph-loop 插件（Stop hook）模型自己输出 <promise>…</promise>，脚本按字面比对同一会话，上下文持续累积自报完成；上下文变长
Claude Code /goal一个小模型（默认 Haiku）读对话，不调用工具，不读文件同一会话只能判断对话里已经出现的东西
自写脚本（check 脚本 + 熔断）脚本，退出码每轮全新check 写错或可被模型改

第二行有一个常见的误解要说清：官方的 ralph-loop 插件不是 Huntley 原版那种「每轮全新上下文」，它是靠 Stop hook 把模型拦在同一个会话里继续做，上下文会越积越多 一手（下面读源码）。

坑 6：完成标记靠自报，也就是「自评」 判断

Stop hook 这个机制本身是好的：它是代码，模型绕不过去。但「什么算完成」这一半交给了模型：它只要在回复里写出那段标记，就退出。你把这个循环用在「测试全绿」这种有客观判据的任务上，应当把标记的输出条件绑定到检查脚本的结果（先跑脚本，脚本通过才允许输出标记），而不是让模型凭感觉。

/goal：用小模型当评审，边界要看清

Claude Code 的 /goal 文档（读自 code.claude.com，2026-11-16，已对原文核对「条件上限 4,000 字符」「小模型评审不调用工具」「默认 Haiku 一档的小快模型，可用环境变量换」）：每一轮结束后，由一个小模型（默认 Haiku）根据你写的条件判断是否达成；这个评审不调用工具、不读文件，只能看对话里已经出现的内容。条件上限 4,000 字符，可以写进「或者最多 20 轮后停」。二手（Claude Code 闭源，文档是转述级别的来源）

因此条件要写成「对话里能看到证据」的样子：

# 对话里没有证据，评审无从判断
/goal the auth code is correct

# 对话里有证据（测试输出、git status）
/goal npm test exits 0 for test/auth, no existing test file is modified,
git status is clean. Or stop after 20 turns.

以上写法引自 X 长文（见 3.2），二手。

Stop hook 还有一个保险：连续拦截 8 次、中间模型没有任何工具调用，Claude Code 会强制放行；上限可以用环境变量 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP 调整，脚本里应当检查 stop_hook_active 避免死循环。一手（读自 hooks-guide 文档原文，但文档描述的是闭源程序的行为，所以行为本身是二手）

4　「做完了」谁来判：自评偏宽的证据

起点：让做事的模型自己判断做没做完

最省事的办法是让干活的 Agent 自己说「完成」。第 1、3 节里的两套机制都部分如此：改 passes 的是干活会话，输出完成标记的也是它。这一节看这样做有多大风险，以及业界怎么补。

4.1　论文拆解：「进展幻象」（arXiv 2607.25152）

怎么测的：让 Agent 在多个「循环」里反复改进同一个产物，每轮结束让一个评审判断是否变好，再用带外的、有依据的指标（对产物实际打分）测真实变化。

测到什么：54 个循环里，Agent 自己声称每一轮都有改进（54 轮全部）；但按真实指标测，56% 的轮次其实 ≤0；采用自评闸门的那一组，部署状态从峰值 95.0 退到 76.7（约 19%）。最强的「带内评审」放行的轮次里，44% 是真实退步；它还拒绝了约 38% 的真实改进。当任务的产物可以被客观验证时，这个幻象消失。只给符号反馈（变好/变差）的得分 110.0，给完整反馈 113.0。结论是：必须有带外的、有依据的评估。一手（后来读到了全文，数字已按表 1 核对，详见本章「精读补强」）

能信多少：样本是 9 次运行共 54 个循环，3 次重复，一个任务族、一个 Agent 模型，论文自己标注为 pilot 和 preliminary draft；out-of-band 的幻象率 0 是定义的结果。方向上与下面几篇一致，但具体百分比别当作行业常数。

4.5　Anthropic 的规划–生成–评估，以及「上下文焦虑」

下面读自《Harness design for long-running apps》原文（2026-03-24）。文章先点了两个毛病：一是上下文变满，模型就丢连贯性；二是有的模型有「上下文焦虑」，快到它以为的窗口上限就提前收工。解法之一是上下文重置（清空窗口、靠交接物换新 Agent），它和压缩不同：压缩留着旧历史，焦虑可能还在；重置给干净的开始，代价是交接物要写够。一手

第二个毛病是自评偏宽：让同一个模型评自己的作品，它会夸；单独拿一个评估者来调，比让生成者自我批评容易得多。一手

三个角色各管什么

规划者：把 1 到 4 句的需求扩成产品规格，只写高层，不写实现细节，免得细节写错连累后面；并把 AI 功能织进去。例子：一句话需求被扩成 16 个功能、10 个 sprint。没有规划者，生成者会把范围做小。一手

生成者：按 sprint 做（React、Vite、FastAPI、SQLite 的栈）。每个 sprint 开写之前，生成者和评估者先通过文件协商一份「sprint contract」，写明什么算做完；其中一个 sprint 谈出了 27 条标准。一手

评估者：用 Playwright MCP 真去点页面，对每条标准设硬阈值，一条不过就退回。原文直说：开箱即用的 Claude 是个很差的 QA，会说服自己「这个 bug 不严重」，只做表面测试。调法是读评估者的日志，找它判断和你不一致的地方，改提示词，反复几轮。一手

前端设计任务用四条评分标准：设计质量、原创性、工艺、功能，前两条权重更高。跑 5 到 15 轮迭代，最长约 4 小时；荷兰博物馆网站的例子里，第 10 轮网站变成了一个 3D 房间。一手

6　一个场景走一遍

场景：你要让 Agent 花一晚上，把一个旧后台的 40 个页面迁到新框架。

1 初始化会话列 40 个页面的清单；每项写成「打开该页，能看到哪几个元素，能做哪几个操作」；passes 全 false；写 init.sh 和冒烟脚本；第一次提交
2 你审一次清单这是整套里最值钱的一次人工，清单错了后面都白干
3 干活会话开局脚本自动跑 init.sh 和全部已通过页面的冒烟，失败则先修；不靠模型选
4 做一个页面实现、用浏览器真点、截图存档；脚本把截图和断言结果追加到证据文件
5 改状态由脚本在证据齐全时把 passes 改成 true，模型只提交「我认为完成」
6 收尾提交、写进度、写 tried（试过什么）；同一失败两次出现就停下找人

这条流程里，每一处「靠模型自觉」的环节都被换成了代码：自检（3）、改状态（5）、停止（6）。事件日志、崩溃后接着跑的细节见 C3。

7　判断与方向

  • 判断 交接物的内容不难，难点在于谁写、谁改、谁验。凡是「只许改某字段」的规则，用代码或 Hook 拦；提示词里的大写警告只是愿望。
  • 判断 初始化器是最杠杆的一步，也是证据最薄的一步。目前没有论文专门测它。你用的时候，把「清单审核」当成必须的人工环节。
  • 判断 停止条件要同时有三种：成功（检查通过）、预算（轮数或金额）、停滞（重复失败）。样例代码只有预算一种，Ralph 插件只有自报一种。
  • 判断 趋势：模型变强后，重置、切分这类结构可以减；独立评估这层没人敢减。
  • 开放问题：没找到专门研究初始化器设计的论文；没找到「回归抽查比例」的剂量曲线；主观标准的自动评审没有可靠方案。

auditor 只审最近的子任务（manager.py 第 778 行附近的注释）。若最后一次干净的报告对应的子任务不是整个原始需求，manager 只能再安排一个可审计的子任务，不能直接宣布完成。读源码时要看清它「找最近一份有效报告」而不是「汇总所有报告」。
