1　控制面：Agent 是一种要登记、要有主人的资产

起点：不登记会怎样

一个团队起初只有两三个 Agent，写在各自的脚本里。半年后有三十个，有的在 cron 上，有的在别人的笔记本上。出事时没人说得清：这个 Agent 谁写的？现在是哪个版本？它能碰哪些系统？

优化方向：当资产管

做法和管服务一样：每个 Agent 有 ID、版本、Owner、发布记录，上线前要过审批，下线要有人确认。OTel 的 Agent span 规范里已经有对应字段：gen_ai.agent.id、gen_ai.agent.name、gen_ai.agent.version（例如 1.0.0 或 2025-05-01）。一手 来源见第 4 节。

方案管什么我读到的程度
Paperclipcompany → agent → run；每个 agent 有月预算、审批、暂停读了 budgets.ts、agent-auth-jwt.ts 和文档 一手
Google Agent Registry / Agent Identity注册、发现、身份（SPIFFE，X.509 有效期 24h）只有调研文件转述 二手
Microsoft Agent 365Agent 的目录与治理；GA 日期各来源不一致（2026-05-01 一说）只有调研文件转述 二手
2607.00345 Registry-Governed Agent Lifecycle用 Registry 管 Agent 的整个生命周期下载了全文，本章没细读，只引题目和方向 二手

坑：版本字段有，但没人填。判断 OTel 规范里 gen_ai.agent.version 是可选字段。框架默认不会替你填。结果是 trace 里能看到「哪个 Agent」，看不到「哪一版」，回归问题没法对上发布记录。解决办法：把版本号放在 Agent 定义文件里，由发布流水线写入，启动时统一注入。

关联：Agent 能碰哪些工具、需不需要人批，是 C2 的内容；这里只管「谁是谁、归谁」。

2　身份与委托授权：Agent 以谁的名义做事

起点：一个长期 token 走天下

最省事的做法：把人的 API key 放进环境变量，所有 Agent 共用。问题有三个。第一，key 泄露，谁都能用。第二，日志里全是「用户 X」，分不出是人还是哪个 Agent 干的。第三，Agent 把任务转给子 Agent 时，权限只会原样传下去，不会变小。

2.1　Paperclip：每次 run 一个令牌，且带「谁授权的」

源码 server/src/agent-auth-jwt.ts（paperclipai/paperclip，master，2026-11-16 读）。一手 令牌里的字段：

interface LocalAgentJwtClaims {
  sub: string;            // agent id
  company_id: string;
  adapter_type: string;
  run_id: string;
  responsible_user_id?: string;
  authorizing_user_id?: string;
  key_scope?: ...;
  iat: number; exp: number;
  iss?: string; aud?: string;
  instance_id?: string; jti?: string;
}

我的读法：run_id 让每条令牌只属于一次运行；responsible_user_id 和 authorizing_user_id 把「哪个人负责、哪个人授权」带进令牌。算法是 HS256。默认有效期是 48 小时，源码注释的理由是：令牌在适配器启动时签一次、以环境变量注入，所以有效期必须盖住整次运行，包括笔记本合盖的空档。一手

更正：本地调研文件把它写成「短期令牌」。源码默认是 48 小时，并不短。它的安全性不靠短，而靠下面这个签名密钥的派生方式。

function deriveCompanySigningKey(masterSecret: string, companyId: string, instanceId: string): string {
  return createHmac("sha256", masterSecret).update(`jwt:${instanceId}:${companyId}`).digest("hex");
}

每个公司、每个实例各有一把派生密钥。公司 A 的令牌验不过公司 B。fork 出来的实例或 worktree 的令牌验不过正式实例（源码注释引用了事故编号 PAP-12896）。jwt: 前缀用来做域分隔。旧的主密钥验证作为兼容后备保留，设置 PAPERCLIP_AGENT_JWT_DISABLE_LEGACY_FALLBACK=true 可关掉。一手

判断 这是「隔离靠密钥派生，不靠寿命」的做法：令牌拿到手后，只能在签发它的那个公司和实例里用。代价是 48 小时窗口内一旦泄露，就只能等过期或轮换主密钥。

入口。文件 server/src/agent-auth-jwt.ts（paperclipai/paperclip，master，2026-11-16，271 行，通读）。签发是 createLocalAgentJwt(agentId, companyId, adapterType, runId, responsibleUserId, keyScope, authorizingUserId)，验证是 verifyLocalAgentJwt(token, { strictRunAuthority })。谁在 HTTP 中间件里调用它们，我没读。一手

设计取舍。

  • 验证前先读未验证的 company_id 来选密钥。伪造它只会算出另一把密钥，签名对不上，所以这个「先读后验」是安全的。判断

  • strictRunAuthority 是给「跨实例检查某个 run 此刻是否还被授权」用的严格模式：关掉旧密钥后备，要求 typ、iss、aud、instance_id 全对，iat 不在未来，key_scope 若存在必须是 standard。一手

坑：旧主密钥后备默认是开着的。disableLegacyFallback 来自环境变量 PAPERCLIP_AGENT_JWT_DISABLE_LEGACY_FALLBACK，缺省解析为 false。也就是说默认情况下，直接用主密钥签的令牌对任何公司都有效。源码注释要求运营者在部署后约一个 TTL（48 小时）把它设成 true。没设的部署，主密钥一泄露，攻击者能给任意公司签任意 exp 的令牌，派生密钥的隔离就白做了。一手（读到的是代码和注释，没有看任何一个真实部署的配置）

2.2　AgentCore：身份令牌随请求进来，不进模型上下文

文件 bedrock_agentcore/runtime/app.py（aws/bedrock-agentcore-sdk-python，main，2026-11-16 读）。一手 运行时暴露 POST /invocations、GET /ping 和 WebSocket /ws。_build_request_context 从请求头读 request_id、session_id 和 agent_identity_token，再调用 BedrockAgentCoreContext.set_workload_access_token(...) 存进运行时上下文；Authorization 头单独规范化，其余头走白名单。

另外 /ping 的状态按「强制设置 > 自定义处理器 > 自动」排序；自动模式下有活跃任务就报 HEALTHY_BUSY，否则 HEALTHY。同一个文件里 _ensure_worker_loop 用单独的事件循环跑 handler，避免阻塞的 async handler 把 /ping 卡住。一手

判断 这里值得学的是分工：令牌由平台在请求入口注入，代码从上下文取，不经过 prompt。模型看不到它，也就没法被诱导念出来。具体怎么在沙箱里隔凭据，见 C2。

2.3　论文拆解：Delegation Without Trust（arXiv 2609.00267）

谁写的、什么日期。VotalAI 的 Dantuluri 和 Sundi，cs.CR，2026-08-31。作者是商业公司员工，这是利益相关点。一手（读了全文，数学公式里的数字在转文本时丢了，下面只用正文里的数。）

怎么测的。先定「不信任模型」的前提：模型可能被提示注入，所以授权不能靠模型自觉。列四类威胁：T1 confused deputy、T2 令牌被盗重放、T3 提示注入导致权限升级、T4 子 Agent 被攻陷。再提 8 条要求：

编号要求编号要求
R1委托链完整性R5轮换
R2最小权限逐级收窄（attenuation）R6撤销沿链传播
R3凭据绑定发送方R7防篡改审计
R4短期签发R8不依赖模型的强制执行（关键）

然后用这 8 条检查框架。LangGraph 1.2.10 是真跑了一个脚本化的 agent 节点；CrewAI 1.15.13 和 AutoGen 0.7.5 是读代码看有没有这些能力；MCP 授权规范 2026-07-28 是读规范。一手

测到什么。LangGraph、CrewAI、AutoGen 三个都没有 R1–R8 中的任何一条；MCP 只覆盖一部分：按 Table 2，R4 完整，R1、R3、R5、R6、R8 是部分，R2（逐级收窄）和 R7（防篡改审计）没有；靠 RFC 8707 有受众限制，但没有 Agent 之间的来源链。默认运行方式（一个宽泛的 bearer 凭据，靠模型把关）对四类威胁全部失守。一手

作者自己做了一个 broker：160 行 Python，只用标准库，macaroon 风格的 HMAC 令牌（只能追加限制条件），绑定 SPIFFE 风格的 SVID，每一跳由签发方做令牌交换，防篡改日志，撤销沿链向下传。结果：自己设计里的 11 种直接攻击都被挡住；20 万个模糊测试令牌一个都没被接受；在 2000 个随机场景、8100 个动作的合成环境里，平均爆炸半径是 1.5 个可达动作，对照 bearer 委托是全部 8100 个；授权耗时 2.6 µs，令牌交换 5.4 µs（10 万次调用，笔记本）。边界测试也写了：攻击者若能出示受害者的 SVID，被盗令牌照样能用。一手

能信多少。判断 方向可信：「权限只能逐级变小」比「发一个短令牌」更根本。数字要打折：环境是合成的、动作模型是抽象的、broker 没开源也没接进被测框架、微秒级耗时只是令牌运算，不含网络。框架结论只对被钉住的版本成立。

文中引的相关工作（二手）：Zhou 等人对 7973 个在线远程 MCP server 做了测量（即 2605.22333），发现超过 40% 的 server 暴露无需认证的工具，119 个启用 OAuth 的 server 每个至少有一处缺陷。我只经 2609.00267 的转述看到，未读原文。

2.3 精读：Delegation Without Trust（arXiv 2609.00267，全文）

一句话。在「模型随时可能被注入」的前提下，Agent 委托链需要满足哪 8 条要求，现有框架满足几条，一个很小的 broker 能不能把它们补上。一手

方法（Fig. 1）。

1 根人的 OIDC 身份，签出根能力令牌
2 每一跳签发方做令牌交换，新令牌能力 ⊆ 旧令牌（cap2 ⊆ cap1），绑定 SPIFFE 风格 SVID，寿命短
3 每次工具调用经过 broker，验签名、查撤销、查发送方绑定、算 caveat，全程不调模型

令牌是 macaroon 风格：只能追加限制条件，不能删。被劫持的 Agent 只能使用它手里那份已收窄的授权。

怎么测的（Sec. 5 和 7.3）。两部分。第一部分是现状检查：LangGraph 1.2.10 真跑了一个脚本化的 agent 节点，目的是把授权层和模型行为分开；CrewAI 1.15.13、AutoGen 0.7.5 读工具执行基类的代码；MCP 授权规范 2026-07-28 读规范。第二部分是自己的 broker：四种对手，一套自己攻击自己设计的测试，一个合成的爆炸半径实验，一组微基准。

文件 server/src/services/budgets.ts（paperclipai/paperclip，master，2026-11-16 读，约 69KB）。先看状态判断：

function budgetStatusFromObserved(observedAmount: string, amount: number, warnPercent: number): BudgetPolicySummary["status"] {
  if (amount <= 0) return "ok";
  if (compareCents(observedAmount, amount) >= 0) return "hard_stop";
  if (compareCents(observedAmount, Math.ceil((amount * warnPercent) / 100)) >= 0) return "warning";
  return "ok";
}

三态：ok、warning、hard_stop。amount <= 0 直接当 ok，也就是「预算设成 0 等于不设上限」。判断 这一点容易误踩：想「冻结」某个 Agent，应该用暂停，不要把预算设 0。

再看什么算「真停」，以及「没有价格的用量」怎么处理：

function unpricedUsageBlocks(policy: PolicyRow, observed: ObservedSpend) {
  return policy.unpricedUsagePolicy !== "allow"
    && (observed.unpricedEventCount > 0 || observed.unknownBrowserRunCount > 0);
}
/** Spend reached the limit, or the operator blocks unpriced usage. Only this
 * opens a hard-stop incident, pauses a scope, or stops running work. */
function hardStopReached(policy: PolicyRow, observed: ...) {
  if (!policy.isActive || !policy.hardStopEnabled || policy.amount <= 0) return false;
  return compareCents(observed.totalExact, policy.amount) >= 0 || unpricedUsageBlocks(policy, observed);
}

我的读法：硬停有三个开关（策略启用、hardStopEnabled、金额大于 0），三者缺一都不停。更有意思的是第二个条件：运营者可以规定「出现没法算价的用量就当超支」。新模型上线、价格表还没更新时，这条能防止账面上花了钱却记成 0。一手

准入检查 recheckAdmittedRunBudgetReadOnly（约 270 行）：先确认 budgetReservations 里有一条 held 的预留，再重读策略（是否启用、是否硬停、指标是否 billed_cents、金额是否大于 0），再算当前花费。如果 hardStopReached，返回「Applicable budget no longer permits provider work」。如果 ledgerCents + effectiveHeldCents 超过策略金额，返回「Available budget is reserved by unfinished runs」。注释写明：这个函数只读，不抢公司锁；之后并发产生的新花费，走另一条持久的 Stop 路径。一手

约 700 行的准入：到硬停就调用 createIncidentIfNeeded(policy,"hard",observed) 和 pauseAndCancelScopeForBudget，返回拒绝原因；否则把已开的软、硬 incident 关掉。注释说：自然月窗口过期、策略停用或预算调高时，只会解除「预算造成的暂停」；人手动暂停的不会被自动恢复。一手

设计原理：为什么是「预留 + 硬停」两层？判断

  • 只有硬停：花完才知道，并发的 run 会一起冲过线。
  • 预留（reservation）：run 开始前先占额度，没占到就不开跑，解决并发超支。
  • 软告警：给人一个提前量，不必等到停。
  • 人暂停和预算暂停分开记，所以「预算恢复」不会把人故意停掉的 Agent 放出来。
  • 代价：只读的复查和并发之间有窗口，所以仍要靠事后的 Stop 路径兜底。

坑 1：只统计 token，不统计浏览器和工具。源码里专门有 unknownBrowserRunCount，说明开发者碰到过「浏览器 run 算不出价」。自己做记账时，要给每一种计费来源留「未知」状态，并决定未知算不算超支。判断

坑 2：预算作用域错了。Paperclip 预算按 agent 和 company 两层设。如果只设公司总额，一个循环的 Agent 会吃掉别的 Agent 的额度。判断

坑 3：停了以后没人知道。硬停后 Agent 不再有 heartbeat，看起来像「没事干」。要有 incident 记录和通知，否则同事以为它坏了。Paperclip 用 incident 表来解决。一手（createIncidentIfNeeded 存在）

4.1 精读（规范文档）：OTel 的 agent span 到底要求什么

入口。docs/gen-ai/gen-ai-agent-spans.md（open-telemetry/semantic-conventions-genai，main，2026-11-16，51220 字节，通读到 plan span 之前的部分，后面的 execute_tool 等没细读）。状态：Development。一手

要点和原文约束。

  • 进程内的 agent 调用用 invoke_agent span，kind 是 INTERNAL；远端 agent 服务用 CLIENT kind 的另一个 span。规范写「应该」发出，不是「必须」。
  • gen_ai.operation.name 取值：LLM 驱动控制流用 invoke_agent，应用写死控制流用 invoke_workflow，其他框架入口用 invoke_{framework_entrypoint}。
  • 实现细节不该单独发 span：规范写「SHOULD NOT」，例子是 agent 或工具在内部拉起 runner 或 workflow 来委托子 Agent；而应用自己定义的嵌套 workflow（如子图当节点）应该发。
  • gen_ai.agent.name 必须低基数（MUST）；没有低基数的名字就默认不记（MUST NOT）。
  • gen_ai.conversation.id 没有可用标识时，不应该用请求内容当替代值。
  • gen_ai.usage.input_tokens 应包含缓存 token 和所有模态；output_tokens 应包含推理 token；供应商只给一个汇总数时报计费数。
  • 内容类属性（gen_ai.input.messages、output.messages、system_instructions、tool.definitions）全是 Opt-In，规范警告它们可能含个人信息；各有 _ref 版本，只放外部存储的 URI，且不建议把带签名的查询参数写进 URI。

设计取舍。规范把「内容」和「元数据」拆开：元数据（谁、花了多少 token）默认可记，内容默认不记，要记就推荐放外部存储再引用。这对平台是一个现成的分层：成本和身份走 span 属性，对话原文走受控存储。代价是内容放哪、谁能读，规范只说「用存储自己的访问控制」，不替你定。判断

坑：「规范里写了」不等于「框架里发了」。全文大量是 SHOULD 而不是 MUST，状态还是 Development。换后端前，要用你的框架实际发出的 span 去对一遍：agent.name 有没有高基数值，conversation.id 有没有拿请求内容当替代。我没有对任何一个框架做这件事。判断

精读：A2ABreak（arXiv 2609.10871 v3，全文，已被 ACSAC ’26 接收）

一句话。能不能把 A2A 的自然语言规范自动变成状态机，在「对方完全守规范」的假设下找出协议本身的漏洞。一手

方法。规范 → LLM 抽取并逐条验证形式化语句（929 条）→ 按六个协议阶段各建一个状态机 → 合并成统一模型（37 个状态、76 个转移）→ 在统一模型上让 LLM 做对抗式推理，生成候选漏洞 → 用自己的 C2 检查筛一遍 → 少数用 Alloy 和 TLA+ 形式验证。

怎么测的。对照物是零样本基线：Claude Opus 4.6（高推理）直接读同一份规范，跑 2 次，产出 9 个候选。评价是专家人工审查。

主结果。

  • 11 个新漏洞；精确率 73.3%（15 个不重复候选中 11 个真阳性）；F1 84.6%。
  • 零样本基线的 9 个候选，用同一个 C2 检查全部被拒，所以「确认数 0」。
  • 只有 283 条（30%）语句带转移结构，进入状态机；92% 的缩减是相对 929 条语句算的。
  • 统一状态机在 PSMBench 上的转移精确率 0.318。
  • 只有 3 个发现做了 Alloy 和 TLA+ 的形式验证。

我核对出的问题。

  • 73.3% 是 11/15，由前三位作者自己审查（每人约 15 分钟）。样本小，审查者就是作者，不是独立专家。
  • F1 84.6% 在精确率 73.3% 下意味着召回 100%，原因是召回的分母就是它自己找出来的集合。这是循环定义，不能当作「找全了」。
  • 「零样本 0 个」是同一个 C2 检查把 9 个候选全拒了，不等于零样本什么都没产出。对照也只有一个模型、2 次运行。
  • PSMBench 转移精确率只有 0.318，说明状态机本身并不精确；漏洞推理建立在它上面。
  • 11 个漏洞逐条的可利用性，我没核实，也没在任何 A2A 实现上复现。

讨论。对本章命题「协议只管能通，不管该不该通」支持到：规范层面存在多跳委托身份丢失、不受保护的 context id 这类缺口。支持不到：这些缺口在真实实现里能被利用到什么程度。读这篇时该追问：

  1. 73.3% 换成不是作者的专家审查，会掉多少？
  2. 30% 的语句进状态机，剩下 70% 的约束（没有转移结构）里有没有同样致命的漏洞？
  3. 漏洞和 2609.00267 的 R1、R2 一一对得上吗？如果对得上，是不是同一个问题的两种测法？

5.x　平台层隔离：凭据不进沙箱，令牌按会话发

来源：Anthropic，how-we-contain-claude（2026-05-25）和 managed-agents（2026-04-08），读了全文（本地副本）。一手；都是 Anthropic 自述，没有外部复现。

前几节讲的是「Agent 之外的控制面怎么记账、怎么发身份」。这一节补上控制面下面那层：沙箱本身该怎么搭，才让上面的身份和预算不被绕过。

要点原文怎么做为什么
凭据不进沙箱Cowork：凭据留在宿主钥匙串，VM 里只有每会话的窄权限 token，可单独吊销；Managed Agents：Git 令牌在初始化沙箱时用来克隆仓库并接到本地 remote，之后 push/pull 在沙箱里照常，Agent 不碰令牌凭据根本不在沙箱里，就无法被外泄，不管原因是用户、模型的「创造性」路径还是攻击者
令牌库放在沙箱外自定义工具走 MCP：OAuth 令牌存在安全的 vault；Claude 经专用代理调用，代理收到的是会话相关的令牌，再去 vault 取真凭据发请求，harness 全程不知道凭据早先把执行代码和凭据放同一容器，提示注入只需说服 Claude 读自己的环境变量；攻击者拿到令牌还能自己起新会话并委派任务
文件挂载分档Cowork 提供只读、读写、读写但不能删三档；企业管理员可用 MDM 里的挂载路径白名单管按需给最小权限
先解析符号链接，再校验路径顺序反了，授权目录里的一个符号链接能指到目录外典型的「检查和使用之间」漏洞
白名单是能力授权放行 api.anthropic.com 就等于放行向任意 Anthropic 账号上传文件；修法是只放行带本会话令牌的请求每个放行的域名后面的所有功能都是攻击面

坑：隔离做好了，看不见了。原文：企业安全团队问「为什么我们的 EDR 看不进去」——让 Claude 被关住的隔离，同样把宿主的端点检测挡在外面，EDR 眼里 Cowork 只是一个不透明的 hypervisor 进程。Anthropic 的缓解是拉取式 OTLP 导出，管理员事后取事件日志，但原文明说这不等于实时监控。一手 对应本章第 4 节：隔离越强，越要把「记录由 Agent 之外的东西写」提前设计，别等客户来问。

坑：把子 Agent 的输出当成更可信。原文在「还没解决」里写：子 Agent 可以把不可信内容隔离，只返回结构化事实给主 Agent；但如果它的输出因为「来自我们自己」被当成比原始工具结果更高的信任，就多出一个提示注入入口。多 Agent 里，分档信任和信任升级是一对取舍。一手 判断 这和本章的「委托授权只能变小」是同一件事：信任也只能逐级收，不能因为经过了一层 Agent 就变大。

原文的三条总结，我认为对做平台的人最有用：先在环境层封边界，再在模型层引导；隔离强度要匹配用户的监督能力（会读 bash 的开发者和不会读的知识工作者不是同一个威胁模型）；对自己写的定制组件保持警惕，因为这些案例里经得起考验的都是成熟的 hypervisor、syscall 过滤和容器运行时，出问题的都是自己围着它们写的东西。一手

能信多少，和本章对得上吗：几个对比数字（CI 400 次、评审 331 次、合并队列 45 分钟到 2.9 分钟）有样本量，比纯描述强，但都是卖家在自己环境测的，没有方法细节。放到本章：它的成本控制是靠「选便宜模型加订阅套餐」，不是靠按运行的预算上限和熔断。所以它没有证明本章第 3 节那条原则（刹车不能由 Agent 自己控制），也没有碰上「失控循环」一类的事故。把多个订阅账号放在一个代理登录后面，意味着很难按人或按 Agent 归因用量，这和本章要的「成本记账」方向相反；我没查各家服务条款是否允许这样用。判断 另外，用便宜模型当 Agent 子任务的风险，见 C5 的 2611.17520；这篇用「再让别的 Agent 验证」来缓解，和那篇论文说的「有接地的验证者能打断级联」是同一方向，但这里没有测量。

三篇 X 长文和本章论文之间的缺口 判断

  • X 讲的是「平台应该有什么」：登记、身份分层、语义判定、回放、并行、CI。论文讲的是「出事时哪里漏了」：宽泛的 bearer 凭据对四类威胁全部失守（2609.00267）、参数校验挡不住越权（2609.14780）、Agent 能改自己的 trace（2609.30266）。X 三篇都没有回答这几类漏洞。
  • 成本和遥测是最大空白：三篇里只有一篇给了每月订阅账单，没有一篇给出按运行的预算、熔断或告警去重做法。
  • 用法：搭的时候拿 Uber 的 PAP / PDP / PEP 当检查清单；验的时候拿本章的论文当攻击清单：令牌权限能不能逐级收窄、越权靠参数校验还是靠工具形状、trace 能不能被 Agent 改。

7　判断与方向

  • 判断 底座的核心原则只有一条：该防 Agent 的东西，不能放在 Agent 够得到的地方。预算、身份、日志都适用；2609.30266 给了日志这一条的证据，2609.00267 给了身份，Paperclip 的硬停是预算。
  • 判断 「令牌短」不是答案，「令牌范围小、只能逐级变小、绑定一次运行」才是。Paperclip 的 48 小时 JWT 靠派生密钥隔离，是一种折中，不是理想状态。
  • 判断 OTel GenAI 还在 Development，字段和名字会变。选它是为了不被后端绑死，但要接受升级时改埋点。
  • 判断 本章最薄弱处：告警去重、LangSmith/Braintrust 这类商用后端、Agent 365 和 Google Registry 的一手资料。读者在引用前请回官方文档核对。
