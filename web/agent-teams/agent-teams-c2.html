全景图：四层防线

先说结论：没有哪一层是够用的。命令规则会被绕，审批会被点烦，沙箱会有漏洞，凭据隔离只管凭据。生产里靠的是叠起来。

层谁来拦拦什么典型失效方式
1 命令规则解析器 + 规则（allow / prompt / forbid）明显危险的命令、已知安全的命令免审批黑名单漏项（awk、find -exec）；解析不了的语法
2 审批人，或另一个模型（auto-mode 分类器）规则判不了、需要越过沙箱的动作人点烦了全点「允许」；分类器漏判
3 OS 沙箱内核：Seatbelt / bwrap + seccomp / Landlock进程能读写哪些路径、能不能联网配置过宽（可写 host 挂载）；内核漏洞；网络放行后当通道
4 凭据与出网沙箱外的代理 / 控制面真密钥不进沙箱；出网域名白名单放行域名被当中转；占位符替换不全

主线一句话：前两层是判断，会错；后两层是强制，不靠谁同意。所以安全的底线要放在后两层，前两层只负责少打扰人。这也是 Codex 代码里的态度：危险命令清单很短，只决定「未匹配的命令是问还是禁」，真正的边界是沙箱（下面第 1、3 节有原文）。判断

1　命令解析与规则：先看懂命令，才谈得上判断

1.1 起点：正则匹配

最朴素的做法是对命令字符串写正则。Pi 的官方示例扩展就是这样做的。一手

1.2 优化方向：用语法树，不用正则

Codex 的做法是用 tree-sitter 把 bash 解析成语法树，再按「能不能证明」分成两种解析。一手

解析能接受的语法用途为什么
严格（word-only）只有 program / list / pipeline / command / word / string / number / concatenation，连接符只有 && || ; |证明「安全」遇到变量展开、命令替换、重定向就返回 None，宁可不认
宽松（literal）复杂语法也接受，返回每个命令节点里静态可知的单词只用来找「危险」动态单词和重定向被丢掉，所以不能用来证明安全

原文的注释写得很直白，一句话概括了整个设计：

// returns the statically known words from every command node in a valid syntax tree.

// dangerous literal commands, but must not be used to prove that a command is safe.

// try_parse_word_only_commands_sequence 中（节选）：

const ALLOWED_PUNCT_TOKENS: &[&str] = &["&&", "||", ";", "|", "\"", "'"];

另外，extract_bash_command 只认 [shell, "-lc" 或 "-c", script] 这一种形状。一手不认的形状就当普通命令，不去猜。

设计原理：不对称。「找危险」可以宽松：多找错了只是多问一次人。「证明安全」必须严格：错一次就是事故。所以同一个 shell 脚本走两套解析，宽松的只能往危险方向投票。判断

1.4 规则文件：execpolicy

用户和团队想要「git status 免问」，靠的是 Starlark 写的规则文件，放在 codex_home/rules/default.rules。一手（README 与 decision.rs）

  • prefix_rule(pattern, decision, justification, match, not_match)：按命令前缀匹配。match / not_match 是内嵌的例子，加载时当单元测试校验，规则写错会在加载时就报错。
  • 决策四档：Allow / Prompt / PromptUser / Forbidden。多条规则命中时取最严的。
  • host_executable 与 canonical_matching：处理「同名命令在不同路径」的情况，避免 /tmp/evil/git 冒充 git。

坑 1：规则按「前缀」匹配，就不要给解释器放行。放行 python、node、bash、awk、find（带 -exec）等于放行任意代码。下一小节的论文量化了这个问题。

坑 2：一条复合命令只有「每一段都被规则明确允许」才能跳过沙箱。Codex 的 bypass_sandbox 就是这么算的（见第 2 节原文）。一段没匹配上，整条还是进沙箱。

2　审批：规则判不了的，谁来点头

2.1 起点：每条都问

最早的做法是每条命令都弹窗。结果是人点烦，开始无脑「允许」。Anthropic 的遥测显示用户约 93% 的弹窗点了同意一手（2026-05 containment 文章），这时弹窗就失去了拦截作用，只剩打扰。同一篇还说：老用户自动批准的频率约是新用户的两倍，但也更常在执行中途打断 Agent，也就是从「逐步审」变成「出岔子才管」。一手

2.2 优化方向：沙箱兜底，审批只管「越界」

流程在 tools/orchestrator.rs：先走审批，在沙箱里跑第一次；失败且是 SandboxErr::Denied，再看策略允不允许去掉沙箱重试。一手

读法：

  1. 只有 Denied 才进重试逻辑；别的错误直接返回。
  2. 注释写明 Never 和 OnRequest 下不重试：把简短的拒绝信息和原始输出还给模型（有一个例外：OnRequest 下网络访问被拒、且默认审批要求是 NeedsApproval 时，仍允许弹窗问「放行这个主机吗」）。
  3. 真要重试，弹窗里的理由是「网络访问 xxx 被策略阻止」，或从输出里提炼的拒绝原因，让人知道为什么要越权。

模块文档还有一句：Guardian 审批只对被审的那个动作有效；沙箱内的尝试被拒后要升级重试，需要重新审一次。一手（orchestrator.rs 开头注释，大意；Guardian 在本章不展开。）

4.3 沙箱有了，为什么还要管出网

Vercel 博客（2026-08-11，Brandon Tuttle）的标题就是答案：「没有网络边界的沙箱只做了一半」。一手（读了前约 4,500 字）

        decision === PolicyDecision.ASK_USER
      ) {
        if (effectiveCwd !== workspace && !isSubpath(workspace, effectiveCwd)) {
          debugLogger.debug(
            `[PolicyEngine.check] dir_path evaluated outside workspace. Preserving ASK_USER: ${command}`,
          );
          return PolicyDecision.ASK_USER;
        }

        if (containsGitCommand(parsedArgs) && !this.isTrustedFolder()) {
          debugLogger.debug(
            `[PolicyEngine.check] Known safe Git command evaluated in untrusted workspace. Preserving ASK_USER: ${command}`,
          );
          return PolicyDecision.ASK_USER;
        }

        debugLogger.debug(
          `[PolicyEngine.check] Command evaluated as known safe, overriding ASK_USER to ALLOW: ${command}`,
        );
        return PolicyDecision.ALLOW;
      }
    } catch {
      // Ignore parsing errors
    }
    return decision;

设计取舍：(1) 降级条件有五条：重定向、命令替换、危险命令、工作目录在工作区外、在未信任文件夹里运行 git。(2) 已知安全命令可以把 ASK_USER 升为 ALLOW，但工作区外与未信任 git 仍保留询问。(3) YOLO 绕过大部分检查。(4) 解析失败时：规则是 DENY 就拒绝；YOLO 下放行，但规则带 argsPattern 时拒绝；其它走默认决策（交互时询问，非交互时拒绝）。(5) 危险与已知安全的判断都依赖 sandboxManager.isDangerousCommand 与 isKnownSafeCommand，也就是策略引擎自己不知道什么是危险，它委托给沙箱管理器。
