全景图：长任务运行时要解决的三件事

Agent 一次任务可能跑几十分钟到几天。进程会被杀，机器会重启，用户会中途插话。运行时（runtime）就是在模型和外部世界之间，保证「挂了能接上」的那一层。

要保证的事不做会怎样本章对应做法
对话状态不丢进程一挂，几小时的上下文全没了追加写日志（append-only log），恢复时重放
外部副作用不重复恢复后又付了一次款、又发了一封邮件意图先记账、副作用不重放、幂等键
能在没人盯着时继续干活只能等人发消息才动inbox（收件）、timers（定时）、outbox（发件）
1 Session一次会话的容器：日志文件 + 写锁
2 Thread / Turn / Item协议层的三层：对话 → 一轮 → 一个动作
3 Rollout 日志每个事件追加一行 JSON
4 Resume从日志末尾倒着重放出状态
5 副作用保护记意图、记结果、不盲目重放

这章最重要的一个判断 判断

  • 状态能恢复，不等于世界能恢复。日志能把对话重放出来，但已经发出去的邮件收不回来。
  • 所以运行时的核心不是「存档」，而是「在动手之前先记账」。后面每一节都在讲这件事。

2　事件日志：怎么写，才不会写坏

起点：直接覆盖保存会怎样

3　恢复：从日志末尾倒着扫

起点：从头重放会怎样

为什么倒着扫？判断：最新的压缩记录里已经带了替换后的历史，它之前的几万行不用看。倒着扫，扫到压缩点就能停，成本只和「最近一段」有关。

设计原理：回滚也写进日志 判断

  • 如果回滚是「删掉最后 N 轮的行」，崩溃发生在删到一半，文件就处于无法解释的状态。
  • 追加一条「回滚 N 轮」的事件，是一次原子的小写入，要么有要么没有。
  • 代价：日志里留着被丢弃的轮次，文件会变大；恢复逻辑要懂这条规则。

4　崩溃、副作用与幂等：最容易出事的地方

起点：恢复后重试，会怎样

拆解 1：ACRFence（arXiv 2603.20625，2026-03-21）

我读了 HTML 全文（约 2.6 万字符，正文很短，是个短论文）。一手

问题回答
怎么测的Claude Code CLI + Qwen3-32B，用它自带的检查点恢复；外部服务用 MCP 服务器模拟（银行、云厂商、审批服务）；检查点放在「验证之后、不可逆动作之前」。
测到什么Action Replay：10 次检查点恢复试验，10 次都产生重复提交（100%），无检查点的对照 0/10。Authority Resurrection（单次授权令牌复活）：无状态校验 2/2 成功重用，有状态校验 2/2 被拒。

拆解 3：Crab（arXiv 2604.28138，2026-04-30）

读了摘要、引言和 3.1 节。一手

问题回答
怎么测的在 SWE-Bench 和 Terminal-Bench 类任务上，每个任务注入一次崩溃；对比四种恢复方式：重启、只恢复聊天（chat-only）、聊天 + 文件系统（Chat+FS）、每轮完整检查点；另测了高密度（最高 96 个沙箱同机）下的开销。
测到什么只恢复聊天：回放模式下仅 6% 任务成功，接真实 LLM 时 28%；聊天 + 文件系统：回放 48%，真实 LLM 只有 34%（环境和原来不一致时，Agent 发现状态不对会做出额外的「纠正」，反而更乱）。重启是正确的，但中位解题时间多 1.81 倍（回放）和 1.55 倍（真实 LLM）。
Crab 的做法用 eBPF 在主机侧观察每一轮的系统效果，判断这一轮有没有改变「恢复相关的状态」。超过 75% 的轮次没有（比如只是读文件），这些轮次不做检查点。检查点和 LLM 等待时间重叠，并统一调度同机各沙箱的检查点流量。
结果恢复正确率从 8%（只恢复聊天）到 100%；检查点流量最多减 87%；崩溃一次的任务只比无故障多 1.9% 时间；每轮都做完整检查点在 96 个沙箱密度下最多慢 3.78 倍。
能信多少数字来自作者自己的评估，和「每轮全量」「只恢复聊天」比的是自己搭的对照。「一次崩溃」是人为注入。我没读 7 节的完整表。结论方向（分轮次判断要不要存，比每轮全存省很多）可信；具体倍数别直接套到自己的场景。

经验与坑补遗（11–22）：来自论文和 X 长文

下面每条都标了来源。「读全文」指我读了 arXiv HTML 全文或 X 长文全文；「读摘要」指只读了 arXiv 摘要，数字没回正文核对。

坑 11：事件不进收件箱，就会丢或重复跑。Always-on 的做法：所有来源（用户消息、webhook、定时器）先写进收件箱，由一个 worker 领取；收件箱记录每条事件的状态，用来源的唯一标识去重；同一个收件箱同一时间只放一个活跃 worker；用户连发几条消息，合并成一次运行、只回复一次。来源：@shao__meng 对 Anthropic 文章的长文转述（2026-11-14，读全文）。二手

坑 12：运行中途来了新事件，必须提前选一种处理方式。三种：推到下一轮、并入当前这轮、中断后重来。选哪种会改变产品手感，文章把选择留给开发者。Codex 源码里 MailboxDeliveryPhase（CurrentTurn / NextTurn）就是在回答这个问题（我读了该枚举，见第 1 节）；LangChain 的 async subagent 把它做成 update_strategy：interrupt（默认，停掉当前运行、带新指令重启，适合「改用 Postgres」这类纠正）和 enqueue（等当前运行结束，适合「做完跑下测试」这类追加）。来源：@shao__meng、@sydneyrunkle（2026-11-05，读全文）、Codex 源码。二手（两篇 X）+ 一手（Codex 枚举）

坑 13：等人审批时，别让整个 Agent 干等。延后执行的工具调用：当前运行直接结束，会话停在这次调用的中途并存下来；用户的回答作为一条新事件回到收件箱，再起一次运行恢复会话；等待期间 worker 照常处理别的事件。和坑 6 对照：LangGraph 的 interrupt 是重跑节点，这里是「结束这次运行、之后新开一次」，副作用不会因为恢复被带着再执行一遍。后一句是我的推断。来源：@shao__meng。二手 判断

坑 14：凭证放在 Agent 的运行环境之外。推荐做法是在环境外放一个代理，由代理往发出的请求里注入凭证，Agent 自己发的请求不带真实凭证。无人值守时一次运行握着用户的访问权限，这是 always-on 风险最大的地方。来源：@shao__meng。二手

坑 15：记忆里只放以后查不到的东西。已在问题跟踪系统里的，只存一个链接。要存的分四类：对 Agent 行为的指令（每次运行都加载）、关于用户的笔记、已经告诉过用户的内容、进行中任务的进度（每个任务一个进度文件，写明做完什么、还剩什么）。会话太长压缩或新开会话都会丢细节，必须保留的要在运行中先写进记忆。来源：@shao__meng。二手

坑 16：「状态持久化了」不等于「执行是耐久的」。@JoshARosen（2026-11-03，读全文）写道：自己手写 Agent 状态机的人，往往从「一个 JSON 文件加几个转移函数」起步，后来会发现自己在实现 checkpoint、分布式锁、调度、可观测、崩溃恢复，等于重造了本来想避开的基础设施；只存状态不能让执行耐久，所以要在外面套 Temporal、Restate、DBOS 这类框架。我对应到本章：第 6 节的 SQLite 草图就是「只持久化了状态」，崩溃窗口（坑 9）还在。一手（读到该 X 长文原文）判断（对应到草图）

坑 17：检查点不是越多越好，第二个可能是亏的。RippleCP 摘要：12 个 SWE-bench Verified 任务、106 个真实恢复分支，检查点平均每任务省 49.4 秒；第一个检查点在 156.5 秒的受保护工作上省了 100.0 秒（转化率 0.64），紧接着一步之后的第二个检查点省 −1.1 秒（41.8 秒受保护，转化率 −0.03）。原因是恢复是「重新推导」而不是「重放」，所以保护了多少工作不等于省了多少时间。这是 12 个任务的试点。来源：arXiv 2610.09088 摘要（读摘要）。一手（摘要）

项目内容
要证明的事现有的幂等办法（唯一请求 ID、记录非确定值、让编排代码确定）共同假设「重试的请求和原来一模一样」。LLM Agent 恢复后会重新生成请求，这个假设不成立。论文把由此产生的攻击叫 semantic rollback attacks。
两类攻击Action Replay（重复执行不可逆动作，可由崩溃诱导）；Authority Resurrection（单次授权令牌在回滚后「复活」，再被用到别的目标）。威胁模型两种：Crash-Induced Restore（外部服务触发崩溃）和 Deliberate Rollback Abuse（有权使用 rewind 的内部人员故意回滚）。
怎么测测试台：Claude Code CLI + Qwen3-32B，用它自带的检查点恢复；外部服务是 3 个模拟的 MCP 服务器（银行：带 UUID 去重的转账；云厂商：建服务器；审批服务：无状态/有状态令牌校验）。

ACRFence 做法在工具边界（如 MCP 代理）为每次不可逆调用记「效果日志」（线程和分支标识、工具名、参数、环境上下文，环境上下文靠 eBPF 系统级监控采集，所以不改框架）；恢复后用一个轻量分析 LLM 区分「每次都会变的字段」（请求 ID、时间戳）和「体现意图的字段」（金额、收款人），把每次调用分三类：语义相同则返回旧响应不重执行（replay）；语义不同则拦住，展示旧日志，要求显式 fork；复用已消耗凭据则提前告知 Agent。分析 LLM 只在恢复路径上运行。

对本章最有用的两点：（1）作者说自己动手的人很快会重新实现 checkpoint、分布式锁、调度、可观测、崩溃恢复，等于重建了一遍想避开的基础设施，且「只持久化状态不等于耐久」，要在外面用 Temporal、Restate 或 DBOS（坑 16）。（2）状态机的实现可以很小：JSON 文件或数据库加转移函数；也可以做成 MCP 服务器，提供 claim_task、complete_task 之类的工具，让不同 harness 的 Agent 共用同一个状态机。能信多少：这是综述性的观察，没有实验、没有数字；各项目的细节我只是读到作者的描述，没有去读 Symphony、Pi Missions、ThruWire 的代码。二手（项目细节）

三篇 X 长文和论文之间的缺口 判断

  • X 上讲的是「怎么搭」：inbox、timer、outbox、状态机、异步子 Agent，几乎都在回答「怎么被唤醒、怎么别阻塞」。
  • 论文讲的是「出事后怎么办」：重复提交、令牌复活、撤不回的邮件。三篇 X 长文都没有量化这类失败。
  • 所以：搭的时候照 X 的分工，验的时候用论文的失败模式去打自己（比如 ACRFence 的「转账 + 崩溃 + 恢复」脚本）。

8　判断与方向

  • 判断 日志永远追加，回滚、分叉、压缩都表示成「新事件」，不改历史。Codex 的 ThreadRolledBack 和 OpenHands 的 parent_id 树是同一思路的两种形态。
  • 判断 恢复分两层：对话层（重放日志，各家已较成熟）和世界层（副作用、文件系统，论文都说还没解决）。别把第一层的成熟当成第二层也成熟。
  • 判断 幂等键必须由运行时生成并绑定意图。让模型自己填，恢复后一定会变（ACRFence 的实验是证据，但只有 10 次）。
  • 判断 先做「单写者 + 追加日志 + 意图先记账」，再考虑文件系统快照。前者代价低、收益大；后者（Crab 级别的 eBPF 方案）只有在高密度沙箱场景才值得。
  • 没读到的地方：Codex 的 thread_state.rs、turn_suspension.rs；Agents SDK 的 Runner 如何在恢复后对账（只读了注释）；Claude Agent SDK 的 session 代码（没取）。后续要补。

  2. Codex 恢复时遇到「回滚 N 轮」的记录，倒序扫描时怎么处理？

    答案

    B。源码注释原文意思：回滚是「丢掉最新 N 个用户轮」，倒着扫时就变成「跳过接下来 N 个封口的用户轮段」。

  3. ACRFence 实验里，检查点恢复后重复提交的比例是多少？对照组呢？
    A. 5/10，对照 5/10　B. 10/10，对照 0/10　C. 2/2，对照 0/2　D. 80%，对照 40%
    答案

    B。10 次检查点恢复试验全部重复（100%），无检查点对照 0/10。C 是令牌复活的实验（无状态校验 2/2 成功）；D 是 Atomix 里 Saga 与 Checkpoint-Replay 的漏发率。

  4. Crab 说超过 75% 的轮次不需要检查点，最合理的利用方式是？
    A. 完全不做检查点　B. 只在改变了恢复相关状态的轮次后做检查点　C. 每轮都做以防万一　D. 只在任务结束时做
    答案

    B。不是不做，而是按轮次判断。每轮都做在 96 沙箱密度下最多慢 3.78 倍；只存聊天恢复正确率只有 8%。

  5. 开放题：你要做一个每晚巡检 CI 并发邮件的 Agent。写出你的 inbox / timers / outbox 表结构，说明崩溃发生在「邮件已发出」和「状态改成 sent」之间时会发生什么，以及你怎么把它从「至少一次」改成「恰好一次」。
    参考思路

    要点：intent_key 由运行时生成（日期 + 任务 id），作为幂等键随邮件请求发给接收方；接收方（邮件服务或你自己的网关）用它去重；本地 outbox 记录 sent 只是辅助。没有接收方去重，就只能做到至少一次，并在邮件里标注「可能重复」。
