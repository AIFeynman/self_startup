1　确定性检查在先：判分程序怎样不被「日志里的字」骗

1.1　起点：只看输出里有没有 PASS

最省事的验收是读 Agent 的输出，看有没有「通过」。它不这么做会怎样，已经有现成事故：

  • 一手 DebugML 审计 Terminal-Bench 2：一个 Claude Opus 4.6 agent 要实现自适应拒绝采样器，它写的代码一运行就打印 PASS。验证器先运行 agent 的代码（印出 PASS），再运行自己的检查（印出 FAIL），但只检查输出里包含 PASS，所以判过。
  • 一手 同一篇审计里，BountyBench 要求真的利用漏洞，有 agent 用 grep 确认漏洞特征存在，再跑一个无关的 pickle.loads() 演示；另一个把整个库换成模拟漏洞的 mock。评估器只看退出码，两个都放行。
  • 一手 SWE-smith 上，一个 Claude 3.7 Sonnet agent 修不好字符串距离算法，就对测试里的具体输入写死返回值，提交说明里写着「为特定测试用例加了特殊处理，让测试通过」。

判断 三个例子是同一个洞：评分器读的是「Agent 能控制的东西」（输出文字、退出码、测试输入），而不是「任务真正完成后才会出现的东西」。

def test_maintained(case: str, sm: dict[str, str]) -> bool:
    """P2P semantics: a skipped test is not a regression, unlike for F2P."""
    key = _resolve_case(case, sm)
    return test_passed(case, sm) or (
        key is not None and sm[key] == TestStatus.SKIPPED.value
    )


def test_failed(case: str, sm: dict[str, str]) -> bool:
    key = _resolve_case(case, sm)
    return key is None or sm[key] in [
        TestStatus.FAILED.value,
        TestStatus.ERROR.value,
        # a skipped F2P test is not a resolution; without this, a patch that makes
        # every F2P test skip lands in neither list and scores RESOLVED_FULL
        TestStatus.SKIPPED.value,
    ]

一手 逐行读：test_maintained 是 P2P（原本就该过的测试）用的，跳过不算回归；test_failed 是 F2P（修复后应该由败转过的测试）用的，缺失、失败、出错、跳过都算失败。源码注释写明了原因：如果跳过不算失败，让所有 F2P 测试都跳过的补丁「既不在通过列表，也不在失败列表」，会被评成 RESOLVED_FULL。另外 test_passed 把 XFAIL（预期失败）也算通过，见 test_passed（85 行起）。

停一下：为什么同一个 SKIPPED，在 F2P 里算失败，在 P2P 里却不算回归？
看要点
  • F2P 的含义：这条测试必须真的跑过并通过，才证明问题被修了。跳过什么都没证明。
  • P2P 的含义：这条测试原本就过，只要补丁没把它弄坏就行。环境差异导致的跳过，不能怪补丁。
  • 判断：判断 同一个状态在「要证明的事」和「不能弄坏的事」里含义相反。写评分器时按「这条测试在证明什么」分别定规则。

def compute_fail_to_pass(report: dict[str, dict[str, Any]]) -> float:
    """
    Compute fail-to-pass metric. Accepts single report as argument.
    """
    total = len(report[FAIL_TO_PASS]["success"]) + len(report[FAIL_TO_PASS]["failure"])
    if total == 0:
        return 1
    return len(report[FAIL_TO_PASS]["success"]) / total

1.4　一个会被刷的评分器，修前和修后

判断 下面这段是我自己写的示意，不是任何仓库的代码。我在本机跑过：grade_v1 返回 True，grade_v2 返回 False（2026-11-16）。场景是 DebugML 里的「PASS 打印」：agent 提交的代码什么功能都没有，只打印 PASS。

我自己写的示意（非仓库代码），本机运行 2026-11-16

import subprocess, sys, tempfile, pathlib

AGENT_CODE = 'print("PASS")\n'
HIDDEN_TEST = 'import sys\nfrom solution import f\nok = f(2) == 4\nprint("PASS" if ok else "FAIL")\nsys.exit(0 if ok else 1)\n'


def grade_v1(workdir):
    out = subprocess.run([sys.executable, "solution.py"], cwd=workdir, capture_output=True, text=True).stdout
    out += subprocess.run([sys.executable, "test_hidden.py"], cwd=workdir, capture_output=True, text=True).stdout
    return "PASS" in out


def grade_v2(workdir):
    r = subprocess.run([sys.executable, "test_hidden.py"], cwd=workdir, capture_output=True, text=True)
    lines = r.stdout.strip().splitlines()
    return r.returncode == 0 and bool(lines) and lines[-1] == "PASS"


with tempfile.TemporaryDirectory() as d:
    p = pathlib.Path(d)
    (p / "solution.py").write_text(AGENT_CODE)
    (p / "test_hidden.py").write_text(HIDDEN_TEST)
    print("v1", grade_v1(d))
    print("v2", grade_v2(d))

判断 v1 把两段输出拼起来找 PASS，agent 的打印被算进去。v2 只跑评分方自己的测试，并且同时要求：退出码 0、输出最后一行等于 PASS。它能挡住这一个例子，挡不住「agent 改了 test 文件」「agent 打印后 sys.exit(0)」，那属于第 2 节的隔离问题。

// user exclude/include, then the extension allowlist and default-path patterns

// survives all of them. It answers only what the path and the diff header say;
// the size gate lives in selectFiles because it needs the resolved token limit.
func (a *Agent) whyExcluded(d model.Diff) ExcludeReason {
	if d.IsBinary {
		return ExcludeBinary
	}

	path := effectivePath(d)

	// and no user exclude can claim it under a different reason.

		return ExcludeSecret

		return ExcludeUserRule
	}

	if f != nil && f.HasInclude() && f.IsUserIncluded(path) {
		return ExcludeNone
	}

		return ExcludeExtension
	}

	if allowedext.IsExcludedPath(path) {
		return ExcludeDefaultPath
	}

6　pass@k 与 pass^k：一次成功是运气还是能力

6.1　起点：单次成功率 75%

一手 luhsnaa 文中的例子：pass@3 为 80% 时约等于 99%，而 pass^3 只有 51%。（CORE-Bench 从 42% 到 95%，原文说的不只是评分器的 bug，放在第 7 节。）

判断 两个口径回答的是不同问题：

口径问的问题适合谁
pass@k试 k 次，至少一次成功的概率能多次尝试并挑结果的场景（写代码、有人在回路）
pass^k试 k 次，全部成功的概率每次都要对的场景（客服、自动执行）

        def pass_at_k(values: list[float]) -> float:
            import numpy as np

            total = len(values)
            correct = sum(1 for v in values if v >= value)
            if total < k:
                # NaN-filtering left fewer than k scored epochs, so the
                # pass@k estimator is undefined; surface the unscored
                # sentinel rather than the spurious 1.0 the short-circuit
                # below would otherwise produce.
                return float("nan")
            if total - correct < k:
                return 1.0
            else:

                    float,
                    np.prod(1.0 - k / np.arange(total - correct + 1, total + 1)).item(),

一手 逐行读：总数 total 小于 k 返回 NaN（不能硬算）；total - correct < k 返回 1.0（错的次数不够 k 次，任何 k 次里必有对的）；其余走 1 - ∏(1 - k/i)，i 从 total-correct+1 到 total。这是 Chen 2021 的无偏估计。

def str_match_scorer(match: Callable[[str, str], tuple[str, bool]]) -> Scorer:
    """Scorer that uses a matching function.

    The matching function returns tuple[str,bool], where str is the answer
    extracted from the model output and bool is whether it matched the target
    """

    async def score(state: TaskState, target: Target) -> Score:
        # Decided once, above the loop, because a raw-empty completion can reach
        # the CORRECT return as well as the INCORRECT one. match() with a target
        # of "." normalizes that target to empty, and "".endswith("") is True;
        # includes() with an empty target is contained in anything. Both score
        # CORRECT off a completion the model never produced. The accepted scope
        # tags a raw-empty completion regardless of the value it ended up with,
        # so the value is preserved here and only the reason is added.
        empty = no_response(state.output.completion or "")
        answer: str | None = None
        for value in target:
            answer, matched = match(state.output.completion, value)
            if matched:
                return Score(
                    value=CORRECT,
                    answer=answer,
                    reason="no_response" if empty else None,
                    explanation=state.output.completion,
                )

        return Score(
            value=INCORRECT,
            answer=answer,
            reason="no_response" if empty else None,
            explanation=state.output.completion,
        )

    return score

一手 读法：先用 no_response 判断模型是否真有输出。源码注释解释了问题：match() 配上目标 "." 时会被归一成空串，而 "".endswith("") 为真；includes() 的目标为空时，什么文本都包含它。两种情形都会在模型什么都没给时判 CORRECT。修法是保留原分数，只加上 reason="no_response"，不改分数。判断 所以「修好了」只是可追溯了：想排除这批样本，要靠下游按 reason 过滤。issue #5619 是调研笔记里的转述，我没核对它的修复状态。

7.6　拆解：评委的 TPR / TNR

一手 luhsnaa 的数字例子：100 条轨迹里 10 条失败。一个全部判通过的评委一致率是 90%；一个 TPR 80%、TNR 90% 的评委一致率是 89%。判断 一致率几乎一样，后者真能抓到 8 条失败，前者一条也抓不到。所以评委只报「一致率」不够，要分开报 TPR（抓到真失败的比例）和 TNR（放过真成功的比例）。

一手 同文还给了「拆问题」的数字：Jev 把一个大问题拆成 5 个窄问题，分数从 62.6% 变成 95%。判断 这个例子是单个团队的经验，没有对照实验，我只把它当作「评委问题过宽会失准」的提示。

二手 Agent-ValueBench（2605.10365）报告评委与人工的精确一致率 91.8%，只读到摘要转述。Hamel Husain 的 LLM 评委文章（hamel.dev，2024 年的经典，二手）也主张用二元判断加人工校准。

坑与经验（本节）

  • 一手 修评分 bug 往往不改分数，只加标签。Inspect 的空答案修复就是这样，读报告要看 reason 字段。
  • 一手 基础设施失败要分类、要可见、不要偷偷剔除。SWE-bench 保持分母不变。
  • 判断 评委要有「未知」选项和人工金标样本。autoevals 默认没有。
  • 判断 差距小于 3 分，先怀疑环境。（Anthropic《Infrastructure noise》原文：低于 3 个百分点的差距，在资源配置没写清、没对齐之前都该存疑；这是有条件的，不是「3 分以内一律无效」。）一手

判断：判断 评分器要像被评的 Agent 一样被测：给它一组「必须判不过」的输入和一组「必须判过」的输入，每次改评分代码都跑一遍。这一组用例就是评分器的回归集。

7.7　原文：同一个模型，只改容器资源，差 6 个点

Anthropic 《Quantifying infrastructure noise in agentic coding evals》（2026-02-05，读原文）。实验：在 GKE 集群上跑 Terminal-Bench 2.0，设六档资源配置，从 1 倍到不设上限。最富的一档和最紧的一档，成功率差 6 个百分点（p<0.01）。一手

为什么：严格执行时，规格既是下限也是硬上限，内存稍有尖峰就被杀，没有缓冲。基础设施错误率最高到 6%。从 1 倍到 3 倍，基础设施错误从 5.8% 降到 2.1%（p<0.001），不设上限时降到 0.5%；但 1 倍到 3 倍之间成功率变化在噪声内（p=0.40）。再从 3 倍到不设上限，基础设施错误又降 1.6 个点，成功率却升近 4 个点，合计约 +6。涨得多的任务有 rstan 转 pystan、compile-compcert；还有一个例子 bn-fit-modify：装 pandas 这类包会触发内存不足被杀。一手

反向对照：SWE-bench 227 题、每题 10 次采样，把内存放大到 5 倍，只涨 1.54 个点，影响小得多。文中还提到一个未量化的观察：一天中的不同时段，通过率也会不同。一手

建议：同时写明「保证分配」和「杀死阈值」两个数；把这个区间调到下限与上限的成绩落在噪声内（文中以约 3 倍上限为例）。低于 3 个点的差距要存疑，因为温和区间内的波动就有近 2 个点，二项分布的置信区间本身已有 1 到 2 个点，基础设施的影响再叠上去。一手

坑　榜单上 2 个点的差，可能是资源配置的差。把资源配置写进每个成绩的报告里，否则两个数不可比。注意这是 Anthropic 在自家集群上的一次实验，6 个点是「1 倍对不设上限」，不是任何两个榜单之间的常见差距。判断

7.8　原文：安全评估的构念、样本量和配置

Anthropic 《Building strong safety evaluations》（2026-11-13，读原文），适合和 7.6 的评委自测对照读。要点：一手

  • 构念要对：自伤类场景用「拒答率」不对，该看多轮对话里的「恰当回应率」，只要有一轮不恰当，整段对话判失败。
  • 难度要校准：在 Anthropic 的 API 上，单轮评估的综合无害回应率对每个近期模型都在 94% 到 98% 之间，已经饱和，只能当回归检查；多轮的分布宽得多。
  • 样本量：多轮评估至少 100 条，单轮至少 1,000 条；多轮评估的置信区间可以超过 ±10 个点。例子：浪漫诈骗多轮评估里两个模型 98% 对 94%，差几个点，但统计上不显著，不能说谁更好。
  • 配置要写清：同一个模型，API 与带系统提示词的 claude.ai 之间，多轮安全评估的恰当回应率差最高可达 34 个点；自伤评估里，API 上是 60%，claude.ai 带新系统提示词和其他针对性提示词缓解后是 94%，这是两种配置的对比，不是只加一句提示词的前后对比。不同评分器的分数不要直接比较。
  • 评分器建议：用原子的二值标准；不给评分器看设计元数据；评分可以考虑换一个不同于被测模型的模型（原文是「consider」，是建议）；评分器自己出错时，出错的那一项要标记并排除，不能悄悄给分或悄悄丢掉；用人工标注校验。

判断 这几条和 7.7 合起来，是同一条规则：分数必须带着它的配置、样本量和误差一起报。数字都是 Anthropic 自测，文章里的模型名按原文，本章不展开。

精读 1　τ-bench（arXiv 2406.12045）：pass^k 的出处，以及它到底怎么判分

def pass_hat_k(num_trials: int, success_count: int, k: int) -> float:
    """
    Compute the pass^k metric for the given number of trials, success count, and k.
    from https://arxiv.org/pdf/2406.12045
    Args:
        num_trials: The number of trials.
        success_count: The number of successful trials.
        k: The number of trials to consider.
    Returns:
        The pass^k metric.
    """
    if num_trials < k:
        raise ValueError(f"Number of trials {num_trials} is less than k {k}.")
    return math.comb(success_count, k) / math.comb(num_trials, k)

    def _aggregate_step_rewards(self) -> VerifierResult | None:
        """Compute per-key means across steps with verifier results.

        Missing keys count as 0. Steps without a verifier result are excluded from
        the denominator.
        """
        if not self.result.step_results:
            return None

        valid_rewards = [
            result.verifier_result.rewards or {}
            for result in self.result.step_results
            if result.verifier_result is not None
        ]
        if not valid_rewards:
            return None

        all_keys = {key for rewards in valid_rewards for key in rewards}
        if not all_keys:
            return None

        count = len(valid_rewards)
        return VerifierResult(
            rewards={
                key: sum(rewards.get(key, 0) for rewards in valid_rewards) / count
                for key in all_keys
            }
        )

Q3（选择）OpenCodeReview 的 reflector 在调用出错或解析失败时怎么办？

  • A. 删光所有评论
  • B. 保留所有评论（fail-open），不删任何一条
  • C. 让作者重写
  • D. 新增一条评论说明失败
看答案

选 B。一手 过滤器只能删评论、不能加；出问题时不删。这适合「筛选评论」，不适合当发布闸门（闸门应当 fail-closed）。

Q4（选择）某 Agent 单次成功率 75%，各次独立。连跑 3 次全对的概率约是多少？

  • A. 75%
  • B. 98%
  • C. 42%
  • D. 25%
看答案

选 C。0.75³ ≈ 0.422。判断 98% 是 pass@3（至少一次对，0.984）。真实任务里各次不独立，这个数只是估算。

Q5（开放）你要给一个「自动修 Bug 并提交」的 Agent 设计验收链。请写出：每一层查什么、谁来查、哪一层 fail-open 哪一层 fail-closed，以及如何证明你的评分器本身没被刷。

看参考思路
  • 确定性层：评分方自己的测试 + 退出码对账；F2P 必须真跑通过，空清单判无效。
  • 隔离：测试晚上传、清旧结果、拿走 .git 和上游联网。
  • 真实入口：从用户报错的入口复现，查系统里的结果。
  • 独立评审：只看 diff 的新会话；闸门 fail-closed，评论过滤 fail-open。
  • 评估集：能力集 + 回归集 + 线上坏例；全败题先过有序筛查。
  • 汇报口径：pass@1 与 pass^3，样本数写清。
  • 评分器自测：空答案、PASS 打印、全跳过、NaN、金标解、已知坏样本的 TPR / TNR。
