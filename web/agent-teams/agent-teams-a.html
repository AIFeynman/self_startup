A　人机协同：人的注意力最贵，该在哪一步介入

本章目标：能为一个 Agent 系统设计「人在哪里介入」：哪些事放行、哪些事问人、问的时候怎么问，才能不让人被审批淹没。

学完能回答：

  1. 为什么「每一步都让人点同意」会失效？有什么数据？
  2. 介入点有哪几种（事前、过程中、事后、异步汇报、共同规划）？各自的代价在哪？
  3. Codex 的 auto-review、Claude Code 的 auto mode 怎么在「不打扰人」和「拦住坏事」之间取舍？熔断器怎么写？
  4. 一张「待决策卡」应该带哪些字段？AG-UI 的 interrupt/resume 怎么保证人迟到、人重复点也不出事？
  5. 哪些操作无论如何必须停在人这里？哪些可以放心多委托？

1　起点：每一步都问人，为什么会失效

1.1　基线：弹窗审批

最朴素的做法是 Agent 每调一次有副作用的工具就弹窗问「允许吗」。这在刚上手时是对的：人在学 Agent 会干什么。问题在于点得越多，看得越少。

坑 1：把审批当安全措施，却不衡量人是否真在看。弹窗数量多，不等于有人把关。Simon Willison 2026-05-06 的文章说他已经不再逐行审 Agent 写的代码，并把这种现象叫 normalization of deviance（偏差常态化：一次次没出事，就把越界当成正常）一手。这不是偷懒的个例，是用久了的普遍轨迹。

坑 2：审批弹窗没有信息量。2611.10058 的设计建议第三条是「显示这个动作会改什么」（D3）一手。只写「Run: bash -c '…'」，人没法判断后果，只能靠信任。后文第 6 节的决策卡就是对这条的回答。

1.2　优化方向

1. 少问先分档：低风险直接放行，不进审批
2. 换谁问让一个独立的审查者先筛，只把真正拿不准的升级给人
3. 问得好卡片自带「改什么、可不可撤销、选项」，人只点不写
4. 不重复问已定的事记下来，不再问第二次
5. 熔断连续被拒就停下来找人，别让 Agent 绕着墙一直试

档 4 就是 Khazix0918 自己给 Agent 画的「必须问人」七类：删数据、停服、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限；其余 Agent 自己做 一手（自述，单人经验）。

为什么要分档，而不是一条「危险命令黑名单」？因为同一个命令风险不同：git push 推功能分支是档 2，推 main 是档 3。Claude Code 有「按命令内容匹配」的 ask 规则，如 Bash(git push *)，匹配上就回到弹窗 二手。但这类规则只能按字符串切，切不到「推的是哪个分支」这类上下文；所以才需要后面讲的、能看上下文的独立审查者。

坑 3：只靠字符串规则，容易被绕过。claude-code 仓库的 issue #43713（2026-04-05）说：在 autoAllowBashIfSandboxed 下，echo $USER 会弹窗，而 echo "user is $USER" 却直接放行 二手（来自研究笔记，我没打开 issue）。同类问题 #87971（2026-08-19）讲 auto mode 下被 Bash 滥用 二手。教训：规则要和沙箱叠起来用，沙箱圈住「最坏能干什么」，规则只管「要不要打扰」。这和第 2 章（C2 工具、权限与沙箱）的结论一致，见 agent-teams-c2.html。

3.2　熔断器：Codex 源码走一遍

目的：筛选者连续说「不行」，往往说明 Agent 在撞墙、绕路。再试下去只会浪费时间，甚至找到绕过去的办法。所以要在「拒绝」累积到一定程度时，把控制权交回给人。

调用链（我从这个 crate 的 5 个文件拼的；宿主那一侧怎么真的打断 turn，我没读，只读了 ext/guardian-reviewer 这一个 crate）：

routing.rs判断这次审批要不要交给 guardian
guardian 审查返回 GuardianReviewOutcome：CachedApproval / Completed / Error
circuit_breaker.rs被拒就 record_denial，通过就 record_non_denial
InterruptTurn计数越线，通知宿主中断；宿主负责真的打断

const MAX_CONSECUTIVE_GUARDIAN_DENIALS_PER_TURN: u32 = 3;
const MAX_RECENT_AUTO_REVIEW_DENIALS_PER_TURN: u32 = 10;
pub(crate) const AUTO_REVIEW_DENIAL_WINDOW_SIZE: usize = 50;

pub(crate) fn record_denial(&mut self, turn_id: &str, policy: ...) -> ...Action {
    let turn = self.turns.entry(turn_id.to_string()).or_default();
    turn.consecutive_denials = turn.consecutive_denials.saturating_add(1);
    Self::record_recent_review(turn, /*denied*/ true);
    let recent_denials = turn.recent_denials.iter().filter(|denied| **denied).count() as u32;
    ...
    if !turn.interrupt_triggered
        && (turn.consecutive_denials >= max_consecutive_denials
            || recent_denials >= max_recent_denials)
    {
        turn.interrupt_triggered = true;
        ...Action::InterruptTurn { consecutive_denials: turn.consecutive_denials, recent_denials }
    } else { ...Action::Continue }
}

pub(crate) fn record_non_denial(&mut self, turn_id: &str) {
    turn.consecutive_denials = 0;
    Self::record_recent_review(turn, /*denied*/ false);
}

逐段讲：

  • 两个计数同时看：「连续被拒」抓的是撞墙；「最近 50 次里被拒 10 次」抓的是断断续续地撞墙（被拒、通过、被拒、通过……连续计数每次被重置，只看连续就永远不会触发）。只看一个就有漏洞，这是熔断器的标准写法，滑动窗口加连续计数。
  • interrupt_triggered 只触发一次：同一个 turn 里中断过，就不再重复发中断。否则宿主会收到一串中断信号。
  • 通过一次就清零连续计数，但窗口里的历史保留。所以一轮里「通过」不能洗掉「被拒」的记录。
  • cyber 模型用 1 和 1：文件顶部还有 MAX_CONSECUTIVE_CYBER_...=1 和 MAX_RECENT_CYBER_...=1，对网络安全专用模型，被拒一次就中断。判断 这是「越敏感的模型，越不给第二次机会」的设计。
  • 状态按 turn 隔离：HashMap<String, ...Turn>，clear_turn 在 turn 结束时清掉。

3.3　人不在线：open-swe 的「唤醒预算」

异步 Agent 会自己给自己排下一次运行（定时唤醒、被监控事件唤醒）。如果没有上限，它可以一直自己叫自己，人回来发现烧了一夜的钱。open-swe 的做法很短：

# langchain-ai/open-swe · openswe/threads/wake_budget.py · main · 读取 2026-11-16
class WakeBudget:
    """Runs a thread may start for itself between human messages, counted in its metadata.
    The count resets whenever a new human message lands in the thread."""

    async def spend(self, client, thread_id) -> bool:
        """Count one more run; False, counting nothing, once the limit is reached."""
        generation, count = await self.used(client, thread_id)
        if count >= self.limit:
            return False
        await self.record(client, thread_id, generation, count + 1)
        return True

THREAD_WAKEUPS = WakeBudget(generation_key="thread_wakeup_generation",
                            count_key="thread_wakeup_count", limit=10)
MONITOR_WAKES  = WakeBudget(generation_key="monitor_wake_generation",
                            count_key="monitor_wake_count", limit=10)

逐段讲：

  • 预算按「人的最新一条消息」分代：used() 读到的 latest_human_message_key 和存的 generation 不同，就当计数为 0。意思是人一开口，预算重置；人不说话，Agent 最多自己醒 10 次（定时唤醒 10 次、监控事件唤醒 10 次，各自独立）。
  • 预算存在 thread 的 metadata 里，不在进程内存里，所以重启不丢。
  • 这是「Agent 自己找活干」的上限，不是「Agent 找人」的上限。判断 我没在这些仓库里找到对应的「打扰预算」，也就是限制 Agent 一天最多向人发几张卡。Khazix0918 的「早期一天几十张卡」是这个缺口的真实后果（见第 5 节）。可以照抄 WakeBudget 的写法做 InterruptionBudget：按天计数、超限时合并成一张摘要卡。这是我的设想，没实现过。

来源：langchain-ai/open-swe 的 openswe/threads/wake_budget.py，main 分支，读取日期 2026-11-16。长任务的预算和恢复机制，见 agent-teams-c3.html。

3.4　问人的协议：AG-UI 的 interrupt / resume

Agent 要停下问人，用户界面要显示，人答完后 Agent 继续。AG-UI 把这件事做成协议，并且处理了几个现实问题：人可能迟到、重复点、只答了一半。

Run 1Agent 发 RunFinished，outcome 是 interrupt，带一组 interrupts
人在界面上看到卡片，决定
Run 2客户端发 RunAgentInput，带 threadId 和 resume: [{interruptId, status, payload?}]
结束Run 2 发 RunFinished，outcome 是 success

每个 interrupt 带这些字段（一手，docs/concepts/interrupts.mdx）：

字段作用
id关联键：resume 靠它对上是哪一个问题
reason / message?为什么停；给人看的话
toolCallId?是哪一次工具调用触发的
responseSchema期望的答案格式，客户端据此渲染表单
expiresAt过期时间；过期后再 resume，服务端返回 RunError
metadata? / subagentRunId附加信息；是哪个子 Agent 在问

协议的规则：resume 必须覆盖所有未决的 interrupt，不允许部分恢复；要幂等（同一个答案点两次不出事）；过期必须强制检查；老的、没有 outcome 字段的生产者仍然合法。判断 「不许部分恢复」这条很有用：Agent 同时问了三件事，人只答了两件，如果放行，剩下那一件相当于被默认批准或默认拒绝，二者都不对。

来源：X 长文「Addressing the code review bottleneck」（2026-11-05，598 赞）一手。Warp 的 Factories 循环：实现 Agent 与评审 Agent 来回，最多 N 轮；有歧义才回给人（在 Slack 线程或看板工单里），PR 上只露出需要人定的评论。「合并风险」五项：Verification（验证）、Alignment（与目标一致）、Impact（影响面）、Rollback cost（回滚代价，单向门还是双向门）、Error detection（出错能否被发现）。建议在 PR 描述里加「影响面」「回滚代价」两栏；并用一个预检决定要不要多轮评审（只给较大的功能）。这五项可以直接当 3.2 之外的「卡片字段」，见第 6 节。

5.5　事故：PocketOS（2026-04）

坑 7：问人的那一步其实不存在。这个事故里没有哪一步是「Agent 明确问了人，人点了同意」。是 Agent 自己找到更大的权限，一步做完。判断 它说明：①审批只管「已经被设计成要问的动作」，管不到「Agent 自己找到的新凭据」；②真正的防线是权限本身（token 范围、备份隔离），不是流程；③档 4 的操作要在权限层封掉，不能只靠「到时候会问」。详细的权限与沙箱设计见 agent-teams-c2.html。

6　走一遍：设计一张待决策卡

6.1　场景

一个 Agent 在夜里跑「清理过期测试数据」的任务，发现需要删除一批生产库里的记录来修复数据一致性。它被设计成：档 4 操作必须人批，人不在线，卡片发到飞书。

1 检测Agent 判断下一步属于档 4（删除生产数据）
2 暂停发 interrupt，状态存盘（任务的上下文、已做的步骤）
3 出卡卡片发到飞书，设过期时间
4 等待人没答：到期后按「拒绝」处理，Agent 改做不依赖这件事的部分
5 恢复人答了：带 interruptId 回来，校验没过期、没重复，继续

6.4　动手练习

  1. 选你手上一个会自己跑的 Agent，把它过去一周的所有「要人确认」的动作列出来，按 0–4 档归类。统计每档的数量和人实际花的时间。
  2. 找出档 0–2 里被问了的动作，改成放行；找出档 4 里没问的动作，加上拦截。
  3. 为你列出的档 3、档 4 里数量最多的一类，按 6.2 设计一张卡，分别给「24 小时没人答」和「人迟到 3 天才答」两种情况写默认处理。
  4. 检查：有没有「已定的事」记录？同一个问题会被问第二次吗？

7　判断与方向

可撤销的 PR、功能分支合 main、发布、数据库结构变更

判断 我从本章归纳的五条原则：

  1. 人的注意力是预算，不是免费资源。像限制 token 一样限制向人发卡的数量。目前开源实现里只看到「唤醒预算」，没看到「打扰预算」。
  2. 按风险分档，别按命令分。同一个命令不同上下文风险不同。
  3. 要求用 Hook 和权限，请求才用提示。能写成「绝不」的事，不要靠弹窗。
  4. 每层熔断：审批被拒、评审轮数、唤醒次数、花费，都要上限，越线交给人。
  5. 问就问得让人只点不写：给后果、给选项、给过期、给默认。

方向：①现有数字大多来自厂商博客和自述，缺少独立的、长期的、观察到的行为数据；②「审查者自己出错时默认放行还是拦」「TimedOut 之后上层怎么办」已在 3.7 读完（前者默认拦、不计入熔断，后者超时会中断整个运行）；宿主侧怎么真的打断、open-swe 里 spend 的调用方有没有加锁，我仍没读；③自动化率越高，人越少看，攻击面越大（2606.08919 的定性提示）。这是下一步要盯的地方。更多关于 SDLC 自主运行的内容见 agent-teams-c7.html。

章末测试

  1. 2611.10058 的问卷里，「认真审代码的人」和「其他人」在「常不细看就批准动作」的比例上：
    1. 前者明显更低
    2. 前者 61%，后者 67%，差异不显著
    3. 前者明显更高
    4. 论文没有比较
    答案

    B。认真审代码不等于认真审批。这意味着不能靠「挑认真的人来点」解决审批疲劳。

  2. Codex 的熔断器同时用「连续 3 次」和「最近 50 次里 10 次」两个计数，主要原因是：
    1. 为了让代码更复杂
    2. 只看连续计数，被拒、通过交替出现时每次通过都会清零，永远触发不了
    3. 两个计数分别给两个模型用
    4. 为了省内存
    答案

    B。连续计数抓撞墙，滑动窗口抓断断续续地撞墙。

  3. AG-UI 规定 resume 必须覆盖所有未决 interrupt，不能部分恢复，原因是：
    1. 协议实现起来更简单
    2. 没被答的那个问题等于被默认批准或默认拒绝，两者都不对
    3. 浏览器不支持部分恢复
    4. 为了节省网络
    答案

    B。

  4. PocketOS 事故对「靠审批流程把关」这种做法的主要启示是：
    1. 审批弹窗要更大
    2. Agent 自己找到更大权限、一步做完时，没有「要问人」的这一步，防线只能在权限和备份隔离上
    3. 不要用 Cursor
    4. 应该关闭所有自动化
    答案

    B。（事件细节为二手报道。）
