1　起点：先问要不要拆

基线：一个 Agent 自己拆

最便宜的基线是什么都不派。一个 Agent 读任务、自己列步骤、自己做。它的好处是上下文完整：前面读到的每一行都在后面看得见。代价是慢，而且上下文会被塞满。

很多人一上来就想加 Agent。但有一篇等 token 预算的对比说，把推理 token 固定后，单 Agent 在多跳推理上持平或更好；多 Agent 要等单 Agent 的上下文用得很差、或者花了更多算力才有竞争力。一手（2604.02460，已读全文，见 5.6。它测的是多跳问答，不是写代码。要加两个例外：思考预算只有 100 token 时多 Agent 更高；上下文被大幅破坏时多 Agent 反超。）

这是本章最该读的一篇，下面第 5 节逐项拆。先给结论，因为后面所有选型都要用它：拆得值不值，看任务形状，不看 Agent 数量。一手（2512.08296 v3 全文关键段）

设计原理：为什么「链」不能拆？ 判断

  • 单 Agent 的好处是上下文整块可见。拆开后，全局上下文必须压成一条条消息递出去，压缩会丢信息（论文把这叫 coordination tax）。二手（论文引言的概括）
  • 所以拆的前提是：子任务要的上下文很少、能写进一段话里。写不进一段话的，通常就不该拆。

坑：用「看起来复杂」当拆分理由。

deer-flow 的 task 工具说明里直说：只有预期收益明显大于委派开销才委派；任务只是复杂、步骤间有依赖、多个任务会改同一批文件、或需要用户交互，都不该拆。一手（读自 task_tool.py，见第 3 节）

3.1　Symphony：看板驱动的派发循环

文件：openai/symphony 的 elixir/lib/symphony_elixir/orchestrator.ex；规格 SPEC.md 第 8.2–8.4 节。分支 main，读取 2026-11-16。一手

调用链：轮询 Linear 工单 → choose_issues → 按优先级排序 → 逐个判断 should_dispatch_issue? → dispatch_issue 起一个 Codex 会话。

defp choose_issues(issues, state) do
  ...
  issues |> sort_issues_for_dispatch() |> Enum.reduce(state, fn issue, state_acc ->
    if should_dispatch_issue?(issue, state_acc, active_states, terminal_states) do
      dispatch_issue(state_acc, issue)
    else state_acc end
  end)
end

defp sort_issues_for_dispatch(issues) when is_list(issues) do
  Enum.sort_by(issues, fn
    %Issue{} = issue ->
      {priority_rank(issue.priority), issue_created_at_sort_key(issue), issue.identifier || issue.id || ""}
    ...
end

defp priority_rank(priority) when is_integer(priority) and priority in 1..4, do: priority
defp priority_rank(_priority), do: 5

defp should_dispatch_issue?(%Issue{} = issue, %State{running: running, claimed: claimed, blocked: blocked} = state, ...) do
  candidate_issue?(issue, active_states, terminal_states) and
    !MapSet.member?(claimed, issue.id) and !Map.has_key?(running, issue.id) and
    !Map.has_key?(blocked, issue.id) and
    available_slots(state) > 0 and state_slots_available?(issue, running) and worker_slots_available?(state)
end

defp failure_retry_delay(attempt) do
  max_delay_power = min(attempt - 1, 10)
  min(@failure_retry_base_ms * (1 <<< max_delay_power), Config.settings!().agent.max_retry_backoff_ms)
end

逐段读：

  • 排序键是三元组：优先级 1–4（没有优先级排最后，当 5），然后创建时间越早越先，最后用标识符打平。也就是「谁先来、谁更急，先派谁」，没有任何语义判断。
  • 能不能派是五道布尔闸：处于活跃状态、没被认领、没在跑、没被阻塞、还有空位（全局和按状态各一个上限）。规格里 max_concurrent_agents 默认 10。
  • 失败重试是指数退避：基数 10 秒，每次翻倍，上限由配置给；正常结束后的「继续」只等 1 秒。
  • 规格里 blocked_by 是尽力而为的元数据。判断 也就是说，依赖有没有被尊重，取决于工单有没有把依赖写对。看板把「拆」整个外包给了写工单的人。

4.3　Carlini 的编译器：没有 orchestrator，靠测试当裁判

来源：Anthropic 工程博客《Building a C compiler with a team of parallel Claudes》，2026-02-05，作者 Nicholas Carlini（Safeguards 团队），我读了原文（2026-11-16 本地副本）。一手

  • 16 个 Agent、近 2,000 个会话、两周，Opus 4.6 共用约 20 亿输入 token、1.4 亿输出 token，总费用略低于 2 万美元，产出约 10 万行 Rust 编译器，能编出 Linux 6.9（x86、ARM、RISC-V），多数编译器测试套件通过率 99%。每个 Agent 在自己的容器里，harness 是一个简单的无限循环：一个会话结束就在新容器里开下一个 Claude Code 会话。更正：早先我写的「while true 加 claude -p」，原文文本里没有这两个具体命令，我撤回；原文只说是「简单循环」，并提醒要在容器里跑，因为循环永远不停（有一次 Claude 误执行 pkill -9 bash，把自己和循环一起杀了）。
  • 分派方式：在共享仓库的 current_tasks/ 写锁文件认领任务，靠 git 同步让第二个认领者换一个。没有 orchestrator，Agent 自己挑「下一个最明显的问题」。

  • 测试输出的写法也是分派的一部分：只打几行，细节写日志；错误统一一行 ERROR 加原因，方便 grep；加 --fast 抽 1% 或 10% 样本，样本对每个 Agent 固定、对不同虚拟机随机，应对 Claude 的「时间盲」。一手
  • 每个 Agent 进新容器时没有任何上下文，要花大量时间自己摸清状况，所以作者让它们维护大量 README 和进度文件。冲突很多，作者说 Claude 能自己解。一手

设计原理：为什么 oracle 能把「整块」拆开？ 判断

  • 拆分需要一个「各自的工作互不依赖」的判据。oracle 把「整个内核对不对」变成了「这个文件对不对」，每个文件的对错独立可测。
  • 所以拆分不一定从任务本身下手，也可以先造一个能把问题切开的检查器。

5.7　ParallACT：没有 orchestrator 的两个 Agent（2611.00314，精读）

读到：arXiv PDF 全文（引言、方法、表 1–2、结果与分析、附录表 5–15）。一手。提交日期 2026-10-30，较新。

一句话。两个 Agent 各拿一个需求、同时改同一个仓库、没人统一调度，会怎样？

方法。每个实例有两份需求，Agent A、B 各领一份。分两类：互补（两个改动可以叠加）与矛盾（必须协调才能都满足）。测试集由 SWE-Bench Pro 的实例加工而成，部分人工构造。比较的策略：

单 Agent 上界一个 Agent 拿到两份需求（oracle）
串行A 做完，B 在 A 的结果上做（A→B），或再来一轮（ABAB）

X1　《Exploring Super-agent Design》（@DeepSeekHarness，2026-11-01）：分派的那一半

链接：x.com/DeepSeekHarness/status/2116857257245987236（点赞约 13823，全文约 4.5 万字符；采集到的是英文机翻版，文首注明原文是中文）。作者是 DeepSeek Harness 团队，文中明说讲的是架构想法，不是已有功能。我读了全文。整篇的架构拆解在 总框架章的「X 长文拆解」，这里只拆和分派有关的部分。一手（读到该 X 长文）

核心主张：把「分派」和「拆任务」分开。Router 是一个长期存在的会话，只和人交互、把任务派出去、记着任务之间的关系，不拆单个任务，也不自己执行（可以没有 Bash 工具）；拆任务是 Worker 的事，一个 Worker 内部可以再开 subagent，甚至是一整个 Agent Team，对 Router 透明。他明确说它和 Agent Team 的区别：Team 的 Lead 要深入理解任务、拆子任务、频繁协调，推理负担重；Router 只路由。

他怎么递：

  • 新任务的第一个事件由 Router 创建 Worker 会话，Worker 订阅这个事件流（一个 PR、一个话题、一串邮件叫一个 Thread）；之后同一 Thread 的后续事件由代码直接透传给订阅者，不再经过 Router。订阅是多对多的：几个 Worker 订阅同一个 Thread，就都能看到对方在做什么，自己发现冲突，不用点对点通信。
  • Router 把同一轮推理期间到达的事件排队，合成一批注入下一次调用。
  • Worker 的汇报只给 Router，由 Router 统一回复用户，避免几个会话各自回话。

数字（作者自报，合成负载）：约 300 条消息、约 20 条工作请求，4 种设计各跑 5 次，编码工作用「只消耗时间」的工具模拟。两级架构完成时间 p50/p95 为 12.4 / 15.7 分钟；单会话 + subagent 工具在中性提示下 20.4 / 29.5 分钟，且 5 次里 0 次调用 subagent；换成「优先委派」提示后 13.8 / 29.0 分钟，5 次里 4 次委派，另一次模型判断「活不大」自己干了。两级用的缓存 token 约为单会话中性提示的 3.8 倍（23.2M 对 6.1M，我自己算的）。Router 压测里，每分钟需决策的事件从约 1 条升到约 40 条，批大小 1.0 → 2.8，摊到每个决策 6.4 s → 1.6 s。作者自己说这些结果「仅供参考」。

能信多少：只有一个团队、合成负载、每格 5 次，没有外部复现，我只拿它说明一个现象：让 lead 自己判断「要不要派」，它不稳。这和本章 4.1 里 Anthropic 研究系统的教训同向（lead 不知道该用多大力气，需要把努力规模写进提示词），后者我已回原文核对，是一手。不同的是 DeepSeek 的解法不是写更好的提示，而是让 lead 没有干活的工具。判断

6　一条规则走一遍

规则：派之前过三关。(1) 这块活能不能被一个确定性检查验收？(2) 各子任务的写集是否互不相交？(3) 预期收益是否明显大于委派开销？三关有一关不过，就别并行写。判断（综合 deer-flow 说明、Cognition、Google 的结论）

场景：仓库里有 12 个失败的测试，要修好。用 Claude Code Agent Teams，3 个队友。

步骤做什么为什么
1 列清单lead 跑测试，得到 12 个失败用例和各自的报错先有可验收的单位（第 1 关）：每个用例一条命令就能判对错
2 查写集让每个用例各追到要改的文件。发现 用例 7 和 用例 9 都要改 utils/parse.py第 2 关。同一文件两个队友同时改，就会互相覆盖
3 合并或串行把 7 和 9 合成一个任务，交给同一个队友隐含依赖显性化。宁可粒度粗一点
4 估收益11 个任务，3 个队友，每人约 3–4 个第 3 关。官方建议 5–6 个/人，我们任务数不够，3 个队友已是上限；再多协调成本超过收益
5 写任务每个任务写：要修的用例名、允许改的文件、验收命令（pytest 用例名）、不许碰的目录对应 deer-flow 的验收条件与 Anthropic 的「边界」
6 设闸用 TaskCompleted Hook 在标记完成前真跑一遍该用例，不通过退出码 2不信队友自述的「完成」
7 收尾全部完成后 lead 跑一次完整测试补语义冲突这一层：各自单测过，合起来可能坏

如果第 2 步发现 12 个用例全都走同一个模块，三关就过不了第 2 关：不并行，由一个 Agent 修，其他 Agent 只读或做审查。判断

7　判断与方向

  • 默认单线程，拆是例外。只有「子问题独立、单 Agent 基线不高」时才拆。依据：Google 的任务形状结论，和 Cognition 的立场。判断
  • 要拆，先造裁判。Carlini 用 GCC，deer-flow 用 acceptance_criteria，Claude Code 用 Hook。有裁判才敢并行写，没有就写入单线程。判断
  • 少角色。Cursor 一路删掉 integrator 和 judge。每多一个角色多一个瓶颈。一手（Cursor 博客）+ 判断
  • 看清证据层级。CooperBench、ParallACT 的跌幅是「会冲突的构造任务」；STALE 的真实 PR 对里几乎不冲突；AgenticFlict 的文本冲突率是另一层。别把它们当同一个数。
  • 方向（我的猜测，未验证）。训练出来的 orchestrator（PARL 一类）和把依赖图算出来的拆分（Co-Coder 一类）可能取代手写的「努力规模规则」。但这些结果都来自作者自建基准，还没见到独立复现。判断

章末测试

1. 一个任务是「按顺序一步步做，每步依赖上一步的观察」。按 Google 的结果，多 Agent 最可能怎样？

A. 明显更好　B. 差不多　C. 明显更差　D. 只要加验证者就更好

答案

C。顺序规划任务（PlanCraft）所有多 Agent 变体都退化，−39% 到 −70%，原因是硬拆之后协调开销挤占了推理。D 不对：中心化验证能抑制错误扩散，但在这类任务上仍是负的。

2. Cursor 为什么没有一直用「锁」来防两个 Agent 抢同一个任务？

A. 锁在技术上做不到　B. 锁被占太久或忘了放，20 个 Agent 只剩 2–3 个的吞吐　C. 锁让模型更保守　D. 锁太贵

答案

B。注意乐观并发替代锁后更稳，但出现了另一个问题：没有层级，Agent 回避难题。所以后来才引入 planner。

3. deer-flow 的 task 工具返回 completed，意味着什么？

A. 任务已验收通过　B. 子 Agent 的执行结束了，是否达标要看验收条件的检查结果　C. 代码已合并　D. 测试全过

答案

B。说明里明确：completed 只表示执行结束；验收条件由程序确定性检查，判断不了的标 UNVERIFIED。子 Agent 的汇报只是自述。

4. STALE 在真实合并过的 Django PR 对上只发现 1/417 的语义干扰，却在构造任务上看到 97%。正确的读法是？

A. 语义冲突几乎不存在　B. 构造任务测的是「出现时有多糟」，不是「有多常出现」，两个数不能互相替代　C. 实验有错　D. 只在 Django 成立

答案

B。作者自己声明构造失败率不估计现实频率。A、D 也过度推断：真实 PR 是已审查过、已解决冲突后的合并结果，样本有选择偏差（我的判断）。

5.（开放题）你要把一个「给三个微服务各加一个字段」的任务派给多个 Agent。写出你会在每个子任务描述里放哪四样东西，以及你在合并前会补哪一道检查。

参考思路

子任务描述：目标（哪个服务、加什么字段）、允许改的文件范围、验收命令（该服务的测试加一条字段断言）、边界（别动哪些接口）。三个服务如果共享一个 schema 或消费者，要先确定接口再并行；这是隐含依赖。合并前补：跨服务的集成测试，因为各服务单测都过，合起来也可能因为字段名、类型不一致而坏（语义冲突）。若这些服务其实共用一个 schema 文件，则由一个 Agent 先改 schema，其余再并行。
