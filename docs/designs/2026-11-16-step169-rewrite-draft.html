Agent Teams 课程 · Part 1 · 总框架 · 2026-11-16

本章目标：拿到任何一个多 Agent 系统（DeepSeek super-agent、Claude Agent Teams、Cursor 的 planner/worker、Gas Town……），能沿着「五道关」逐关检查：该不该拆、状态放哪、接口怎么写、并发写怎么不互相踩、要不要 manager。检查完能说出这个系统最薄的一关在哪，以及它适不适合你的任务。

学完能回答（五个问题就是五道关，后一个问题是前一个问题答完之后冒出来的）：

  1. 拆成多个 Agent，值不值？账怎么算，失败从哪来？（第 1 节）
  2. 拆开以后共享的东西放哪、谁能写？七种常见架构各自怎么答，各先坏在哪？（第 2 节）
  3. 模块之间的接口怎么写，出错时才有人负责？（第 3 节）
  4. 多个 Agent 并行写同一份东西，怎么不互相踩？有哪些数字？（第 4 节）
  5. 要不要有 manager？为什么论文互相打架？（第 5 节）

预计用时：2.5 小时（第 3、4、5 节有源码和论文精读，可分两次读）。

标记：一手 我读过原文或源码；二手 别人转述，我没读到原文；判断 我自己的推断。论文只读摘要的，文中会写「只读摘要」。

全景图：一个问题，五道关

先说这章在回答什么。一句话：把一个 Agent 拆成一队 Agent，原来藏在一个脑子里的东西，都得变成写出来的东西。上下文要变成外置的状态，「我顺手知道」要变成接口，「我改了就是改了」要变成有主的写权限，「我觉得对」要变成有人核实。

所以本章不是并排介绍十几个系统，而是顺着一条因果链走五道关。每过一关，都会冒出下一关的问题：

1 值不值得拆多花几倍 token，只有任务能拆、结果能验时才划算。决定拆，就有了多份上下文
2 状态放哪多份上下文要共享的东西，总得放在某处，并规定谁能写。放好了，还得有模块去读写它
3 接口怎么写读写的入口收窄成几份合同，出错时才知道谁负责。入口收窄了，仍会有人想同时写
4 并发写隔离、单写者、原子抢占、版本号。写冲突挡住了，写进去的东西对不对谁来判
5 要不要 manager有核实手段才值得加这一层。五关过完，拿真实系统检验，再走一遍场景

六层各是什么

为什么切成六层：我按「一件事从被触发到交付，依次经过谁」来切。先有人或事件发起（入口），再有人理解并拆分（主 Agent），然后要记账和调度（工单），再有人干活（子 Agent），干完要有人验收，最后所有这些都跑在隔离、权限、存储之上（底座）。为什么这几列：每一层先说它解决什么问题，再说它对外暴露的接口形状，再给两三个真实实现，最后标本课程哪一章讲它。接口形状那一列最重要，因为第 3 关就是在讲它。

拿到一个新系统，按三步走：（1）先画六层，找出它的状态在哪一层、谁在写；（2）按五道关逐关问，每一关都问「它的答案是什么、证据是什么」；（3）找最薄的一关，那里就是它最先坏的地方。后面每一节开头都会接上前一节留下的问题，结尾回答章首的对应问题。

1 第一关：值不值得拆

一句话：拆成 Teams 要多花几倍到二十几倍的 token，只有任务能拆开、结果能验证时才划算。先把账算清，再去谈怎么搭。

📎 先补两个背景

token：模型读写文本的计费单位，成本和耗时都按它算。多个 Agent 各自带一份上下文，同一份材料会被重复读多遍，所以「多几倍」主要指这个。

基线（baseline）：拿来对比的最简做法，这里指同样预算下的单个 Agent。没有基线，就没法说拆开到底有没有赚。

起点：一个 Agent 够不够用

不做 Teams 的默认路线是：一个 Agent，一个上下文，一条循环。它有三个天花板：上下文装不下（任务太长）、墙钟时间太长（串行）、没人挑它的毛病（自己写自己审）。Teams 是对这三条的回应，但它不是免费的。所以第一件事是算账。

成本倍数：先问「比的是什么」

课程里最容易被混用的就是「多 X 倍」。同样写「多几倍」，有的比聊天，有的比标准会话，有的比单 Agent，数字没法直接比。所以下表先把每个数的分母写死。列只留引用一个倍数必须知道的：比的是什么、出自哪里、我读到没读到，缺任何一样都不能引用。

账是花出去的钱。换回来什么？先看反面：失败往往比成功多。下面几篇论文各从不同角度回答这个问题。

失败比成功多：论文怎么说

挑这几篇，是因为「值不值得拆」要先后回答：什么任务适合拆（Scaling Agent Systems），合作为什么反而差（CooperBench），失败具体长什么样（MAST），以及效果是不是只因为多花了 token（2604.02460）。前一个问题答完，才轮到下一个。表里「能信多少」这一列是我加的，因为它们大多只读了摘要。

论文 怎么测的 测到什么 能信多少
Scaling Agent Systems（v3 2026-04） 260 种配置，6 个基准，5 种架构，3 个模型家族 二手 不同任务从 −70.0%（需要顺序规划）到 +80.8%（可分解的金融任务）；单 Agent 基线已经高时，协调收益递减；集中式验证让错误传得更少 只读摘要。R²=0.373，「预测哪种架构好」只解释了不到四成，别当公式用

读表要点：这几篇指向同一个方向，但没有一篇说「别用 Teams」。判断 合起来的意思是：任务能不能拆开决定成败；比较要和「同样 token 预算的单 Agent」比，不能和「一次便宜的调用」比；常见失败来自接口（沟通、承诺、验证），不是模型智商。这正是后面几节都在谈接口的原因。

这些论文里，只有 MAST 给的是「失败长什么样」的分类。后面几关各补它的一块缺口，所以值得读到全文。

读全文：MAST，多 Agent 到底怎么失败

要解决什么问题：大家都知道多 Agent 常失败，但失败是随机的，还是有规律？没有分类，就没法针对性地修。MAST（NeurIPS 2025 Datasets and Benchmarks，经典例外）想先给出一个失败的分类。一手（全文）

怎么做的：先人工读 150 条轨迹，归纳出 14 种失败模式、三大类；再让 LLM（o1 加 few-shot）按这个分类去标 1,642 条轨迹，覆盖 7 个开源框架（ChatDev、MetaGPT、AG2、Magentic-One 等）。LLM 标注员对人工的一致性是 Cohen κ 0.77，没给示例时只有 0.58，所以 LLM 标注能用，但有误标。

图：MAST 的 14 种失败模式，按三大类和对话阶段（执行前、执行中、执行后）排列。来源：arXiv 2503.13657 v3 Figure 1，第 2 页。横条长度是它跨越的阶段，不是严重程度。图片版权归原作者，引用用于学习讲解。

结果说明什么：三大类占比：系统设计问题 44.2%，Agent 间错位 32.3%，任务验证 23.5%。最大的单项是「推理与动作不一致」13.2%，其次「不知道何时终止」12.4%、「违反任务规格」11.8%。这些都不是模型智商问题，而是系统没有硬停、没有对账。作者还试了两种修法：改 prompt 和改拓扑，效果都小（ChatDev 在作者自造的 32 题上 25.0 → 34.4，约多对 3 题），作者自己说「不算大幅提升」。

我核对出的几个限制：占比的分母是「失败里的占比」，不是任务失败率，我在二手文章里见过把 44.2% 说成「多 Agent 有 44% 的任务失败」，那是错的；大部分标注来自 o1，人工只有 210 条；轨迹是 2025 年初的框架和模型，Claude Code 这类现在的 harness 不在里面，所以分类仍可用，占比不能直接搬。

和本节的关系：它回答了「失败从哪来」，这是第 1 节的下半个问题。判断 三大类刚好对应后面的关：系统设计问题落在状态和接口（第 2、3 关），Agent 间错位落在接口和并发写（第 3、4 关），任务验证落在 manager 和验收（第 5 关）。

失败多，不等于不能用。业内最有名的争论是 Cognition 的前后两篇文章，它们把「并行的读和想」与「并行的写」分开了。一手 Cognition 2025 年写了《Don't Build Multi-Agents》，2026-04 又写了《Multi-Agents: What's Actually Working》。后者的立场是：并行写依然不行，但「多个 Agent 提供智力、写操作保持单线程」可以。例子是代码审查循环：coder 和 reviewer 不共享上下文时效果最好。判断 把它和 Anthropic、Cursor 放一起，可以调和成一条：并行的「读」和「想」没问题，并行的「写」要有单写者或隔离；任务可验证时 Teams 更值。

还有一个反面的提醒：Anthropic 发布的Cognition 案例（2026-07）说，单个模型已经能自己连续跑 8 小时。一手 但这是厂商客户故事，没给任务类型、成本，也没有外部复现，所以它只能支持一句话：单 Agent 的有效时长在变长，第 1 节的账每过一代模型都要重算，不能支持「Teams 没用」。

本节小结（回答章首问题 1）

  • 账：15×、7×、20× 以上，分母各不相同；自己的预算要用自己的任务跑一次单 Agent 基线再比。
  • 失败：主要来自协调，不是模型智商。MAST 三类失败正好对应后面的关。
  • 边界：并行的读和想没问题，并行的写要有单写者或隔离；任务可验证时 Teams 更值。

决定拆之后，第一个后果马上出现：两个 Agent 各有一份上下文，要共享的东西总得放在某处。这就是第二关。

2 第二关：状态放哪，谁能写

一句话：七种架构之间真正的差别，是状态放在哪、谁有写权限，而不是角色叫什么。上一关决定了要拆，这一关决定拆开的各方靠什么共享事实。

📎 先补几个背景

状态：系统「现在做到哪了」的全部记录：任务清单、谁领了什么、中间结果。Agent 自己的对话不算，因为对话一断就没了。

写权限：谁有资格改这份记录。多个 Agent 同时改而没规矩，就会互相覆盖。

checkpoint（检查点）：把状态定期存下来，崩了能从上次存的地方接着跑，不用重来。

事务：数据库里「要么整批写成，要么整批不写」的机制，保证写到一半崩了也不会留下半截记录。

起点：为什么按「状态」来分类

多数人是「先上框架，再发现状态乱了」。框架的宣传都按角色讲（lead、worker、reviewer），但角色名不决定系统会怎么坏。系统会怎么坏，取决于三件事：共享的东西存在哪（进程内存、文件、数据库）、谁有权改它、崩了之后能不能接上。所以下表用这三件事做列，再加「适合」和「最先坏的地方」两列，用来对应使用场景。行是我在本章读到的七种形态。

七种里，③ 图工作流最特殊：它的并发安全不靠锁，靠调度器保证「同一节点同一时刻只跑一份」。这到底怎么实现的，回到 ADK 的源码看。

读源码：Google ADK 怎么用「节点串行」换掉竞态

要解决什么问题：图工作流里，一个节点可能被多个上游同时触发。如果同时跑两份，它们会写同一份状态。ADK 要在不加锁的前提下，让重放（replay）的结果和历史一致。

怎么做的：入口是 src/google/adk/workflow/_workflow.py 的 _run_loop（main，2026-11-16 读）。它是一个调度循环：先 _schedule_ready_nodes 按触发缓冲区顺序启动节点，再 asyncio.wait 等任意一个完成，按固定顺序处理完成的任务，最后把下游触发放回缓冲区。关键片段：

for node_name in list(loop_state.trigger_buffer.keys()):
  run = loop_state.static_runs.get(node_name)
  if run:
    # Serialize executions of the same node to prevent race conditions.
    if run.state.status == NodeStatus.RUNNING:
      continue
  if self._at_concurrency_limit(loop_state):
    break
  await self._start_buffered_node(loop_state, ctx, node_name)

这样做的结果：同一个节点正在跑时，新触发只排队，不并发，这是用串行换不出竞态；并发上限在调度处统一检查，重放中的节点不占名额；完成的任务按「恢复序列」排序处理，让重放结果可复现。代价是整个循环围绕「可重放」设计，一个调度函数里混了 held transfer、interrupt、replay 三套逻辑，复杂度很大。

⚠️ 坑：节点处于等待人回应时，新触发会一直排队。人一直不回应，上游持续产出会在缓冲区里堆起来。我没找到缓冲区上限的代码，不能下结论它会不会无限增长。

和本节的关系：它是「单点调度」这一种写权限的典型：调度器决定谁跑，所以不需要锁。代价是灵活性，图是写死的。

  • 原来每一步都让模型自己判断，现在人多了、步数多了，每一步都猜既贵又不稳：确定性骨架。

3 第三关：模块间接口，别看角色名，看接口怎么写

一句话：接口是模块之间的合同。合同写得窄，状态才守得住；写不窄，第 2 关选的单写者、锁都会被绕过去。

📎 先补两个背景

接口 / 端口：模块之间约定好的「能传什么、能做什么」。这里的 ports.ts 是 TypeScript 的类型声明文件，只写约定，不写实现，所以读它就能看出每个模块被允许做什么。

幂等：同一个请求重复提交多次，结果和提交一次一样。系统崩了重试时，靠它避免重复派活。

多 Agent 常见的毛病是：Agent A 的输出就是 Agent B 的输入，中间没有一层「合同」。出了错，谁都说不清是谁的责任。DeepSeek 的原型是少数把合同写成代码的例子，下面读它的接口。

DeepSeek 原型：四个端口

要解决什么问题：一个值守系统（没人盯着）要处理 Issue、聊天消息这类外部事件，最怕三件事：被恶意内容说服去干不该干的事；重启后重复派活；崩了之后状态和对外动作对不上。dsh-superagent-prototype 的做法是把这三件事全部写进 src/core/ports.ts 的四个接口里。一手（main，2026-11-16 读；下面只摘文档注释和签名，省略部分字段）

/** What the assessor receives: bounded facts, never authority. */
export interface Candidate { evalId; thread; triggers; strength; policyVersion; tickets }

/** Semantic judgement. `request` queues the assessment, idempotently per `evalId`;
    the outcome returns through `Engine.decide`. */
export interface Assessor { request(candidate: Candidate): void; release?(evalId: string): void }

/** Executes assignments. The Engine calls it inside its commands,
    so each method only queues work, which reports back through the Engine's callbacks. */
export interface Executor { start(ticket, assignment): void;
  deliver(ticket, assignment): void; stop(ticket, assignment, reason): void }

export interface Outbox { send(message: OutboundMessage): void;
  status(id): ReplyStatus|undefined; withdraw(id): void }

设计点 是什么 防什么
「bounded facts, never authority」 把「事实」交给语义判断的 Agent，权力不给它 模型被一条恶意 Issue 说服，自己给自己加权限
request 按 evalId 幂等 同一次评估重复请求只排队一次 重启或重试后重复派活

Executor 的方法「只排队」 每个方法只入队，完成后通过回调汇报 在事务里做慢事、做副作用

读表要点：前两行防的是「输入」（模型被骗、重复触发），中间两行防的是「状态」（多写者、事务里做慢事），最后一行防的是「输出」（对外动作）。五行合起来，就是进、改、出三个方向的合同。

配套规则在 docs/007-architecture.md：Engine 是 Triggers / Threads / Decisions / Tickets / Assignments 的唯一写者；所有方法同步，一个命令一个事务；对外的工作在事务里只入队，提交之后才由适配器去做。持久化是单个 SQLite 文件。

这样做的结果：好处是模型决策和普通工具走同一条路径；代价是一轮里只允许一次转交，同轮多个并行转交被丢掉。失败时不触发 hook，当前 Agent 继续下一轮。

⚠️ 坑：想让一个 Agent 同时把任务分给两个专家，handoff 做不到，只能用 agent-as-tool 模式。被忽略的调用，模型只能从工具输出里知道「被忽略了」，不会自动重试；提示词没告诉它的话，它可能以为两个都执行了。这是我从代码路径推出的，没有跑过。

和本节的关系：OpenAI 把「交给谁」当成模型的一次工具调用，所以要在 SDK 里加规则兜底；Gas Town 把同样的问题放在文件锁上；DeepSeek 放在数据库事务上。判断 这是同一个问题，派活的幂等与互斥，在三个层次上的三种解。

设计者自己怎么说：一篇 X 长文

DeepSeek 团队写过一篇《Exploring Super-agent Design》（2026-11-01，中文原文，我读的是机翻版）。它讲的是上面原型背后的设计想法，原型只实现了一部分。核心主张是：一个 ReAct 循环给不了「连续、高效、主动、持久」，要靠外面的系统结构补；具体办法是让常驻的 Router 只派活不干活，每个任务由隔离的 Worker 去做。一手

文中有一组作者自己跑的预实验：约 300 条消息的合成流，四种设计各跑 5 次。最有信息量的一格是：单会话加 subagent 工具时，中性提示下 5 次里 0 次委派，活全在主会话里做；换成「优先委派」提示才委派。两级架构把「要不要委派」从提示词变成了系统规则，代价是缓存 token 约 3.8 倍（23.2M 对 6.1M，我自己算的）。判断 数字只有一个团队、合成负载、每格 5 次，没有方差，只能当方向性证据：不靠提示词，用结构让 Router 不干活，能让委派变稳。它对第 5 关有一个补充，留到那里说。

本节小结（回答章首问题 3）

  • 三招让接口守得住：（1）只交事实，不交权力，结果走 decide 提交；（2）调用只入队，提交之后才真正执行（outbox）；（3）能力靠「不给」，不靠提示词劝说。
  • 另一种取舍：OpenAI 把 handoff 做成工具调用，换来统一路径，代价是每轮只许一次转交。同一个问题，三个层次三种解：SDK 规则、文件锁、数据库事务。
  • 设计者的补充：让 Router 不干活，结构上杜绝「既拆又做」；证据只是方向性的。

4 第四关：并发写同一份东西

一句话：并行的读和想可以放开，并行的写要有主。前三关把写入口收窄了，这一关看真有多个 Agent 同时要写时，各家怎么挡。

📎 先补几个背景

git worktree：同一个仓库同时检出多份工作目录，每个 Agent 各占一份，各改各的，最后再合并。

文本冲突 / 语义冲突：两人改了同一处，git 合并不了，是文本冲突；各改各的、合并也成功，但两段代码互相矛盾，是语义冲突。后者 git 看不出来。

原子操作：一步做完、中间不会被别人插进来的操作，比如一条带条件的 UPDATE：条件不满足就什么都不改。

乐观版本检查：不加锁，各自先改；提交时带上自己读到的版本号，版本已经变了就拒绝，让它重读再改。

起点：让 N 个 Agent 直接改同一个目录，会在两层出事

一层是文本冲突，合并不了；另一层是语义冲突，合并了但两段代码互相矛盾。下面按「证据从哪来」分三步：先看两家工程实践（Cursor 和 Anthropic 的编译器），再看论文给的数字，最后读两份实现细节（Agensh 和 Paperclip），看「不靠中央调度」是怎么做到的。

两家工程实践：锁到底有没有用

Cursor 的《Scaling agents》（Wilson Lin，2026-01-14，读了全文，一手）讲了三代做法，每一代都是被上一代的问题逼出来的：

第 1 代共享文件 + 锁：Agent 拿锁太久或忘了放，20 个 Agent 的吞吐降到 2–3 个
第 2 代乐观并发：更简单，但没有层级时 Agent 变得保守，只做小而安全的改动

结果是作者自述、没有第三方复现：浏览器项目约一周，超过 100 万行；Solid 迁到 React 三周，+266K / −193K 行。他们还写到：先设的集成者（integrator）角色制造的瓶颈比解决的多，后来去掉；仍然需要定期重新开始，对抗漂移。

⚠️ 坑：别拿这些数字去比谁更强。项目不同、没有统一验收、没有成本数。判断 它们是「系统能撑多长」的演示，不是性能基准。

反例是 Anthropic 的《Building a C compiler》（2026-02-05，读了原文，一手）：16 个并行 Claude，只用最简单的锁文件，往 current_tasks/ 写一个文本文件当锁，两个 Agent 抢同一个任务时靠 git 同步迫使后者换一个，也跑成了。判断 两者不矛盾：编译器有现成的测试集当 Judge，目录天然能按模块切开；Cursor 的目标更开放，锁一多就拖累。差别在「可验证 + 可切分」，不在锁本身。

读源码：Paperclip 的原子 checkout 到底锁了什么

要解决什么问题：Paperclip 里多个 Agent 的 heartbeat run 会同时来抢同一张工单。要保证只有一个抢到，而且某个 run 崩了留下的锁不能永远占着。

怎么做的：入口是 server/src/services/issues.ts 的 checkout（master，2026-11-16 读，该文件约 1.5 万行）。调用链：assertAssignableAgent → 查子树暂停 → 清掉已死 run 留下的锁 → 查依赖阻塞 → 一条带条件的 UPDATE ... WHERE 抢占；抢不到再走「收养」分支。一手

const updated = await db.transaction(async tx => {
  ...
  return tx.update(issues).set({
      assigneeAgentId: agentId, checkoutRunId,
      executionRunId: checkoutRunId, status: "in_progress", ...
    })
    .where(and(
      eq(issues.id, id),
      inArray(issues.status, expectedStatuses),
      or(isNull(issues.assigneeAgentId), sameRunAssigneeCondition),
      executionLockCondition,
    ))
    .returning().then((rows) => rows[0] ?? null);
});

取自 issues.ts，有省略。

这样做的结果：「原子」靠的是一条 UPDATE 的 WHERE 条件，不是显式行锁：状态要在期望集合里，指派人要空或就是自己，executionRunId 要空或就是本 run；两个 run 同时执行，数据库只让一个返回行。抢不到不是直接报冲突，而是看旧锁是不是死的：旧 run 已终止就接管（adoptStaleCheckoutRun，先对 heartbeatRuns 行 for update）。锁挂在 run 上而不是 Agent 上，所以同一个 Agent 的新 run 能接管自己旧 run 的锁。代价是一个函数写了两百多行状态机。

⚠️ 坑：「过期」依赖 heartbeatRuns.status 是否终止。run 进程崩了但状态没改成终止时，锁一直有效，要等别处的清理任务把它标成终止。清理任务我没读，所以「多久能恢复」没有数字。

和本节的关系：和 Anthropic 的文本锁文件比，一个靠数据库事务保证一致，一个靠 git 同步，成本差别很大。还有第三条路，既不抢锁也不设单写者：版本号加幂等键。

再一条路：乐观版本检查（Ankole）

《Building a Real Agent OS for Teams》（@AgentBullLab，2026-11-03，读了全文）讲一个开源、不绑模型的多人 Agent OS，对象是三十人左右的公司。它回答的是：并行会话把同一张表写出多个版本怎么办。办法是：复合自然键（平台 + 店铺 + 外部订单号）让超时重试变成幂等 upsert；按字段更新，每个单元格带版本号，旧版本写入被拒，调用方重读；值真的变了才发事件，切断双向同步的死循环；文档用三方合并，只有两边改同一块才存进恢复目录。一手（读到该长文），实现细节二手（没读仓库）

判断 全篇没有数字，「99% 可靠」「月账单几万美元」都是作者描述，没有测量；当成一份「很完整的设计清单」用，别当成已验证的做法。它补上了前面三种办法（隔离 + 合并、单写者、原子抢占）之外的第四种：结构化状态靠版本号和幂等键，文档靠三方合并，两边都不靠锁。

回头把三份源码放在一起

Paperclip 把「谁在做」写进 Postgres 一行并靠 WHERE 条件抢占；OpenAI SDK 限定每轮只有一个活动 Agent；ADK 用触发缓冲加节点串行化。判断 共同点是都在调度点上硬编码了互斥，没有一个靠 Agent 自己协商。

本节小结（回答章首问题 4）

  • 几种答案：隔离 + 合并（CAID、Cursor 的 Worker、Gas Town 的 worktree）；单写者（DeepSeek 的 Engine）；原子抢占（Paperclip 的条件 UPDATE，ADK 的节点串行）；版本号 + 幂等键（Ankole）。
  • 有数字的：CAID 在 PaperBench 绝对 +25.6%；Agensh 128 个 Agent 把最难 5 题从 19.31% 推到 28.78%，但总算力不等；真实仓库里跨 Agent 的文本冲突率 41.7%，高于同 Agent 的 19.8%（观察数据）。
  • 有效的是隔离加合并，不是讨论。

写冲突挡住以后，剩下的问题是：写进去的东西对不对，谁来判，谁来拍板？这就是第五关。

5 第五关：要不要 manager

一句话：manager 值不值，取决于它手里有没有核实手段。这是上一关留下的问题：隔离和合并只保证写得进去，不保证写得对。

📎 先补几个背景

层级 vs 扁平：层级是有人专门分派、检查别人的活；扁平是大家平等地分工、互相讨论。本节比的就是这两种组织方式。

核实手段：能独立判断结果对不对的办法，比如跑测试、对照原文。manager 只靠「读一遍觉得对」不算。

神谕（oracle）：论文里假设「事先知道谁最擅长每道题」的理想情况，只用来当上限，现实里做不到。

起点：几篇论文在互相打架

和本节的关系：它支持「讨论式汇总会稀释专家」，但范围是没人拍板时。放在 MSEval 和 Loop-Back Authority 旁边，说的是同一件事：要有明确的责任人，而不是更多的讨论。

另一个判据：manager 要少干活

DeepSeek 的设计文章（第 3 关）对「层级」有一个补充：它反对的不是 manager，而是一个既要拆任务又要自己干活的 manager。Router 不拆、不干，只路由；拆交给 Worker。判断 这和「manager 要有核实手段」不冲突，给出第二条：manager 要少干活。

⚠️ 坑：把「有层级」当成「有验收」。层级只是组织形式；真正拦错误的是可执行的检查。这就是 E 验收与评估要单独成章的原因。

本节小结（回答章首问题 5）

  • 判据：manager 手里要有核实手段；manager 要少干活，不要既拆又做；责任人要明确，没人拍板的讨论会稀释专家，接口契约被一个 owner 破坏会让别人的正确工作连带清零。
  • 论文为什么打架：任务不同、基线不同、预算不等。OrgAgent 的 +102.73% 是对扁平算的，大半来自弃答；MSEval 的「差 30 分」是单项目最好最差，平均差 10 到 18 分。
  • 真正拦错误的是可执行的检查，不是层级本身。

五道关到这里问完了。接下来拿两个真实系统检验：它们是不是都这么答的。

6 一次检验：两家真实系统的答案趋同吗

📎 先补一个背景

值守型 vs 协作型：值守型是系统自己长期跑、人不盯着（DeepSeek 原型属于这类），所以「该问才问」「出错自己兜」要写进代码；协作型是人在终端旁边看着、随时纠正（Claude Agent Teams 属于这类），兜底可以交给人。后面比较两家的差异，很多来自这一点。

五道关是我从材料里归纳的。归纳容易自圆其说，所以拿两家真实系统检验一次：它们对这五个问题的回答是不是一样的。我最初的假设是：DeepSeek、Codex、Claude Code、Pi 做出来的东西，组织结构会越来越像。

先说证据范围，免得夸大：DeepSeek 原型读了架构文档、README、哲学文档和 ports.ts（一手）；Claude Code 闭源，只能引 Agent Teams 官方文档，文档写了什么是一手，真机行为没验证；Codex 和 Pi 本章没读它们的多 Agent 部分（循环见 C1），不下结论。所以只比较前两家。

两家的对照

下表的行就是五道关里能直接比较的维度：状态、写权限、谁派活、能力边界、对人的打扰、检查点。最后一列写是否趋同。

读表要点：趋同的只有「状态外置」。到了「谁有写权限」就分叉了。判断 原因大概是产品形态：DeepSeek 要的是不打扰人的值守系统，所以愿意在 Engine 里把规则写成代码；Claude Agent Teams 是人在场的并行助手，灵活性放在模型手里，兜底交给人。假设只对了一半，我把它从课程的「结论」降成「观察」。

💡 为什么值守型更要把兜底写成代码？判断 值守意味着没人看着。没人看着时要做到「该问才问」，就必须有一个能说「这个 Trigger 现在不该处理」的代码层，不能靠模型自觉。

还有两个说法我没核实，所以只当示例不引数字：Untangle / Ryan Carson 的云队列（只见转述和视频描述，找不到仓库或原文），Antigravity 的 teamwork（没找到一手来源）。

再看一个样本：一个人的事件中台

前两家都是团队级的系统。再看一个很不一样的：《折腾了整整 1 年……Agent 自动化系统》（@Khazix0918，2026-11-02，读了全文）。作者一人做产品，系统跑在自己的两台 Mac Mini 上；他明说是读了 DeepSeek 那篇之后写的。一手（读到该长文），数字都是自报，二手

他的做法有四点：事件先统一进一个中台，规则写在 rules.json，指定交给哪台机器的哪个 Agent、同组最多并行几个；Agent 主动去拉活（长轮询），不是中台去推，Mac 不用暴露公网；所有找人的消息只走一个出口，只在需要人判断时才发；代码交付走「开 PR 即结束，后面全交给自建 CI」，审查最多 3 轮。判断 我愿意信的是做法的组织方式，不信那些「节省」的比例：333 条问题是「被报出来的」，没有误报率，也没有无审查的对照。

它和本章的两处关系：对得上的是「给自动循环加上限」（并行上限、审查最多 3 轮）与状态外置；对不上的是 Router 用多强的模型，DeepSeek 文章说轻模型常常够用，他说决策和管理的模型一定要最强。两篇都没有对照实验，我不裁判。

💡 三篇 X 长文和论文之间的缺口 判断

第 5 关的论文在比「层级还是扁平」；三篇 X 长文都在回答另一个问题：没人盯着的时候，系统怎么不乱。只有 DeepSeek 那篇给了一个对照实验，而且是合成负载、每格 5 次，另两篇没有。所以它们是「设计清单」，不是「证据」：搭的时候抄它们的分工（Router 不干活、幂等键、规则表），验的时候回到第 4、5 关的论文和 E 章，要有可执行的检查，要在等预算下比。

人的带宽：最硬的约束

判断 前面所有机制，最终都在保护人的注意力。DeepSeek 的哲学文档直接这么写；Cognition 建议审查循环用不共享上下文的 reviewer；Agent Teams 建议 3–5 个 teammate。一个系统每小时要人看的东西超过人的处理量，再多 Agent 也没用，只是把积压推给人。详见 A 章。

本节小结

  • 趋同的只有一条：状态外置。写权限上两家分叉：值守型把兜底做成代码，协作型把兜底交给人。
  • 假设只对了一半。「趋同」降为观察；Router 该用多强的模型，一线没有共识。
  • 三篇 X 长文是设计清单，不是证据。

最后，把五道关串起来，在 DeepSeek 原型上走一遍。

7 走一遍：一个 Issue 怎样变成一次交付（DeepSeek 原型）

📎 先补一个背景

Issue：代码托管平台（如 GitHub）上的一条任务或问题单，这里当作触发工作的外部事件。下面几步里的 Trigger、Candidate、Policy.gate、Engine 等名字，都是第 3 关读过的接口，每一步对应一个。

这条链路是我根据 ports.ts 和 007-architecture.md 重建的，没有在真实环境里跑过；字段和顺序以源码为准，表名对应关系是推断。目的是让前五节的零件在一条线上出现一次，每一步标出它在过哪一关。

1 Trigger外部事件（比如一条 Issue 评论）进入 Intake，落一条 trigger 记录
2 Policy.gate按版本化规则判断这个来源能不能发起工作；不行就 ignore
3 Candidate只带「有限的事实」给 Assessor，不带权力
4 Assessor语义判断：ignore / unavailable / accept / stop；结果通过 `Engine.decide` 回来
5 Ticket + Assignmentaccept 时建工单和分派；Engine 在一个事务里写
6 Executor.start只排队；提交后适配器才真正起 worker
7 worker 汇报用 report / ack 等 6 个工具回来，不能问人
8 Outbox回复或通知入队，提交后发出，状态 pending→sent/dropped
步骤 过的是哪一关 它做了什么
1–2 Trigger、Policy.gate 第 3 关（接口） 来源和规则在入口处用代码挡掉，不让模型决定谁有资格发起
3–4 Candidate、Assessor 第 3、5 关 只给有限的事实；判断权在模型，但只能提交决定
5 Ticket + Assignment 第 2、4 关 Engine 唯一写者，一个命令一个事务
6 Executor.start 第 3、4 关 只入队，提交之后才起 worker
7 worker 汇报 第 3 关 6 个工具回来，能力靠不给
8 Outbox 第 2 关 对外消息有状态，可撤回，崩了能重发

再看每一步出错时谁兜底，这才是这条链路设计的核心：

这一步出错会怎样 谁兜底
评估超时 Policy.evalTimeoutMs；Assessor 可返回 unavailable
重启后重复评估 request 对 evalId 幂等
Issue 内容诱导 worker 去找人或改文档 worker 的工具里没有这些能力（预设 dsh-superagent-worker）
回复发出前崩溃 Outbox 状态 + 事务提交后才发
规则变了，旧授权还有效吗 Policy.revalidate(mandate)

判断 对照 Claude Agent Teams，同一个 Issue 要靠 lead 读完、拆成任务、teammate 抢任务；每一步靠模型，兜底主要在人和两个 Hook。区别就是前面说的：值守型把兜底做成代码，协作型把兜底交给人。

8 判断与方向

  1. 先过第 1 关。没有同预算单 Agent 基线，就不要说 Teams 更好；成本比要用同一个分母，15×、7×、20× 以上不是一回事。
  2. 先画六层，再选架构。第 2 关的 L3（状态与写权限）决定系统能不能恢复、能不能审计、并发会不会互相踩。
  3. 接口只交事实，能力靠不给。调用只入队，提交后才执行。
  4. 并行写要隔离，并行想可以放开。CAID（worktree + merge）、Gas Town（flock）、Cognition（写保持单线程）三者一致。
  5. Manager 要有核实手段，而且少干活。没有，就别加这一层。
  6. 要验证的三件事（没做）：在自己的任务上量单 Agent 与 Teams 的 token 比；DeepSeek 原型 Engine 单写者在高并发时的吞吐；Codex、Pi 的多 Agent 结构是否趋同。

以上 1–5 条都是判断：由本章读到的证据推出，不是哪家的官方结论。
