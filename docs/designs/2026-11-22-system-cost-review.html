二、耗时

已修知识库同步原来每次写请求后在全局数据库锁里整表重建索引，持锁 30.6 秒；现在只更新变化的行，持锁 0.09 秒（提交 cd76159）。

空闲时主要接口都在 0.2 秒内：最慢的是 /api/feed/picks 163ms，/api/feed/items 81ms，其余都在 40ms 内。/api/learn/plans/15 一次返回 803KB，偏大。

剩下的耗时问题：

  • 信息流刷新、X 长文、产品雷达等采集都跑在网页服务同一个进程里。刚启动时 CPU 满载约 1 分钟，期间 /api/dev/status 从 9ms 变成 2.1 秒。所有线程还共用一把全局数据库锁 db._lock。
  • 知识库同步除了索引，每次还要重新生成 6,654 个文档，约 2.4 秒 CPU；因为 INDEX.md 里带了当前时间，每次都会重写 35 个文件。同步期间页面请求偶尔会抖到 0.6 秒。

四、优化清单（按优先级）

P0轻量模型调用关掉用户级 hook

现象：X 长文“判相关”在 11-20、11-21 共 4 次运行全部失败（1357/1357、1955/1955、3229/3249、3830/3830），近 3 天 519 批无法解析。模型输出被全局收尾 hook 顶掉了，变成“这个未推送的提交不是我产生的……”。

原因：app/modules/_paper_label.py:102 和 app/modules/_oss_label.py:121 直接调 reclaude -p，没像 agent.py 那样传 --settings {"disableAllHooks":true}。论文和开源项目打标签用的是同一种调用，也会被影响。

后果：3 天没有新的 X 长文入库；Haiku 调用全部白费；每天还白烧约 3,500 次 GetXAPI 调用。

改法：两处都加上关 hook 的参数，补一条测试；把失败运行已用掉的 GetXAPI 次数也记进 x_art_run.calls，让月度上限 9 万次真正生效。另外，今天 07:39 那次运行被服务重启打断，一直停在 running，导致今天不会再跑；启动时应把残留的 running 标成失败。

P0前端等待已完成任务时的死循环

现象：11-19 12:13–13:07 约一小时里，/api/jobs/1036 被请求 44,620 次，/api/learn/plans/15（每次 803KB）44,631 次，约每秒 26 次，相当于传了约 35GB。

原因：web/modules/learn.js:436 的 watchJob：任务已经结束但页面状态还显示“生成中”时，waitJob 立刻返回、立刻刷新页面，重新渲染后又开始等待，中间没有任何间隔。

改法：第一次轮询就发现任务已结束的，不再触发刷新；刷新之间加最小间隔。

P1清理旧备份，整理数据库

11-03 到 11-09 的 10 个备份共约 5GB，对应的改造都已稳定。建议保留今天那份和每个里程碑最新的一份，其余删除，可省约 5GB。x_art 里已丢弃行的正文清空后做一次 VACUUM，app.db 预计从 1.6GB 降到 1.0GB 左右。删除和 VACUUM 都要你点头。

P1每个 Agent 任务记录 token 和等价费用

在 agent.py 解析 result 消息时，把 usage 和 total_cost_usd 存进 jobs 表，Haiku 打标签也一样。改完就能按板块、按天看消耗，下次盘点不用再猜。

P1日志轮转，轮询请求不写访问日志

按大小轮转 server.log（例如 20MB × 5 份）；/api/dev/status、/api/jobs/finished、/api/notify/since 这几个轮询接口不写访问日志，日志量预计减少七成以上。

P2采集任务移出网页进程

把信息流刷新、X 长文、产品雷达这些重任务放进现有的任务子进程里跑，网页服务只负责响应页面，启动后不再卡约 1 分钟。

P2知识库同步在数据没变时跳过

INDEX.md 不再写入当前时间，或在源数据没变时直接跳过整个同步，省下每次写操作后约 2.4 秒的 CPU。

P2深读仓库瘦身

深读完成后删除 src/.git（434MB），或改用浅克隆；Deep Dive 的 lab/repo 改用 git worktree 或硬链接，不再整份复制。合计可省约 0.6GB。
