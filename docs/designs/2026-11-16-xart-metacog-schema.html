元认知卡片 Schema 设计

依据：38 篇样例长文抽出的 369 个认知单元（判断 86、数据 83、做法 77、批评 64、前提 34、动机 25）和 9 张结论卡的实际制作过程。

结论：用“三层 + 一张边表”。
① 单元（每篇文章里一句话的最小认知）→ ② 结论卡（跨文章聚合出的一个判断，卡面固定 6 个槽位）→ ③ 关系边（卡与卡、单元与卡之间带类型和原文依据的连线）；另有 概念 / 场景词表 作为所有层共用的连接键。
样例暴露的核心缺陷是：旧的“单元类型”把它是什么和它对结论起什么作用混在一起，并且缺少“场景”和“结构化数据”。新 schema 把这三件事拆开。

1　现有数据暴露的 5 个问题

问题证据（样例里的真实情况）后果
类型和角色混用“批评”共 64 条，但里面既有“无 harness 时 20 个任务只有 8 个真完成”（其实是支持“不能自评”的数据），也有“网关剥离缓存标记会让历史全按未缓存计费”（是踩坑）。同一个单元放进不同卡片，角色不同；类型无法稳定复用，只能靠人工分支持/反驳。
没有“场景”槽没有任何字段回答“什么情况下用 / 不用”。限定条件散在“前提”里，有 34 条，措辞各异。卡片只能说“是什么”，不能说“在哪成立”；也无法按场景检索或把两张卡关联到同一场景。
数据是自由文本“84→79”“52.8%→66.5%”“33/60”都是我手挑的大数字，靠正则加粗。无法自动选 hero 数字，也无法判断“有没有基线、样本多大”。
来源独立性靠手工修正8 篇同题“Harness, Loops, Graphs”互相转述，被我手工合并成 1 个来源；论文被引用多次也要手工归并。共识强度会被虚高；必须在 schema 里留“被引来源”字段自动去重。
关系只有隐含的结论间的 8 条关系（支撑、落地、依赖…）是我手画的；卡内“演进”是手写句子。要建立关系必须有独立的边表，带类型、原文依据、判定者。

2　三层模型

L1 认知单元 unit　（每篇文章 8–12 条，模型抽取）一句话的最小认知：判断 / 做法 / 事实 / 踩坑 / 原因 / 场景。带原文引文、来源层级、数字。
L2 结论卡 card　（跨文章聚合，约每 3–6 篇产生 1 张）一个判断 + 适用场景 + 怎么做 + 证据强度 + 边界 + 演进。卡面槽位固定，扫一眼能懂。
L3 关系边 rel　（卡↔卡、单元↔卡）类型固定、必带原文依据、标明由模型还是人判定、可被人改。
共用词表 vocab　（概念 concept、场景 scene、实体 entity）所有层都挂这些 ID；两张卡只要共享同一个概念或场景，就能自动被推荐关联。

3　L1 认知单元：把“是什么”和“起什么作用”拆开

单元只描述自己是什么。它对某张卡是支持还是反驳，写在边表里（同一单元可以对 A 卡支持、对 B 卡限定）。

字段取值 / 说明
kind 内容类型判断 claim（作者的观点）· 做法 practice（具体怎么做）· 事实 fact（数据 / 实测 / 案例结果）· 踩坑 pitfall（失败、陷阱、例外）· 原因 rationale（为什么 / 动机）· 场景 context（在什么条件下）
text一句话 ≤60 字，自成一句，不依赖上下文。
quote原文逐字引文 ≤40 字；入库前程序逐字核对，对不上就丢弃（样例 144/144 通过）。
polarity 倾向主张 / 反对 / 中性。表示作者对自己讨论的对象的态度，不是对卡的角色。
scene[] 场景三个维度，从词表选：任务类型（编码 / 研究 / 长任务…）· 技术栈（Claude Code / Codex / 自建 harness…）· 规模（单 Agent / 多 Agent / 团队）。
concept归一化概念 ID（如“验证闭环”“缓存”），解决同义不同词。
metric 结构化数据仅 kind=事实：{what, value, baseline, n, unit}，例：{what:"完成属实率", value:8, baseline:20, unit:"个任务"}。有基线、有样本才算强证据。
tier 来源层级一手实测（作者自己跑的）· 引用论文 / 官方 · 自报 · 转述 · 纯观点。决定证据强度，也决定能不能算“一手”。
cites[] / origin被转述的原始来源 ID（论文、他人文章）。同一 cites 自动合并成一个独立来源。
article_id, user, posted_at溯源；点击能回到 x.com 原文。

4　L2 结论卡：6 个固定槽位

下面是“不能自评”这张卡按新 schema 填出来的样子（数据取自样例，场景槽和做法槽是新增的）。

不能让模型自己验收自己：验证必须来自外部，最好是程序能判“不通过”
① 结论
一句话判断 + 为什么重要：Agent 报告“完成”不可信（20 个任务只有 8 个属实）。
② 适用场景
任务：自主长任务 / 编码栈：Claude Code · Codex · 自建 loop规模：单 Agent 起
③ 怎么做
把完成标准写成脚本可判定的终态（Done when）；验证者与执行者分开；验证强度取决于它接受的最弱证据。
④ 证据强度
独立来源 10 · 一手 1 · 反驳 1  →  共识，但有保留
hero：8 / 20（一手实测，有基线）；论文：217 个循环仅 76 个有验证器
⑤ 边界与反例
边界/goal 评估者只读对话时仍不可信；反例对抗式 AI 评审“多半浪费 token”。
⑥ 关联与演进
落地 ← 先写完成标准；被依赖 ← 评测驱动改动；支撑 → Harness 影响不亚于换模型。
Oct 23 首次提出 → Nov 4 收紧 → Nov 14 出现反驳

“认知 / 经验”怎么落在卡上：认知＝①（判断 + 原因）；经验＝②③⑤（场景 + 做法 + 踩坑）。两者各占固定位置，所以元认知扫一眼就能分辨“这是道理”还是“这是打法”。

卡片字段（存储）

card {
  id, statement(≤40字), why(≤60字),
  scene[],             // 并集或人工校正
  actions[],           // 做法类单元 id，≤3 条置顶
  hero: {unit_id, text},   // 自动选：tier最高且有 baseline 的 metric
  verdict: 广泛共识|共识但有保留|有争议|缺一手数据|单一来源,   // 规则计算，不用模型
  counts: {articles, sources, first_hand, counter},
  open_gap,            // 缺的证据，如“没有写 / 没写完成标准的对照数据”
  status: draft|confirmed|retired, version
}

5　L3 关系边：便于和其他卡建立关系

rel { id, from, to,            // card 或 unit 的 id
      type, basis_quote,       // 必须带原文依据，没有依据不入库
      by: model|human, confidence, created_at }
关系方向含义样例里的例子
支持单元 → 卡实测“20 个任务只有 8 个属实”支持“不能自评”
反驳单元 → 卡“同设置下换模型差距仍然很大”反驳 Harness 影响
限定单元 → 卡“60 行只是一家公司的经验值”限定“规则越短越好”
具体化卡 → 卡规则越短越好 → 机制优于文字
依赖 / 落地卡 → 卡先写完成标准 落地 不能自评；评测驱动 依赖 不能自评
解法 / 前提卡 → 卡多 Agent 以“隔离上下文”为前提，是上下文污染的一种解法
同源卡 ↔ 卡成本大头 与 上下文污染 共同指向“反复重读历史”
演进卡 → 卡（新取代 / 收紧旧）“验证强度取决于最弱证据” 收紧为 “必须程序可判否”

为什么这样更容易建关系

  • 共享词表就是天然的连接点：两张卡只要共用同一概念或同一场景，系统就能自动提示“可能相关”，由模型补类型、给依据，人只确认。
  • 单元可被多卡复用：同一个单元对 A 卡是支持、对 B 卡是限定，不用复制。
  • 关系带依据且可追责：每条边有原文引文和判定者，错了能改；人改过的边不被模型覆盖。
  • 卡的版本化：新文章进来只追加单元和边，卡的 verdict 重算，旧结论不丢（对应“演进”）。

6　抽取与聚类的落地方式

  1. 逐篇抽单元（现有 Haiku 流程，改 prompt）：输出 kind / polarity / scene / metric / tier / cites；引文程序逐字核对，失败丢弃。
  2. 概念与场景归一化：先从已有单元聚出候选词表，人批量合并改名（可复用已有 kb_concept_edit 的重命名与隐藏逻辑）。
  3. 归簇成卡：同一概念下的判断类单元，模型归成候选卡并起草 statement；每张候选卡必须带支持与反驳单元。
  4. 规则算 verdict 与 hero：不交给模型，保证可复核。
  5. 提边：对共享概念 / 场景的卡对，模型判关系类型并附引文，人确认后入库。

成本：抽取已验证约等于免费（本机 Claude CLI 轻量档）；新增的是归一化与提边两步，量级为“卡数 × 近邻数”，远小于逐篇抽取。

7　验证与已知风险

  • 验证方式：拿样例 38 篇用新 schema 重抽一遍，检查三件事：① 同一单元能否稳定分到同一 kind；② 9 张卡的场景和做法槽是否填得出（填不出的比例）；③ 手画的 8 条边模型能复现几条（召回）以及多出的边是否合理。
  • 风险：轻量模型抽 metric（基线、样本量）可能不准，数据类需抽样人工复核；场景词表一开始太细会碎，先控制在 ≤30 个；长文有大量营销或转述，tier 判断要允许“不确定”。
  • 不做：不引入图数据库；SQLite 三张表（unit / card / rel）加词表足够。

自主决策

选了什么备选理由改回代价
单元类型与对卡角色拆开，角色只存在边表沿用 claim / evidence / counter 混合类型样例里“批评”类被不同卡当成支持、反驳、踩坑，混用无法复用中，需重新抽取
新增“场景”为一等字段和词表把场景写进“前提”文本场景是跨卡建关系和检索的主要连接键低，可后补
verdict 和 hero 用规则算让模型判断可复核、可解释，且已在样例验证低
关系边必带原文依据只存类型没有依据的边无法被人审，会累积噪声低
卡面固定 6 槽自由排版扫一眼可比，缺的槽（如“没有对照数据”）直接暴露缺口低
