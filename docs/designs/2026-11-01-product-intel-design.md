# 产品雷达：AI 产品深度跟踪与解读（设计稿 2026-11-01）

- **分支**：`feat/product-intel-design`（基于 main `792b7b1`），本稿只有设计，不改代码。
- **一句话**：盯住一批 AI 公司和产品，发现每一次功能、定价、商业模式的变化，按「用户问题 → 产品逻辑 → 技术逻辑 → 商业逻辑」解读，能实测的就自动评测；并把你自己的判断记下来、事后打分，用来训练商业战略判断力。

## 0. 目标与完成标准

**目标**：不用自己刷各家的 blog、changelog、X，就能及时知道重要 AI 产品「变了什么、为什么这样变、对谁有影响、实际好不好用」。几个月下来，对每家公司有一份持续更新的档案，同时能看到自己判断准不准、在哪类问题上判断偏。

**完成标准**（分期验收见第 9 节，下面是终态）：

| # | 检查项 | 怎么验证 |
|---|---|---|
| C1 | 关注名单里 T1/T2 公司的官方变化（发布、changelog、定价页、文档）在 24 小时内变成「变化事件」 | 抽 20 条已知发布，对照事件时间；漏报率 < 10% |
| C2 | 每个重要事件（≥ B 级）都有解读卡，五层齐全，每条事实带来源和日期，推测有标注 | 平台校验字段 + 审稿阶段打分 ≥ 阈值 |
| C3 | 同一发布在 blog / X / HN 多处出现，只算一个事件 | 去重测试集 |
| C4 | 每家公司有一份活档案（战略主线、产品矩阵、定价史、能力时间线），事件进来后自动增量更新 | 档案的 `updated` 跟着事件走；打开就是最新状态 |
| C5 | 至少一个品类（编码 Agent）能自动评测：固定任务集、可重复跑、产品更新后自动重跑，并给出和上一版的差异 | `evals` 里同一任务集有 ≥ 2 个版本的运行记录和差异报告 |
| C6 | 判断账本：A 级事件先让你写判断再看 AI 解读；预测带验证日期，到期提醒你核对并打分；能统计各维度的准确率 | 账本页面 + 到期提醒进入规划 / 复盘 |

**通用性要求**：解读、去重、评测都按品类和事件类型设计，不为单家公司写特例。新加一家公司只需要填它的信息源配置。

## 1. 现状：已有什么，缺什么

| 已有 | 位置 | 可复用的部分 |
|---|---|---|
| 产品类信息采集：Product Hunt / YC Launch / TrustMRR / a16z 等分析 RSS | `_feed_sources.py`、`_feed_follow.py` 的 `product` 组 | 采集器、关注源解析、`sites` 的「无 RSS 列表页 + link_re」 |
| 产品五项速评（收入 / 模式 / 定位 / 价值 / 痛点），DeepSeek 批量跑 | `_feed_product.py` | 「只用给定事实、没有就写未公开」的写法和输入哈希防重算 |
| HN 评论提炼 + 跨帖经验库 | `_feed_hn.py` | 产品口碑的来源；经验库的组织方式可以照搬到「模式库」 |
| 调研多引擎（Claude / Codex / GrokBot / Muse）+ 综合 | `research.py` | 深度档案直接发调研任务；GrokBot 查 X 上的反应 |
| 产品体验记录 `products` 表 | `research.py` | 你的一手体验；并入产品档案 |
| 分阶段后台任务 + 每阶段校验 + 审稿返修 | `_deepdive.py`、`jobs.py` | 深度解读和评测都照这个模式做 |
| 知识库同步、批注、问 Claude | `kb.py`、`annotations.py` | 档案和解读卡进 `data/kb`，可划线追问 |
| 规划排程（非专注时间跑自动任务） | `plan.py` | 评测、深度解读排到非专注时间 |

**缺的**：

1. **对象模型**：现在的产品分析针对的是「一条推荐」，看完就过去了。缺「公司 → 产品 → 功能」这一层持久实体，也就没法看到一个产品随时间怎么变。
2. **官方一手源 + 变化检测**：定价页、changelog、文档这些地方大多没有 RSS。要知道它们变了，得定期存快照、做 diff。
3. **事件层**：把多处来源归并成一个「变化事件」，并分出轻重。
4. **解读框架**：五项速评只回答「这是什么」，不回答「为什么现在做、技术上怎么做到、对竞争格局意味着什么」。
5. **实测**：现在完全没有。
6. **判断力训练闭环**：AI 解读了，但你自己的判断没有记录，也没有回头验证。

## 2. 整体链路

```
 关注名单（公司 / 产品 / 品类，三档）
        │
 ① 采集  官方源（blog / changelog / 定价页 / 文档 / GitHub release / App Store 更新说明 / 官方与创始人 X / 招聘页）
        │  + 已有 feed（HN / Reddit / PH / YC / X / 播客 / 知乎）按实体名命中
        ▼
 ② 识别  快照 diff + 条目 → 候选变化 → 实体链接 → 跨源去重 → 事件（类型 + S/A/B/C 分级）
        ▼
 ③ 解读  B 级及以上：解读卡（五层）│ S/A 级：深度解读任务（理解 → 实测 → 写作 → 审稿）
        ▼
 ④ 实测  按品类的任务集 + 评分规则；产品更新后自动重跑，出版本差异
        ▼
 ⑤ 沉淀  公司活档案 / 品类对比矩阵 / 定价与模式库 / 周报
        ▼
 ⑥ 训练  先写判断再看解读 → 预测账本 → 到期核对打分 → 偏差画像 → 回流复盘和学习计划
```

所有步骤都是平台已有的后台任务（`jobs.py`），不新增服务，也不新增常驻 Agent。板块对话 Agent 只用一个 `skills/intel/SKILL.md`。

## 3. 对象模型

```
company（公司）  1─n  product（产品）  1─n  feature（功能 / 能力点）
     │                    │                     │
     └──── source（信息源配置：类型、地址、抓取方式、频率）
                          │
 snapshot（页面快照）──► change（候选变化）──► event（变化事件）──► analysis（解读卡 / 深度解读）
                                                   │
                                   eval_suite ── eval_run（评测）
                                                   │
                                          judgment（你的判断 / 预测）── resolution（到期核对）
```

### 3.1 关注名单：三档

| 档 | 范围（初始名单待你确认，见 D2） | 跟踪深度 |
|---|---|---|
| T1 大公司 | OpenAI、Anthropic、Google / DeepMind、Meta、Microsoft、Apple、Amazon、xAI、字节、阿里、腾讯、DeepSeek、月之暗面 | 全部官方源；每个 B 级以上事件都出解读卡；S/A 级出深度解读 |
| T2 明星 AI native | Cursor、Perplexity、Lovable、Replit、Cognition、Harvey、ElevenLabs、Midjourney、Glean、Sierra、Decagon、Suno、Runway、Manus、Genspark 等 | 官方源 + 定价页快照；A 级以上出深度解读 |
| T3 有创意的 startup | 不手填，从 PH / YC / TrustMRR / HN 自动发现 | 只出五项速评（已有）；满足晋级条件后进 T2 观察期 |

**T3 → T2 的晋级条件**（满足任意两条就提名，你一键确认）：30 天内在 ≥ 3 个来源被讨论；TrustMRR 收入或增长达到阈值；HN 讨论 ≥ 200 分；你点赞或收藏过；它的模式命中模式库里标为「新」的类别。

## 4. 采集与变化识别

### 4.1 信息源（每家公司一份配置，新加公司只填配置）

| 源 | 抓取方式 | 频率 | 价值 |
|---|---|---|---|
| 官方 blog / newsroom | RSS，没有就用 `sites` 列表页 | 2h | 正式发布 |
| changelog / release notes | 列表页或快照 diff | 6h | 小功能变化最全的地方，最容易被忽略 |
| 定价页 | 快照 diff（只保留正文 + 价格表结构化） | 12h | 商业模式变化的最直接信号 |
| 文档 / API 参考 | 站点地图 diff（新增页面）+ 重点页快照 | 24h | 新能力往往先出现在文档里 |
| GitHub releases（SDK / CLI） | API | 6h | 技术细节、发版节奏 |
| App Store / Google Play 更新说明 | 公开页面 | 24h | 移动端功能 |
| 官方账号与创始人 / PM 的 X | 已有 X 采集，加名单 | 跟随 feed | 预告、灰度、用户反应 |
| 招聘页 | 快照 diff，统计岗位类别变化 | 7d | 战略方向的先行信号（例如开始招企业销售、招某个方向的研究员） |
| 状态页 / 事故 | RSS | 24h | 可靠性 |
| 第三方 | 已有 HN / Reddit / 播客 / 知乎 / a16z | 跟随 feed | 口碑和解读 |

抓不到的页面（登录墙、反爬）：按已有约定先找本地副本，再派 Codex 走浏览器；仍然失败就把这个源标记为「需人工」，不卡住其他源。

### 4.2 快照 diff → 候选变化

- 正文提取后归一化（去导航、时间戳、随机 id），再算哈希；哈希没变就跳过，不调模型。
- 定价页单独做结构化：用便宜的模型抽成 `{plan, price, unit, limits[], features[]}`，变化按字段比较，例如「Pro 从 $20 涨到 $25」「免费档额度从 50 次变成 20 次」。这样比文本 diff 可靠得多。
- 文本 diff 只把新增和修改的段落交给模型判断「这是不是一个产品变化」，避免把改错别字报成变化。

### 4.3 实体链接与去重

- **实体链接**：公司 / 产品的 `aliases` 加上产品名词表做规则命中，命中有歧义时（比如 "Claude" 可能是公司也可能是产品）再用模型消歧。
- **去重**：`dedupe_key = 产品 + 事件类型 + 关键名词（功能名 / 模型名 / 价格档）`，72 小时内同一个 key 合并成一个事件，`sources` 追加。官方源时间最早的那条作为 `happened_at`。

### 4.4 分级（决定后面花多少钱）

| 级 | 标准（满足任意一条） | 后续处理 |
|---|---|---|
| S | T1 的新产品线或旗舰模型；定价 / 打包方式改变；进入新市场；会重塑一个品类的发布 | 先写判断 → 深度解读 → 有对应评测就重跑 → 进周报头条 |
| A | T1/T2 的重要新功能；T2 的定价变化；大额融资；关键人员变动 | 先写判断 → 深度解读 |
| B | 一般功能更新、API 变化、新集成 | 解读卡 |
| C | 修 bug、文案、小优化 | 只进时间线，每周汇总一条 |

分级规则先写死在代码里，模型只负责把事件归到类别；你可以手动升降级，升降记录当反馈，每月调整一次规则。

## 5. 解读：五层框架

### 5.1 解读卡（B 级及以上，单次模型调用）

| 层 | 要回答的问题 | 写作纪律 |
|---|---|---|
| ① 变了什么 | 具体功能 / 价格 / 限制，前后对比；面向谁、什么时候、哪些地区 | 只写事实，带来源链接和日期 |
| ② 用户问题 | 解决谁的什么问题（JTBD）；用户原来怎么凑合；痛点有多痛、多频繁 | 引用真实用户讨论（HN / Reddit / X），区分一手和转述 |
| ③ 产品逻辑 | 为什么是这个形态、为什么是现在；在产品矩阵里的位置；增长路径（获客 → 激活 → 留存 → 付费）上动了哪一环 | 标「推断」 |
| ④ 技术逻辑 | 背后大概率依赖什么能力（模型能力、上下文、工具调用、检索、端侧），哪些是新的可行性，成本结构大概怎样，别人跟进难不难 | 有论文 / 文档就引用；没有就标「推断」并写出依据 |
| ⑤ 商业逻辑 | 谁付钱、怎么收费、单位经济；护城河类型（数据 / 分发 / 网络效应 / 切换成本 / 品牌 / 规模）；对竞品、上下游、创业公司是利好还是威胁 | 数字只用公开数据，没有写「未公开」 |
| ⇒ 所以呢 | 3 条以内：这意味着什么；要盯的后续信号；对你（做产品 / 创业）的可执行启发 | 每条可以被事后验证 |

**分析透镜**（按事件类型选用，不硬套）：定价类用价值度量与打包（按席位 / 按用量 / 按结果）；平台类用聚合理论和互补品策略；竞争类用 7 Powers；新品类用 JTBD 和 Wardley 演化阶段。透镜用来提问题，不在文章里背框架名词。

### 5.2 深度解读（S / A 级，后台分阶段任务，照搬 Deep Dive 的模式）

| 阶段 | 做什么 | 产物 | 平台校验 |
|---|---|---|---|
| gather 取证 | 官方原文、文档、定价页前后快照、创始人 / PM 的发言、HN / X 反应（派 GrokBot）、竞品的同类功能 | `evidence.md`，每条带链接和日期 | 来源数 ≥ N，官方源 ≥ 1，有日期的比例 ≥ 80% |
| probe 实测 | 有对应评测集就跑；没有就做一次手动脚本化试用（API / CLI / 浏览器），保存原样输出和截图 | `probe/` | 至少一条真实运行记录，否则写明「未实测」及原因 |
| write 写作 | 五层框架长文 + 与历史事件的联系（同一公司的战略主线、同类竞品的应对） | `analysis.md` | 五层齐全；事实句都有引用 |
| review 审稿 | 独立审稿：事实核对、推断是否标注、有没有空话、「所以呢」能不能验证；然后直接改稿 | `review.json` + 改后稿 | 评分 ≥ 阈值，否则打回重写一次 |

深度解读也可以直接发一个调研任务（`research.py`，角度预填：技术原理 / 关键玩家与竞品 / 用户口碑与体验 / 商业模式 / 最新进展），复用多引擎和综合能力。产品雷达这边只负责事件上下文和结果回挂。

## 6. 自动化评测

做评测的目的不是排榜单，而是回答：**这次更新到底让哪类任务变好了 / 变差了，变化有多大，花了多少钱和时间**。

### 6.1 按产品形态选执行方式

| 形态 | 例子 | 执行方式 | 前提 |
|---|---|---|---|
| 模型 API | GPT / Claude / Gemini / DeepSeek / Kimi | 直接调 API | API key（已有的复用） |
| CLI Agent | Claude Code、Codex CLI、Gemini CLI、Cursor CLI | 在 `data/workspace` 下的隔离目录跑固定任务，沿用 Deep Dive 的时间预算 | 本机已装；Claude Code / Codex 现成就有 |
| 有 API 的 Agent 产品 | Perplexity API、Devin API、ElevenLabs | 调 API | key，可能要付费（D4） |
| 只有网页的产品 | Lovable、Manus、Genspark | 浏览器自动化（Codex 浏览器操作），保存截图和产出 | 账号需要你登录；不能自动注册、不能付费 |

### 6.2 评测集

- **按品类建任务集**：编码 Agent、深度研究、浏览器 Agent、应用生成（Lovable 类）、语音、图像 / 视频、企业搜索。每个任务集 10–30 个任务。
- **任务来源**：优先用你自己真实遇到的任务（从规划 / 复盘的事项里挑脱敏后的），其次是公开基准的子集。这样分数直接对应你的使用场景，也不容易被厂商针对公开榜单优化。
- **每个任务**：输入、环境准备脚本、确定性检查（测试通过、文件存在、输出格式）+ 评分规则（LLM 评判，按条打分并写理由），记录成功率、步数、耗时、花费。
- **防止评判偏差**：评判模型和被测产品不能是同一家；每个版本对至少 3 个任务做人工抽查，记录人和模型评分的一致率。

### 6.3 触发方式

- 事件触发：S/A 级事件命中某个产品的版本变化 → 排队重跑这个产品的评测（放到非专注时间）。
- 定期：每月全量跑一次，看看有没有悄悄发生的退化。
- 产出：版本对比报告（任务级的赢 / 输 / 平，代表性样例的原样输出对照），回挂到事件和产品档案。

### 6.4 第一个落地品类：编码 Agent

Claude Code 和 Codex 本机现成，不需要额外账号，Deep Dive 已经验证过「克隆仓库 → 跑任务 → 存原样输出」的链路。所以评测先做这个品类，跑通后再扩到模型 API，最后做网页产品。

## 7. 沉淀：越用越值钱的部分

| 产物 | 内容 | 更新方式 | 知识库路径 |
|---|---|---|---|
| 公司活档案 | 战略主线（3–5 条，带支撑事件）、产品矩阵、定价史、能力时间线、关键人物、对手、未解问题 | 每个 B+ 事件进来后做增量更新（只改受影响的小节，改动留历史） | `kb/intel/companies/<slug>.md` |
| 产品档案 | 定位、功能树、定价史、评测曲线、你的一手体验、口碑摘要 | 同上 | `kb/intel/products/<slug>.md` |
| 品类对比矩阵 | 同一品类各产品的功能 × 定价 × 评测分数 | 事件或评测后重算 | `kb/intel/categories/<slug>.md` |

## 8. 判断力训练闭环

只看 AI 写的解读，判断力很难提高。所以要在看答案之前先逼自己表态，然后让现实来打分。

1. **先判断，后看解读**（S/A 级默认开启，见 D5）：打开事件时，先只看「变了什么」，回答 3 个问题：这是进攻还是防守？受威胁最大的是谁？6 个月后它会成功吗（给一个置信度）？提交后才显示 AI 解读，并把你的判断和 AI 的判断并排对比。
2. **预测账本**：可验证的预测带 `resolve_by` 日期，例如「Cursor 6 个月内会推出按任务收费的档位，70%」。到期时进入规划事项提醒你核对；模型先给出建议裁决和证据，最后由你确认。
3. **打分与画像**：用 Brier 分数；按维度（技术可行性 / 用户需求 / 定价 / 竞争反应 / 时间点）统计准确率和校准曲线，找出你系统性偏乐观或偏悲观的地方。
4. **复盘**：每月一次战略复盘：哪些判断错了、错在哪个假设上；错误模式写进 `notes`（经验）。
5. **回流学习**：偏差集中的维度，自动建议一个学习计划主题（例如「定价策略」），走已有的深度学习板块。
6. **案例练习**（可选）：每周从历史事件里挑一个，按案例教学的方式提问（「如果你是 Anthropic 的 PM，面对这个发布怎么应对？」），Agent 追问和点评，记录进账本。

## 10. 成本与风险

- **模型成本**：快照哈希没变就不调模型；候选变化判断和定价结构化用 DeepSeek（和 `_feed_product` 一样）；解读卡用 Sonnet；深度解读和审稿用 Opus，只给 S/A 级。估计每天几十次便宜调用，加上每周 3–8 篇深度解读（预算见 D6）。
- **抓取被封**：降低频率，加条件请求（ETag / Last-Modified）；失败的源单独显示，不影响其他源。
- **噪音**：分级是控制噪音的主要手段；C 级不打扰，只进周汇总。你的升降级操作就是训练信号。
- **幻觉**：事实层只准引用快照和来源；审稿阶段核对每个事实句；推断必须标注。
- **评测不公平**：版本、配置、日期都要记录；任务集版本化，换了任务集的分数不和旧的比较。
- **账号和付费**：需要登录或付费的产品，只在你提供账号之后才评测；平台不自动注册、不自动付费。
