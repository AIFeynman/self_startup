# 开源雷达：按功能检索 GitHub 高星项目（设计稿 2026-11-01）

- **分支**：`feat/product-intel-design`，属于「产品雷达」板块的第 6 个标签，见 [产品雷达设计稿](2026-11-01-product-intel-design.md) 第 9 节。本稿只有设计和原型实验，不改平台代码。
- **一句话**：把 GitHub 上 stars > 1000 的 AI / 软件工具类项目（包括教程、书、awesome 列表）都打上「类型 + 领域 + 功能」标签，用户用一句中文说想做什么（「我想做 PDF 解析」），就能找到对应项目，可以按相关性排，也可以按 star 排。
- **分类体系**：[oss-radar-taxonomy.json](oss-radar-taxonomy.json)（版本 `2026-11-01.1`）。

## 0. 目标与完成标准

**目标**：找开源项目时不用再拼英文关键词翻 GitHub 搜索。用一句话说需求，几秒内拿到「真能做这件事」的项目列表，并能用类型、领域、语言、是否活跃来筛选。

| # | 检查项 | 怎么验证 |
|---|---|---|
| O1 | 覆盖：stars > 1000 且不属于 misc/other 的仓库全部入库并打标签，标签字段合法率 100%（非法的会重问） | 入库数和 GitHub 搜索计数对账；校验脚本 |
| O2 | 功能检索质量：在 ≥ 60 条中文功能查询的标注集上，目标项目进 top 10 的比例（recall@10）≥ 90%，top 3 命中率 ≥ 80% | `oss_eval` 脚本，每次改检索或标签都重跑 |
| O3 | 两种排序：「相关性」按综合分；「star」只排相关分达标的（重排 ≥ 2），不能混进无关的高星项目 | 标注集里检查按 star 排的前 10 没有 0/1 分的项目 |
| O4 | 速度：首屏结果 ≤ 3 秒（改写 + 全文召回），精排结果 ≤ 8 秒后替换；重复查询走缓存，1 秒内返回 | 埋点计时 |
| O5 | 新鲜：每天收录新跨过 1000 star 的项目，每周刷新 star 和活跃度；README 或描述变了才重新打标签 | 任务日志；`label_src` 哈希 |

**通用性要求**：检索链路不为单条查询调参。15 条原型查询只是证据，验收以更大的标注集为准（O2）。

## 1. 为什么 GitHub 自带搜索不够

- 只能对 name / description / topics 做关键词匹配，中文需求直接搜不到。原型里 15 条中文功能查询，模拟 GitHub 关键词搜索的 baseline **全部返回空**。
- 英文关键词也有字面问题：MinerU、docling 的描述里不一定出现 "PDF parser"；caveman 的描述是 "why use many token when few token do trick"。
- 能做 PDF 解析的项目和能生成 PDF 的项目共享关键词 "PDF"，靠关键词分不开。

所以需要两样东西：**入库时给每个项目写好功能标签和中文一句话**（把「它能做什么」显式化），**查询时理解需求、召回、再由模型判断「能不能做这件事」**。

## 2. 数据范围与采集

| 项 | 数字（2026-11-01 实测） |
|---|---|
| stars > 1000 | 66,112 |
| 其中 1000–2000 | 32,215 |
| 近一年有 push | 38,623 |
| 未归档 | 60,657 |

- **全量拉取**：Search API 每条查询最多返回 1000 条，所以按 star 区间切片（如 `stars:1000..1010`），切到每片 < 1000 为止，约 150–250 次请求。README 用 GraphQL 每次 50 个仓库批量取（约 1,320 次请求，在 5000 次/小时的额度内）。沿用 `_feed_sources._gh_headers`。
- **增量**：每天查 `stars:>1000 created/pushed` 的新项目，入库并打标签；每周刷新 star、pushed_at、archived。
- **README 摘录**：取正文前 1,500 个字符（去掉徽章、图片、HTML），只给标注模型用，不入全文索引。
- **范围**：用户要求的「AI、软件工具相关」按分类体系判断：被标成 `misc/other` 的（个人主页、纯资料存档、和软件无关的）不进检索；教程、书、awesome、面试题都保留（`kind = tutorial / book / awesome`、领域 `cs`）。

## 3. 分类体系（摘要，全文见 JSON）

每个仓库一条标签：

```json
{"k": "library", "d": "doc_parsing", "d2": ["ai_data"], "ai": "for_ai",
 "t": ["PDF 解析", "版面分析", "表格识别", "公式识别", "PDF 转 Markdown"],
 "s": "把 PDF 等复杂文档转成适合大模型使用的 Markdown/JSON。"}
```

- **k（类型，12 种）**：app、library、framework、plugin、model、dataset、research、tutorial、book、awesome、template、other。
- **d / d2（领域）**：17 个一级、约 100 个二级，主领域 1 个，次领域 0–2 个。例如 `data.doc_parsing`、`agent.coding_agent`、`ops.selfhost`、`system.phone_mod`、`cs.career`。
- **ai（和 AI 的关系）**：core（AI 本身）/ for_ai（给 AI 用的工具）/ ai_powered（用了 AI 的应用）/ none。
- **t（功能标签，3–8 个）**：自由文本的中文功能短语，**检索的主要依据**。一级领域只负责粗召回和筛选，「能做什么」靠 t 和 s。
- **s**：40 字以内的中文一句话，说清楚它做什么。

**设计原则**：领域按「用户想解决的问题」分，不按技术栈分（PDF 解析放 `data.doc_parsing`，不放 `ai.cv`）。每个二级领域都给了正反例，减少边界摇摆。

## 4. 标注流水线

**引擎**：订阅版 Haiku（`reclaude -p --model claude-haiku-5-5`），跟随 `settings.model_tiers.light`。

| 参数 | 选择 | 依据（原型实测） |
|---|---|---|
| 每次调用的仓库数 | 50 | 50 个每次都完整返回；100 个时延迟和输出波动大 |
| 分类体系放哪里 | `--system-prompt`（替换 Claude Code 自带的 ~24k 系统提示，可缓存），`--tools ""` | 输入从 ~49k 降到 ~13k，每次调用 $0.0155 → 约 $0.010 |
| effort | 默认（不设 low） | low 会出现非法代码和明显错分（openwrt → lang_runtime、mimotion → games） |
| 并发 | 4 | 单次 32–98 秒 |

**校验与重问**：代码不在体系里（默认 effort 下也偶尔出现 `cryptography`、`video_stream`、`edu` 这类）、t 少于 3 个、s 为空的条目，汇总后单独重问一轮；还不合法的落到 `misc/other`，并进「待人工」列表。

**一致性**（同一批 400 个仓库跑两次）：类型 0.88–0.91；二级领域 0.80–0.88，换成「在对方的 d/d2 里」算是 0.90–0.94；一级领域 0.85–0.92；AI 关系 0.95–0.98。`other` 占 2–3.5%，平均每个仓库 4.5 个功能标签。不一致主要出在本来就两可的边界（工具类 Agent 算 coding_agent 还是 agent_ext），检索用 d + d2 + t 一起召回，对这类分歧不敏感。

**功能标签的准确性**（重点抽查文档类 25 个）：MinerU、docling、markitdown、PyMuPDF、各 OCR 工具都进了 `doc_parsing` 并带「PDF 解析 / 版面分析 / OCR」；pdfme、pdf-lib 被标成「PDF 生成」，和解析分开；firecrawl、crawl4ai 主领域是 crawler，d2 是 doc_parsing。

**重标规则**：`label_src = sha1(描述 + topics + README 摘录)`，变了才重标；分类体系版本升级时只重标受影响领域的仓库。

**功能标签归一化**（P2）：t 是自由文本，同义词会分散（「PDF 转 Markdown」「PDF→MD」）。入库后对全量标签做一次聚类，生成「规范标签 + 别名」表，索引时同时写规范名和别名。

## 5. 检索机制

```
用户一句话 ──► ① 需求改写 ──► ② 多路召回 ──► ③ 特征打分 ──► 首屏（≤3s）
                                                   │
                                                   └► ④ 模型精排前 40 ──► 替换结果（≤8s）
                                                                      └► star 排序 = 精排分 ≥ 2 的按 star 排
```

1. **需求改写**（一次便宜调用）：把中文需求改写成 `{must, should, not, domains, kinds}`。must/should 同时给中英文功能词，not 用来排除相反功能（「生成 PDF」查询排除「PDF 解析」），domains 给 1–3 个二级领域，kinds 只在用户明确要教程 / 书 / 库时给。
2. **多路召回**（本地 SQLite，零成本）：
   - FTS5 trigram 索引，字段为 name、s、t、description、topics（复用 `kb.py` 的做法；2 个字的中文词退回 LIKE）。
   - **短语召回**：must / should 原样匹配。
   - **原子词召回**：把改写出的长短语拆成词，命中不同原子词 ≥ 2 个的进入候选。原型里「给 Claude Code 省 token」就是靠这一路把 caveman（标签「Claude Code 技能 / Token 压缩」）召回的。
   - **领域召回**：d 或 d2 命中 domains 的全部进入候选。
   - （P2，可选）向量召回：s + t 用 bge-m3 做向量，补同义表述。原型阶段前三路已经覆盖 15/15，先不上。
3. **特征打分**：must 命中 1.0 + bm25 加成、should 命中数、原子词命中数、主 / 次领域加分、类型符合 ±、命中 not 且没命中 must 时扣分，再加 0.12·log10(stars) 作为热度。这一步决定首屏顺序和送去精排的前 40 个。
4. **模型精排**：把需求和前 40 个候选（name + s + t，约 3k token）交给模型，按「能否直接满足需求」打 0–3 分。最终分 = 精排分 + 0.3·特征分 + 0.12·log10(stars)。**按 star 排序时只保留精排分 ≥ 2 的**，避免高星但不相关的项目混进来。
5. **筛选**：类型、一级 / 二级领域、AI 关系、语言、近 N 个月有 push、排除已归档。筛选在召回之后、精排之前做。
6. **缓存**：同一查询（归一化后）的改写结果和精排结果缓存 7 天；标签库更新后失效。

### 5.1 原型评测（约 450 个已标注仓库，15 条中文功能查询）

| 方案 | 前 8 名里有目标项目且排序合理 | 典型问题 |
|---|---|---|
| baseline：原文关键词匹配 name/desc/topics | 0 / 15（全部为空） | 中文需求和英文描述对不上 |
| 改写 + 短语召回 + 领域召回 + 特征打分 | 12 / 15 | MinerU、docling 在「PDF 解析」里排得低；「让 AI 管理 k8s」漏了 kubernetes-mcp-server；「给 Claude Code 省 token」漏了 caveman |
| + 原子词召回 + 模型精排 | **15 / 15** | 目标项目都在第 1–3 名，按 star 排序也只剩相关项目 |

精排后的例子：「我想做 PDF 解析」前 8 名是 opendataloader-pdf、PyMuPDF、pdfplumber、MinerU、docling、olmocr、marker、zerox（都是 3 分）；「生成 PDF 报表」第一名是 pdfme，解析类工具降到 1 分；「路由器刷固件」是 lede、openwrt；「统一多家大模型 API 的网关」是 OmniRoute、litellm、gpt-load。

**局限**：原型库只有约 450 个仓库，全量 6.6 万个时候选更多、近似项目更多，精排的前 40 个窗口可能不够。所以 O2 要求在 ≥ 60 条查询的标注集、全量库上验收；不达标时先把精排窗口扩到 80，再考虑向量召回。

## 6. 成本

### 6.1 一次性全量标注（约 6.6 万个仓库，1,320 次调用 × 50 个）

| 方案 | 估算 | 说明 |
|---|---|---|
| **订阅 Haiku（默认）** | API 等价约 **$13–16**，实际消耗订阅额度；4 并发约 6–9 小时 | 每次调用约 $0.010（实测 $0.005–0.014）。加 README 摘录每次多约 2 万 token 输入，约 +$0.002 |
| DeepSeek v4 flash | 约 **$3.5**（不带 README）/ **$7**（带 README） | 分类体系 12k 走缓存命中（$0.0028/M），每次未命中输入约 7.5k–27k（$0.14/M），输出约 5.5k（$0.28/M，关掉思考）。质量需要用同一批 400 个仓库对比后再定 |
| Jev | 约 **$1.7** | 只能回答是 / 否概率，不能出标签和一句话；只能当「是否 AI / 软件工具」的过滤器。分类体系里的 `misc/other` 已经起到这个作用，**不需要** |

**增量**：每天新跨过 1000 star 的仓库估计几十到一两百个，每天 1–4 次调用，可以忽略。

### 6.2 每次查询

| 步骤 | 订阅 Haiku（实测） | DeepSeek flash（估算） |
|---|---|---|
| 需求改写 | 约 $0.0003 / 条，单独调用 6–10 秒（CLI 启动开销） | 约 $0.0002，1–2 秒 |
| 精排 40 个候选 | $0.0008–0.0024，11–20 秒 | 约 $0.0006，2–4 秒 |

订阅 CLI 每次调用有几秒的启动开销，精排要 11–20 秒，达不到 O4。所以**默认：批量标注走订阅 Haiku，线上改写和精排走 DeepSeek flash**（已有 key 和 `_feed_product` 的调用方式）。每天查 50 次的话，每月不到 $2。也可以换成 Anthropic API 的 Haiku（每次约 $0.002，2–4 秒），见决策 O-D2。

## 7. 存储与代码位置

- 表：`oss_repos`（name、stars、lang、topics、description、readme_excerpt、pushed_at、archived、updated）、`oss_labels`（name、k、d、d2、ai、t、s、taxonomy_ver、label_src、labeled_at）、FTS5 虚表 `oss_fts`、`oss_query_cache`。
- 代码：`app/modules/_oss_collect.py`（切片拉取、GraphQL README）、`_oss_label.py`（打包、校验、重问）、`_oss_search.py`（改写、召回、打分、精排）。挂在「产品雷达」的 `intel.py` 下，后台任务走 `jobs.py`，**不新建独立服务**。
- 页面：产品雷达第 6 个标签「开源雷达」。顶部一个搜索框，下面是筛选条（类型 / 领域 / 语言 / 活跃）和「相关性 | star」切换。结果卡片显示一句话、功能标签、star、语言、最近 push 和精排给的理由。没有输入时按领域浏览（领域树 + 每个领域按 star 排序）。

## 9. 需要你拍板的问题

| # | 问题 | 我的默认选择 | 理由 |
|---|---|---|---|
| O-D1 | 标注时要不要带 README 摘录 | **带**，前 1,500 字 | 很多仓库的描述太短或太营销化（caveman、claw-code），README 能明显提高功能标签质量；成本增加约 20% |
| O-D2 | 线上改写 / 精排用哪个模型 | **DeepSeek flash** | 订阅 CLI 单次 11–20 秒太慢；DeepSeek 已有 key、便宜。备选是 Anthropic API 的 Haiku |
| O-D3 | 范围是否剔除 `misc/other` | **剔除**，但保留教程 / 书 / awesome | 符合「AI、软件工具相关」；剔除的列表可以在页面上单独查看 |
| O-D4 | 向量召回 | **先不上**，O2 不达标再加 | 原型上前三路已经够用，少一个依赖 |
| O-D5 | 是否用 DeepSeek 替代订阅做全量标注 | **不替代**，先用订阅；DeepSeek 只在订阅额度紧张时，用同一批 400 个仓库对比质量后再切 | 你要求优先走订阅 |
